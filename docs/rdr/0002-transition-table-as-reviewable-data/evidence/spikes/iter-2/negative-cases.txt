## Merge semantics (contexts clause; A13)


Idempotence: a byte-identical atom from rule + inherited context collapses to

the reversed `use` order digests identically, so the result does not depend
on `use` iteration order.

### Delimiter-bearing controls — THE discriminating witnesses (A13)

Every control above uses single-member literals, under which a joined
rendering and a member sequence are the same string. These carry the joining
delimiter inside a member, so they distinguish the two candidate keys.

```
merge-delim-atom  rows                     4
merge-delim-atom  atoms (row 1)            finalized_at.eq=a@match finalized_at.eq=a,b@match 
write-delim-a     labels                   labels=[x,y|z]
write-delim-b     labels                   labels=[x|y,z]
```

Two contexts contributing `in = ["a,b", "c"]` and `in = ["a", "b,c"]` on one
key and block yield TWO atoms, so the rule stays the dead rule the author
wrote. The two set-write spellings yield DIFFERENT values. Against the
pre-fix spike both collapsed — one atom, and `labels=x,y,z` for both writes.

## Delimiter-parameterized controls — THE discriminating witnesses (A13)

Every other control uses single-member literals, under which a joined rendering
and a member sequence are the SAME string — so none of them can tell a correct
merge key from a joined one. These carry the joining delimiter inside a member.

Parameterized over five plausible join delimiters, per Testing Strategy 2: a
black-box test cannot read the delimiter a wrong implementation chose. This is
not hypothetical — the pre-fix spike joined on `,` and collapsed ONLY the comma
case; all four other delimiters yielded two atoms while the defect was live.
A single-delimiter control would have passed it.

### Atom arm — MUST yield two atoms for every delimiter

```
merge-delim-comma finalized_at atoms in row 1: 2
merge-delim-semi finalized_at atoms in row 1: 2
merge-delim-pipe finalized_at atoms in row 1: 2
merge-delim-space finalized_at atoms in row 1: 2
merge-delim-empty finalized_at atoms in row 1: 2
```

### Write arm — the two spellings MUST normalize to different values

```
comma    a: labels=["x,y" "z"]       b: labels=["x" "y,z"]       distinct
semi     a: labels=["x;y" "z"]       b: labels=["x" "y;z"]       distinct
pipe     a: labels=["x|y" "z"]       b: labels=["x" "y|z"]       distinct
space    a: labels=["x y" "z"]       b: labels=["x" "y z"]       distinct
empty    a: labels=["xy" "z"]        b: labels=["x" "yz"]        distinct
```

The write RENDER quotes each member for the same reason the identity is
length-prefixed: an unquoted separator is forgeable. The `pipe` row caught this
during Stage 6 — an unquoted `|` separator rendered `["x|y","z"]` and
`["x","y|z"]` alike, so a test asserting on the rendered value would have passed
the collision even though the identity was already correct.
