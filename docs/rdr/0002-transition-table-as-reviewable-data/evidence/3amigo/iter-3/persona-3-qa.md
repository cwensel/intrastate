# 3amigo Iteration 3 — Persona 3 QA / Tester

- **QA3-001 — The delimiter-bearing merge control's pass/fail arm is an RDR 0006 verdict that does not exist, so A13's owed assertion cannot be written.** Testing Strategy scenario 2 states the control as two obligations: the pair `in = ["a,b", "c"]` / `in = ["a", "b,c"]` on one key and block "must yield **two** atoms, **and the rule must be a dead rule for lint rather than a live expanding row**." The first half has an oracle (atom count on the normalized value). The second half does not, and it is the half the RDR relies on to explain what a collapse costs: "dead rule" is RDR 0006's unreachable-rule finding, RDR 0006 is Pending (Capability Dependencies), the Testing Strategy defers all cross-row lint to scenario 4, and the Minimum Viable Validation already refuses to count the one lint assertion it names ("Marking the overlap assertion green before RDR 0006 lands would be asserting on a stub"). So the second half is either untestable in this RDR's tree or must be reduced to a load-side proxy the draft never names — and the draft never says which. Worse, a merge keyed on a joined rendering fails the count-two arm only if the joining delimiter happens to be the comma the fixture uses; the clause says "the implementation's own joining delimiter, whatever it is", which is not a value a black-box test can read. The literals clause forbids joining on *any* delimiter, but scenario 2 supplies no delimiter-agnostic oracle (e.g. asserting the merge key is derived from the member sequence structurally, or asserting over a matrix of candidate delimiters), so the control is written against a delimiter the test author must guess. Prevents: the single MVV assertion A13 is Pending on — the delimiter-bearing distinct-literal merge control — from being written with a determinate pass/fail arm at all.
  Passage: Testing Strategy scenario 2, the "distinct-literal control must use members containing the implementation's own joining delimiter" paragraph (with Critical Assumptions A13 and the `merge atoms` row of Conditional Mini-Checks `trace`).

- **QA3-002 — `[model.metadata]` "carried verbatim / untouched" is asserted with no oracle: the clause removes it from every comparison the RDR defines.** The Normative Contracts `[model.metadata]` clause requires the loader to "carry it through to the normalized model untouched" over "arbitrary keys, values, and nesting", and Testing Strategy scenario 1 lists "`[model.metadata]` carried verbatim" as an Expected. But the same clause places it "outside the dump's field list and outside the Round-Trip invariant, which compares candidate-row sets", and the dump contract's field list (row identity, locator, outcome, atoms, gate ids, next tags, writes, required-owned, escape classes) excludes it. There is therefore no defined value the test compares against: the Round-Trip invariant explicitly cannot see it, the dump explicitly must not carry it, and the only witness the RDR cites is the `trace` row's `metadata_keys=owner,review_cadence` — a sorted list of top-level key *names*. That oracle is satisfied by a loader that decodes keys and discards every value, coerces every value to string, or flattens nesting. A "verbatim" claim over an unconstrained-shape table needs a stated comparison (deep-equal against the decoded `map[string]any`, say) and the draft states none; the field-list clause's "MUST carry every field of it" obligation, which is what makes the other fields assertable, is deliberately withheld here. Prevents: the scenario 1 assertion that `[model.metadata]` values and nesting survive the load — a nested-and-typed metadata fixture (int, array, sub-table) compared to its source — has no expected value to compare to.
  Passage: Normative Contracts, the `[model.metadata]` extension-namespace clause (with Testing Strategy scenario 1, Expected).

- **QA3-003 — The `[initial]`-undeclared-key control is named for a category the spike refuses under a different one, and the draft's own probe reasoning does not cover it.** Testing Strategy scenario 3 lists "an `[initial]` key that is undeclared" and then, in the probe paragraph, assigns it: "`malformed initial declaration` is controlled by its value arm ... **and by the undeclared-key variant above**." The spike's actual refusal for that fixture is `neg-initial-unknown … refused: unknown tag "nosuchtag" written` (`evidence/spikes/iter-2/negative-cases.txt`) — category `unknown tag`, not `malformed initial declaration`. Since the Expected clause is emphatic that "the assertion is on the category, not the message text", the fixture as promoted will fail the assertion the draft assigns to it, or the implementation will be steered to emit `malformed initial declaration` for an undeclared key and thereby diverge from the spike the same scenario says to promote. The draft cannot have both. Note this is not the closed observed-key arm: that arm is handled by the probes and is separately named as unauthorable — this is the *undeclared* key, which is authorable and does have a fixture. Prevents: the per-category control for `malformed initial declaration` in scenario 3 — the assertion cannot be written because the draft names two different expected categories for the same fixture.
  Passage: Testing Strategy scenario 3, the probe paragraph clause "`malformed initial declaration` is controlled by its value arm ... and by the undeclared-key variant above".

- **QA3-004 — Scenario 3's three escape-shape controls are asserted to be distinguishable but share one category, so the assertion the draft justifies them by cannot discriminate.** Scenario 3 requires "malformed escape declarations (an empty write block on an escape rule, and separately an escape rule carrying a `clear` list — the normalizer is the only enforcement point for a write-free escape row, **so each shape needs its own control**)", and the category list adds the `gate`-list shape. The Expected clause then fixes the oracle: "refused with the **one** category its mutation targets and no other ... the assertion is on the category, not the message text." All three shapes carry the *same* category — `malformed escape declaration` — which the category-floor list confirms ("a write block, clear list, or `gate` list on an escape rule"), and the spike bears this out: `neg-escape-with-write`, `neg-escape-with-clear`, and `neg-escape-with-gate` all emit the identical string `malformed escape declaration: escape rule "draft-no-match-escape" carries a write block, clear list, or gate list`. Under a category-only oracle the three controls are one control run three times: an implementation that detects only the write-block shape and ignores `clear` and `gate` entirely passes two of the three by accident of the fixture also carrying a write block — or, if the mutations are truly single, fails silently in a way the category assertion cannot name. The draft's stated reason for three controls ("each shape needs its own control") requires a per-shape discriminator the category set deliberately does not provide, and the only discriminator available is message text, which the Expected clause bans. Prevents: the scenario 3 assertion that an escape rule carrying a `clear` list, and one carrying a `gate` list, are each independently refused — the oracle cannot tell those two from the write-block case.
  Passage: Testing Strategy scenario 3, the "malformed escape declarations ... so each shape needs its own control" clause, against its Expected ("the assertion is on the category, not the message text").

- **QA3-005 — Scenario 3's witness counts and A1's disagree with each other and with the transcript, so "the promoted set must not be narrowed" has no countable baseline.** Scenario 3 says "**Thirty-five of these controls are witnessed by the §D7 spike**, one refusal per mutated fixture", and closes with "Implementation promotes these fixtures; it may extend the set but must not narrow it." Critical Assumptions A1's evidence, describing the same run, says "**32 negative fixtures** refuse one category each and **2 positive controls** load." The transcript actually lists **37** refusal lines (35 `neg-*` plus two `probe-*`) and **5** positive controls (`pos-no-initial`, `pos-no-terminal`, `kata-fixture`, and two `-strict-only` STRICT-OK lines). Three different counts for one artifact, in a draft whose promotion rule is a *cardinality* rule. A promotion test that asserts "at least N controls survived" has no N; a reviewer checking the not-narrowed obligation cannot tell whether the probes and the strict-only controls are inside or outside the protected set. Prevents: the promotion guard test scenario 3's closing sentence calls for — an assertion that the production negative-fixture set is not smaller than the promoted spike set — because the required count is stated three incompatible ways.
  Passage: Testing Strategy scenario 3, Expected ("Thirty-five of these controls are witnessed ... must not narrow it") versus Critical Assumptions A1 Evidence ("32 negative fixtures ... and 2 positive controls").

- **QA3-006 — The probe fixtures scenario 3 cites by path do not exist under those names, so the enumeration that closes the unauthorable-arm gap is not reproducible from the citation.** Scenario 3's probe paragraph closes: "Verified by enumeration this stage: both authorings were built and each refused under the writer-binding category (`evidence/spikes/iter-2/probe-a.toml`, `probe-b.toml`)." Prevents: re-verification of the "both authorings were built and each refused under the writer-binding category" enumeration, which is the justification for the deliberately-absent observed-key control in scenario 3.
  Passage: Testing Strategy scenario 3, the probe paragraph's evidence citation (`evidence/spikes/iter-2/probe-a.toml`, `probe-b.toml`).

- **QA3-007 — The fail-fast clause's own carve-out for absorbed defects describes a failure mode that no scenario-3 fixture can detect, and the draft names no substitute oracle.** The version-gate/fail-fast clause states the one-defect-per-fixture rule makes check order unobservable, then carves out: "A defect consumed earlier in the pipeline — merged away, de-duplicated, or otherwise absorbed before any category is decided — trips *zero* categories rather than one, so a one-defect fixture for it asserts nothing and the order-unobservability argument does not cover it." It then asserts such absorption "is a normalization defect in its own right (the merge clause's set-over-full-identity obligation, and the literals clause's ban on joined identities, exist to prevent exactly this)". But those two clauses are guarded only by the merge controls of scenario 2 — the very controls QA3-001 shows have no determinate arm — and scenario 3, which is the *only* place the draft tests refusal categories, is built entirely on the one-defect rule the carve-out just excluded. A defect that is absorbed produces a *loading* document with no refusal at all: scenario 3's oracle (refused with exactly one category) is trivially unsatisfied and the fixture is not even in the set, so nothing observes it. The draft correctly identifies the blind spot and then routes it to a clause whose control is owed, leaving zero live assertions on absorption. Prevents: any regression test for "a defect that should have been refused was silently absorbed instead" — the draft names the class, disclaims the one-defect rule for it, and supplies no fixture shape or oracle in its place.
  Passage: Normative Contracts, the version-gate clause's "Load is fail-fast" block, third paragraph ("That argument is scoped to defects that **reach a check**").

- **QA3-008 — Round-Trip requires comparing "the locator's presence and its rule-identifying part" but the field's structure is left optional, so the comparison has no defined projection.** The Round-Trip / Inverse Invariants section fixes the invariant over "the full field list the dump contract carries ... with the source locator's optional line/column detail excluded from the comparison", and then insists the exclusion is partial: "The locator's **presence and its rule-identifying part** are compared, even though its line/column detail is not: excluding the whole field would let a normalizer that dropped locators entirely satisfy the invariant." That is a correct design instinct with no testable projection behind it. Technical Design says only "The locator must identify at least the model id and rule id; byte line/column coordinates are optional diagnostic detail" — "at least" leaves the field's shape open, so a locator may be an opaque string, and the spike's is exactly that (`source=rdr:prelock`, a single rendered token in `output.txt`). Given an opaque locator, a test cannot separate the rule-identifying part from the positional detail in order to compare one and skip the other: it must either compare the whole field (which the section says would churn, and which fails the moment a normalizer adds line numbers) or compare nothing (which the section says lets a locator-dropping normalizer pass). The draft never fixes a structured locator, a canonical `(model id, rule id)` accessor, or a normalization step that strips positional detail before comparison. Prevents: the scenario 5 permutation assertion at its stated strength — "the normalized value is identical in every case ... compared over the full field list including the locator's rule-identifying part" — cannot be written, because there is no defined operation that yields the rule-identifying part of a locator.
  Passage: Round-Trip / Inverse Invariants, the paragraph "The locator's **presence and its rule-identifying part** are compared" (with Technical Design's "must identify at least the model id and rule id").
