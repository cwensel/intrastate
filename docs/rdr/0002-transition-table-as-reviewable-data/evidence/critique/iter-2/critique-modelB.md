## 1. The three most likely ways implementation goes wrong

### 1a. The dump is built as "the reviewable artifact" and then can't do the one job it exists for

**Root cause.** The RDR spends its entire Problem Statement and Approach selling the dump as the thing that makes "is this transition legal" have one reviewable answer — "the expanded table view those peers consume," "Reviewers can inspect the full table without maintaining it by hand" (Capability Dependencies), "send diagnostics back to the authored sparse rule." Then, deep in the Round-Trip section, it pulls the rug: "Rendering is a review surface here, and the normalized value is the contract... a textual round-trip is not claimed," and lists three specific, named ways the rendered text is lossy (`<clear>` sentinel collision, unescaped separators on multi-entry fields, unreserved expansion-suffix separator).

**The specific passage that enabled it.** "Three sites make the rendered form lossy today and would each have to be closed by any later RDR that defines a re-readable dump: the `<clear>` sentinel is not reserved in the tag-value space, so an authored value of `<clear>` renders identically to a cleared tag; set-valued and multi-entry fields are rendered with unescaped separators; and the expansion suffix has no reserved separator, so a rule id containing it makes `(rule id, suffix)` unrecoverable from the rendered identity."

This is not a hypothetical edge case dismissed as out of scope — it is a *named, specific, currently-true defect* in the exact artifact the entire RDR is framed around ("Transition Table As Reviewable Data" is the title). A reviewable artifact whose author has enumerated the specific strings that will silently lie to a human reader is not reviewable in the sense the Problem Statement promises.

**Symptom the user will see.** A flow author authors a rule that clears `finalized_at` and, separately, another rule that legitimately writes the literal string `<clear>` to some tag (unlikely today, but the RDR does not forbid it — no normative contract reserves the value). Both render identically in the dump. A reviewer approving a PR based on the dump text cannot distinguish "this rule clears the tag" from "this rule sets the tag to the four-character string `<clear>`." The RDR's own fidelity table confirms this is not hypothetical: it's listed as a currently-lossy exemption, present at initial ship, not something introduced by later drift.

### 1b. The version gate becomes a wall with no door

**Root cause.** C-001 (from the prior pass) added `[model].version = 1` as the only accepted version, refused before normalization. This closes the compatibility-gate hole the first pass found. But the fix is purely defensive — it stops a version-2 file from being silently misinterpreted as version 1 — and the RDR does nothing to describe what happens on the *day* someone needs version 2. There's no migration story, no coexistence story (can a repo have some v1 and some v2 tables during a rollout?), no CLI verb, no even-a-sentence acknowledgment that the schema will need to evolve given RDR 0003 is explicitly "Pending" and will add "predicate operators" this RDR "defers." The RDR treats the schema as simultaneously final ("Version `1` is the only version this RDR accepts") and provisional ("Exact field layout needs spikes before lock" is listed as a *con* of the chosen alternative, unresolved).

**The specific passage that enabled it.** "`[model]` MUST contain `id` and `version`. Version `1` is the only version this RDR accepts; any other version MUST be refused before normalization." Compare against Alternative 1's own admitted con: "Exact field layout needs spikes before lock." The RDR locks the field layout as normative ("The source schema MUST use the Resolve spike field layout") while never specifying the version-bump procedure that the schema's own admitted immaturity all but guarantees will be needed soon (RDR 0003 is Pending and this RDR explicitly says "RDR 0003 must expand the predicate grammar or this table format becomes too weak for the target flows" as A3's own "If wrong" case).

**Symptom the user will see.** The first time RDR 0003 lands and needs one more predicate operator slot, or RDR 0004 needs an additional accessor-reference shape, every existing `.toml` table in the repo has two choices: get rewritten in lockstep with the schema bump (a repo-wide flag day with no incremental path), or the version number silently doesn't change and the schema quietly grows in a way the "version 1 is locked" contract didn't anticipate, defeating the entire point of having a version field. Either way, the compatibility gate that was added specifically to prevent silent misinterpretation produces a hard stop with no specified recovery, which is a worse operational failure mode than the one it fixed.

### 1c. The load/lint arity split creates a hidden circular dependency that stalls Phase 5 indefinitely

**Root cause.** The RDR is very insistent that its own MVV is self-contained and load-bearing ("the Minimum Viable Validation is in scope and will be executed during implementation, not deferred" is literally the Finalization Gate's Scope Verification prompt). But Testing Strategy scenario 4 requires running "RDR 0006's lint over a deliberately overlapping variant" as part of *this RDR's* validation, and the Capability Dependencies table lists RDR 0006 as "Pending" with "Spec Impact: This RDR must expose enough structure for determinism and reachability checks" — i.e., RDR 0006 depends on this RDR, and this RDR's test suite depends on RDR 0006. The Implementation Plan's Phase 5 is literally named "Lint Handshake" and is sequenced last, after Phases 1-4, which means by the RDR's own ordering, scenario 4's lint assertion cannot execute until Phase 5, yet it's presented as part of the "Minimum Viable Validation" that gates lock scope, not as a Phase-5-only deferred check.

**The specific passage that enabled it.** "Separately, run RDR 0006's lint over a deliberately overlapping variant. **Expected**: ... The overlapping variant is reported by lint as an ambiguous overlap before the model is accepted, naming both rows." This sentence is inside the numbered Testing Strategy list that the RDR elsewhere calls out as implementing the MVV, with no caveat that scenario 4's second half is conditionally deferred to RDR 0006's own implementation timeline.

**Symptom the user will see.** A team implementing this RDR reaches the point of writing scenario 4's test, discovers RDR 0006 doesn't exist yet (it's Pending), and has to either stub the lint call, skip the scenario, or block the whole RDR on RDR 0006 landing first — none of which the RDR tells them to do. Whichever they pick, "Minimum Viable Validation... executed during implementation, not deferred" becomes false in practice, and the Finalization Gate's Scope Verification question gets a written answer that quietly papers over an unresolved sequencing gap.

## 2. The one section that will be rewritten within 6 weeks of shipping

**§Technical Design → Round-Trip / Inverse Invariants (the "fidelity" mini-check and its three named lossy sites).**

This section will be rewritten first and fastest, for a structural reason: it is the only part of the RDR that describes a defect in the shipped artifact *while defending shipping it anyway*. Every other section in the RDR either states a positive contract ("MUST", "MUST NOT") or defers a concern to a named peer RDR. This section instead says, in effect, "the reviewable table this whole RDR exists to produce cannot be safely diffed by a human because three specific string collisions exist, and fixing that is somebody else's later RDR." That is an admission that the RDR's own Problem Statement — "every legal edge to live in one reviewable artifact" — is not fully met by what ships.

The moment a real reviewer hits the `<clear>`-vs-literal-`<clear>` ambiguity, or tries to diff two dump outputs across a rebase and finds unescaped separators making a multi-value field visually indistinguishable from a different multi-value field, the fix will not wait for "a later rewrite-capability RDR." It is cheap to reserve the sentinel and escape the separators *now*, at the format-definition stage, and expensive to retrofit once tables exist in the wild with unreserved characters already in use. The RDR itself all but predicts this: "would each have to be closed by any later RDR that defines a re-readable dump" reads as a promise this gets revisited, not a closed decision. Six weeks after shipping is exactly the timescale on which the first real PR review trips over it and someone files the fix.

## 3. The one assumption that will not survive first contact with a real user

**A6 / the "sparse contexts are sufficient factoring" claim, operationalized as: "a human reviewer can read the *sparse* source and correctly predict the *expanded* candidate-row set in their head."**

The RDR verifies A6 via one spike fixture with a three-level inheritance chain (`draft -> prelock -> large-prelock`) and declares success because the normalizer produces the mathematically correct expansion. But the entire value proposition of "reviewable data" rests on a *human*, reading the sparse TOML in a code review tool, being able to predict what candidate rows a rule change produces — not on the tool computing it correctly. The RDR's own Risks section names this directly: "Sparse contexts hide an accidental Cartesian product," and "Future contributors treat row order as priority" — both risks about *human* misreading, not tool correctness — and mitigates them by pointing at the dump (whose fidelity problems are covered above) and at lint (RDR 0006, not yet built).

A6's Evidence is a Spike that proves the normalizer computes the right answer for one fixture. It is not evidence that a reviewer looking at `use = ["prelock"]` plus `[rule.guard.all] iter.lt = 3` plus `[rule.guard.unless] profile.eq = "small"` on a five-line rule block can, without running the tool, correctly reconstruct that this rule's guard is "inherited status=Draft AND inherited stage=prelock AND iter<3 AND NOT profile=small," notice whether a sibling rule's context makes the two ambiguous, or notice a missing case. Real flow authors do not run the normalizer in their head during PR review; they read the diff. The RDR's central claim — that sparse-with-inheritance keeps things reviewable — has never been tested against an actual human reviewer looking at an actual PR diff of a context change, only against whether the *code* computes the expansion correctly. The first time a real reviewer approves a change that silently altered an inherited context's effect on three other rules they didn't look at (because those rules `use` the context and nothing in the diff shows their rows changed), this assumption breaks, and it breaks exactly the way "reviewable data" was supposed to prevent.

## 4. Premortem

*Six weeks post-ship. Written as if it already happened.*

The transition-table normalizer shipped behind RDR 0007's kernel reshape landing, as Prerequisites specified. Phase 1-3 code sat for three weeks waiting on `internal/resolve/resolve.go` to grow an `Atom` type and export `OpExists`/`LiteralTrue`/`LiteralFalse`. When the reshape finally landed, the team fast-tracked Phase 2-3 to catch up on a slipping deadline, and code review compressed to "does it pass the MVV scenarios."

The first production incident came from `internal/transitiontable/normalize.go::Normalize` (the function this RDR specifies but does not name — implementation named it during Phase 2). A flow author editing the RDR-flow table added a new `large-prelock` sub-context inheriting from `prelock`, intending to add one guard for a new rewind path. The context change was three lines. The reviewer read the diff, saw the three lines, approved. What the reviewer did not see — because the dump command wasn't run as part of review, only as part of CI, and CI's dump diff was noisy from an unrelated rename that same week — was that two *other* rules using the `prelock` context now silently expanded differently, because `large-prelock`'s new guard shadowed a case those rules previously matched. The three-line diff was reviewable; its blast radius was not, because nothing in the review surface (the sparse source, per the RDR's own admission that "the rendered table is review support, not the source authors maintain") forced the expanded consequence into the same diff view.

The second incident traced to `TagSet.matches` behavior interacting with the version gate. A contributor bumped `[model].version` from 1 to 2 in a personal branch while experimenting with an RDR-0003-adjacent predicate extension that never landed, then reverted the extension but forgot to revert the version bump. CI's load step refused the file with `unsupported version` — correct per spec — but the refusal category carried no hint distinguishing "you're on an old binary" from "you have a stray version bump," because A5's residual gap (no parse-validation code has ever traveled the CLI envelope before this RDR) meant the `Hint` field was never populated with anything more specific than the bare category name. The contributor spent forty minutes bisecting before finding the one-line diff.

The third and worst incident was silent for two weeks. An escape row for `no_match` on the kata flow was authored with a rule-level `clear` list left over from a copy-paste of an ordinary transition rule — a load-time bug this RDR's own Normative Contracts forbid ("An escape rule... MUST NOT contain a write block or clear list, even an empty one"). The normalizer's load-time validation correctly rejected the malformed rule during Phase 3 development. But the *test fixture* exercising this exact category (`escape rule carrying a write block`) was, per Testing Strategy scenario 3, one of the nine categories "already witnessed by the spike" — and the engineer implementing Phase 3 read that as "this category is already tested," wrote the production validator, ran the existing spike fixture (which still passed, since it was the same fixture), and moved on without writing a *new*, implementation-level negative test for the clear-list variant specifically, only the write-block variant the spike happened to cover. A clear-list-only escape rule — same defect, different field — shipped without a validator path exercising it, because the spike's evidence covered `escape.write-block` and the implementation's coverage silently inherited that exact boundary instead of the full category the normative contract describes. It sat undetected until someone hand-authored exactly that shape for an unrelated reason and it loaded successfully when it should have been refused, producing a normalized escape row with a non-empty `RequiresOwned` derived from the leftover clear list — precisely the defect `adversarial_test.go::TestAdv2b_EscapeEdgeMustNotBypassTheOwnedStateRequirement` exists to catch at the kernel layer, except this RDR's own load-time gate was supposed to make that kernel test unreachable in practice, and didn't.

## 5. Acceptance tests that would have caught each failure at RDR-review time

**AT-1 (catches 1a / C-1): Dump round-trip ambiguity.**
```
Given a transition rule that writes the literal string "<clear>" to an owned tag
And a second rule that clears the same tag via the rule-level `clear` list
When both rules are normalized and dumped
Then the dump output for the two rows MUST be distinguishable by a human reader
  without consulting the normalized value directly
```
This test cannot pass against the current draft — the RDR's own Round-Trip section admits it. Requiring this AT at RDR-review time would have forced either reserving the `<clear>` sentinel in the tag-value space or explicitly scoping the dump as "machine-readable, not human-diffable," rather than shipping under the "reviewable artifact" framing while carrying a known human-legibility defect.

**AT-2 (catches 1b / C-2): Version-bump has a specified path.**
```
Given a transition-model file authored at version 1
And a schema change is proposed that requires a new field
When the RDR (or a successor) is asked "what does an author do to migrate this file"
Then the answer must be a normative sentence in this RDR, not silence
```
Applied at review time: "Version `1` is the only version this RDR accepts" should have been paired with at minimum a Design Decision entry stating what recourse exists at v2 — even "no migration tooling; hand-edit and re-verify" is an answer, but the RDR gives none.

**AT-3 (catches 1c / C-8): MVV self-containment.**
```
Given the Minimum Viable Validation section
When each scenario is checked against the Capability Dependencies table
Then no MVV scenario may depend on a capability whose Status is "Pending"
  unless that scenario is explicitly marked deferred-until-<RDR>
```
Scenario 4's RDR-0006-lint half fails this check today. At RDR-review time this AT would have forced either splitting scenario 4 into an in-scope load-only half and an explicitly-deferred lint half, or moving RDR 0006 lint dependency out of "Minimum Viable Validation" language entirely.

**AT-4 (catches C-4 / A8 residual): `Input.Recognized` emptiness is governed somewhere.**
```
Given a caller of internal/resolve::Resolve with Input.Recognized == ""
And the table's outcomes alphabet (by this RDR's own contract) cannot contain ""
When Resolve is invoked
Then some RDR — this one, RDR 0001, or RDR 0005 — must state whether this is
  refused, and by which component, before this RDR is marked Final
```
The current draft says this "remains open" under JDR 0001 §JD-10 while simultaneously treating the alphabet fix as if it closes the hole. This AT would have surfaced that the fix is partial, not complete, before lock.

**AT-5 (catches C-5): Contradictory guard atoms are diagnosable, not silent.**
```
Given a rule authoring the same (key, operator, literal) atom in both
  `all` and `unless`
When the model is loaded
Then load-time validation MUST reject it as a malformed predicate atom
  (or lint MUST flag it as a named category), not accept it as a
  silently-always-false guard
```
Nothing in the current load-category list or lint-category list covers this. Written as an AT before lock, it would have forced the Normative Contracts' guard-block paragraph to state a resolution rule instead of leaving "combine both into one candidate-row predicate set" undefined for the contradictory case.

**AT-6 (catches C-6): Escape-row RequiresOwned has RDR-owned coverage, not only kernel coverage.**
```
Given an escape rule whose authored `clear` list is non-empty
  (a shape the Normative Contracts forbid)
When Phase 3 load-time validation is implemented
Then a dedicated negative-fixture test for "escape rule with only a clear list"
  (distinct from "escape rule with a write block") MUST exist in this RDR's
  own test suite, not only asserted indirectly via the kernel's adversarial test
```
The current Testing Strategy scenario 3 lists "malformed escape declarations (including an empty write block on an escape rule)" but never separately enumerates the clear-list-only variant. This AT, applied at review time, would have caught the category gap that the premortem's third incident depends on.

**AT-7 (catches C-9): No unspecified interim state for Phase 2/3 while blocked on RDR 0007.**
```
Given Phase 2 and Phase 3 are both blocked on RDR 0007's kernel reshape landing
When an implementer asks "can I make partial progress before the reshape lands"
Then the Implementation Plan must say yes-with-a-defined-shim or
  no-block-fully, not leave it to a one-sentence aside in a Testing
  Strategy scenario
```
Currently only Testing Strategy scenario 6 gestures at an interim state ("the spike mirrors the constants locally because the kernel does not yet export them") without promoting it to a Phase or a normative contract. This AT would have forced that decision into the Implementation Plan before lock.
