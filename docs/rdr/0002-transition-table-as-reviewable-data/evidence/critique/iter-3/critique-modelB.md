## 1. The three most likely ways implementation goes wrong

### 1a. The joined-rendering defect ships to production because its own evidence artifact contains it

**Root cause.** The RDR's central defensive claim — that set-valued literals and set-valued writes are "a member sequence, never a joined string" — is stated twice as a MUST (the literals clause and the write-replaces clause), yet the spike code that is supposed to demonstrate the RDR's shape violates it in both places, and the *promoted, canonical* output file still shows the violation.

**The specific passage.** The write-replaces Normative Contract says: "A `set`-kind write value MUST normalize to an ordered, member-sorted sequence and MUST NOT be joined into a single delimiter-separated string, in the stored value or in any comparison derived from it." The desk trace table in the same document records, under "write values": "**CONTRADICTION** — the spike joins write values (`main.go::renderValue` → `strings.Join(parts, ",")`), so `labels = ["needs work"]` renders `labels=needs work` and `["a,b","c"]` / `["a","b,c"]` collide." I confirmed this directly: `evidence/spikes/iter-2/main.go` line 898 is `return strings.Join(parts, ",")` inside `renderValue`, and the promoted `evidence/spikes/iter-2/output.txt` — the file Testing Strategy scenario 2 names as "the normative fixture… whose nine RDR rows and two kata rows are the expected value" — shows `kata.review-needs-work … next=[labels=needs work; …] write=[labels=needs work; …]`, i.e., a member sequence `["needs", "work"]` rendered as the single string `needs work`, indistinguishable from a genuine one-element set `["needs work"]`.

**The symptom.** RDR 0004's read-back "compares the held value for equality" (cited from JDR 0001 §D7(iv) and restated here). If the production normalizer inherits the spike's `renderValue` pattern — which is exactly what an implementer copying "the normalizer spike" as a starting point would do, since the RDR repeatedly instructs implementers to "promote the Resolve spike into production fixtures" — then two semantically distinct set writes collide, and RDR 0004 will report a write as "applied" when the held value differs from what was actually written, or vice versa. This is not a hypothetical: it is present, today, in the artifact this RDR asks reviewers to trust as evidence the design works. The RDR's own required control (the delimiter-parameterized write-value assertion in Testing Strategy scenario 2) exists specifically because this defect is known to have shipped once already in the spike; there is no structural reason to believe it will not ship again in "real" code, since the fix depends entirely on an implementer noticing and applying a MUST clause buried ~700 lines into a 2070-line document, rather than on any load-time check catching it (per A13's own "If wrong": "It is also the arm that trips zero load categories").

### 1b. The dump's own column-name contract is self-contradicting, so `[dump]` validation breaks on day one

**Root cause.** The Normative Contract fixing the expanded-table dump's column vocabulary enumerates ten snake_case identifiers by name — "`row_identity`, `source_locator`, `outcome`, `atoms`, `gate`, `next`, `write`, `requires_owned`, `escape`, `kind`" — and states "An `order` naming an unknown identifier, repeating one, or omitting one is a `malformed dump declaration` refused at load." But the RDR's own "canonical example" fixture, which Load-Bearing Decisions calls out as one "implementation tests must promote," authors `[dump] order = ["identity", "source", "kind", "outcome", "atoms", "next", "writes", "requires_owned", "gate", "escape"]` — using `identity` (not `row_identity`), `source` (not `source_locator`), and `writes` (not `write`).

**The specific passage.** Compare `docs/rdr/0002-transition-table-as-reviewable-data.md` line 1052 (`row_identity`, `source_locator`, ..., `write`, ...) against `evidence/spikes/iter-2/rdr-fixture.toml` lines 181-185 (`identity`, `source`, ..., `writes`, ...). I verified this by direct grep against both files; the mismatch is exact and threefold.

**The symptom.** The first implementer who writes the `malformed dump declaration` check against the letter of the Normative Contract will find that the RDR's own promoted canonical fixture — the one Testing Strategy scenario 1 says to parse, and the one whose normalized output (`output.txt`) scenario 2 says is "the expected value" — fails to load under the very rule this RDR just wrote. Someone will have to decide, unreviewed, whether to rename the fixture's `[dump]` keys or rename the Normative Contract's column vocabulary, and that decision changes a public identifier surface ("Category identifiers are… an API surface, not message text") with no process specified for it. This is a small defect in isolation, but it is diagnostic of the larger problem: a 2070-line document with this much internal cross-referencing has enough surface area that self-consistency is no longer being verified end-to-end, even by the extensive iterative review this RDR has clearly already been through.

### 1c. Phase 2/3 cannot be implemented at all until RDR 0007's kernel reshape lands, and the rest of the cluster is locked around a hole

**Root cause.** Four of fourteen Critical Assumptions (A9, A10, A12, A13 at the header count — A11 and A14 were resolved this pass) remain `Pending` at lock time, and two of them (A9, A12) are blocked on code that does not exist: "On `main` `internal/resolve/resolve.go::Row.Guard` is a `string`, `Row.Match` is a flat `[]Tag` equality list… there is no `Atom` type, no operator-token type, no per-atom block field, and no `OpExists`/`LiteralTrue`/`LiteralFalse` anywhere in the repo." Meanwhile the Metadata block declares this RDR a "foundational — cross-RDR producer" consumed by RDRs 0003, 0004, 0006, 0007, 0008, and 0009, and I confirmed directly that 0006, 0007, 0008, 0005 are already `Status: Final` (0003 and 0004 were demoted back to Draft from Final for unrelated re-verify reasons) while this RDR itself is still `Status: Draft`.

**The specific passage.** Prerequisites: "RDR 0007 is `Final`, so the *specification* is settled — but its kernel reshape is unimplemented, and the gap is the whole atom surface, not only the constants… Phases 2 and 3 therefore sequence behind the reshape in their entirety, and the Testing Strategy assertions that cite `resolve.OpExists`/`LiteralTrue`/`LiteralFalse` are unsatisfiable until it lands." Grepping `internal/resolve/resolve.go` directly confirms: `Guard` is declared `Guard string` (line 185), `Match []Tag` (line 179), and no `Atom`, `OpExists`, `LiteralTrue`, or `LiteralFalse` symbol exists anywhere in that file.

**The symptom.** An implementer who starts Phase 2 ("Normalizer and Dump") will get partway through — outcome lifting and `RequiresOwned` derivation have fields to land in — and then hit a wall: per-atom block retention and existence-constant emission have nowhere to go until RDR 0007's kernel reshape ships as actual Go code. This means implementation of this "foundational" RDR is gated on implementation work in a *different*, already-Final RDR that has not itself been implemented — a hidden critical-path dependency that the "Prerequisites" checklist reports honestly but that a project-planning read of the RDR (Priority: High, no scheduling note beyond a checkbox) would miss. Worse: if RDR 0007's actual reshape, once written, differs even slightly from the atom shape this RDR assumes (three-valued `Block`, `OpExists`/`LiteralTrue`/`LiteralFalse` as exported constants), the ripple invalidates load-bearing decisions in 0002, 0007, 0008, and 0009 simultaneously, and per the shop's own convention ("we never amend rdrs") none of them can be quietly patched — each divergence becomes a new RDR or an `/rdr-cluster-reconcile` pass.

## 2. The one section that will be rewritten within 6 weeks of shipping

**The CLI-facing mapping of the ~25 load-time validation categories (A5, and the "Load-time validation failures MUST retain stable data-level categories before CLI mapping" Normative Contract).**

This RDR is explicit and unusually honest that this mapping does not exist yet: A5's Evidence states plainly that "No parse-validation code has yet travelled [the CLI error envelope]," that `config-invalid` "exists solely as a doc comment and a TODO," and that "This RDR's table parse and lint categories would be the **first** parse-validation codes in the envelope, so their code names, `Group` assignments, and exit mapping are new design work at implementation, not a pattern to copy." The RDR fixes ~25 category *identifiers* as an "API surface, not message text" but explicitly punts every question about how a human sees these categories — error code namespace, exit code grouping, `Hint` text, which of the granular categories collapse into a shared user-facing bucket — to RDR 0005.

Why this is the section that breaks first: 25 categories is a lot of granularity for a CLI surface that has, per A5's own accounting, exactly four error codes in the entire codebase today (`config-not-found`, `config-read-error`, `flag-invalid-value`, `command-error`). The first real author who hits `malformed accessor binding` (which the RDR notes covers at least two distinct causes — arity violation and provenance violation, deliberately merged: "A violation of the second or third bullet is a `malformed accessor binding`") is going to want a `Hint` that tells them *which* violation they hit, and the category-not-message design explicitly defers that distinction to something other than the category. Similarly, the three shapes folded into one `malformed escape declaration` category (empty write block, `clear` list, `gate` list on an escape rule) are stated to deliberately not be split further "because the shapes are one authoring error," but the first CLI author mapping categories to `Hint` strings will need per-shape messages regardless, meaning the message-generation layer re-derives distinctions the category taxonomy just spent enormous effort *not* making. This is a classic setup for "the taxonomy that was right for the loader was wrong for the human," and it will be rewritten (or wrapped in a translation layer) once RDR 0005's actual CLI mapping work happens and someone tries to fit 25 loader categories through a handful of exit-code groups without producing useless error messages.

## 3. The one assumption that will not survive first contact with a real user

**A6 / the sparse-authoring premise itself: "Shared contexts and positive/negative guard lists are sufficient to keep the RDR model sparse without hiding ambiguity."**

The RDR verifies this against two small, curated fixtures — nine RDR rows and two kata rows, hand-picked by the RDR's own authors to exercise specific clauses (inheritance depth 3, one `in`-expansion, one sibling pair, one escape rule). This is not evidence that the format stays legible at the scale it will actually need to reach. The Decision Rationale itself names the real target: "status, profile, prelock iteration, cluster eligibility, rewind scope, and guards" — six independent dimensions for the RDR flow alone, before kata's separate lifecycle model. The RDR's own premortem, quoted almost verbatim in Decision Rationale, names exactly this risk and hedges it with a spike that is far smaller than the real graph: "this could fail if the sparse source becomes a verbose pseudo-language or if expansion hides surprising implicit rows... The recommendation survives only if Resolve proves the RDR and kata examples with a parse-normalize-dump spike." The spike passed on nine rows. It says nothing about what the *actual* RDR lifecycle graph (which per this project's own kata/RDR flow has stages `propose → refine → resolve → prelock (with 5 named lenses!) → finalize → implement`, iteration caps, cluster gates, and rewind semantics on top of profile-dependent branching) looks like once every real edge is authored.

Concretely: the RDR fixture's own `continue-prelock` context chain is already three levels deep (`draft → prelock → large-prelock`) for a *slice* of the real flow. The actual prelock lens set alone has five members (`grounding, cove, 3amigo, critique, repeatability` — visible in the fixture's own `[tags.prelock_lens]` domain declaration), each of which likely needs its own guard or context in a real table. Multiply status × profile × stage × prelock-iteration-cap × cluster-eligibility × rewind-scope × prelock-lens and the "avoids Cartesian-product authoring" claim is exactly the claim that has not been tested at any scale resembling production. The first real user — someone hand-authoring the actual RDR lifecycle table, not a nine-row slice of it — will discover whether inherited contexts actually collapse this dimensionality in practice, or whether (as the premortem itself warns) the sparse source becomes "a verbose pseudo-language." Nothing in this RDR's evidence answers that question at real scale; it answers it at demonstration scale.

## 4. The premortem

*It is six weeks after RDR 0002 shipped. The transition table for the real RDR lifecycle — the actual `docs/rdr/*.md` workflow this project runs on itself, not the nine-row slice in the spike — has been hand-authored and is now in daily use driving `rdr-resolve`, `rdr-finalize`, and the prelock lens sequence.*

The first incident report comes from a contributor running `rdr-prelock` on a large RDR. The `prelock_lens` tag write during the 3amigo pass silently fails to distinguish `["3amigo", "critique"]` (two lenses queued) from `["3amigo,critique"]` (a single malformed lens name someone fat-fingered into the source TOML with a comma instead of a list). Both authored spellings normalize to the same `write` value in the promoted normalizer, inherited unmodified from the spike's `renderValue` → `strings.Join(parts, ",")` pattern (C-1) because nobody caught the write-replaces MUST clause during implementation — it is one paragraph inside a ~700-line block of Normative Contracts, and the delimiter-parameterized test the RDR specifies as the only defense (Testing Strategy scenario 2's "same control runs on the write side") was written as an afterthought late in the pre-lock cycle and, per the RDR's own account, is "owed" alongside A13's fixture at the time of lock — meaning there is no guarantee it was actually implemented rather than merely specified. RDR 0004's read-back reports the write as "applied" either way, because the held-value equality check RDR 0004 performs cannot see the difference the loader already erased. The contributor's RDR silently skips the critique lens. Nobody notices until a much later `rdr-cluster-reconcile` finds a contradiction that critique should have caught.

The second incident is quieter and more damaging. A maintainer authoring a rewind rule writes two guard atoms intending them as alternate spellings of the same constraint — one contributed directly by the rule, one inherited from a context — expecting the merge to treat them as one fact if identical and flag a contradiction if not. Per A13's own documented contradiction, the merge is keyed on a joined rendering, not full atom identity: an atom whose literal is `["a,b", "c"]` and one whose literal is `["a", "b,c"]` collapse into a single surviving atom under the spike's `Atom.identity()` (confirmed at `main.go::Atom.identity` → `literalString` → `strings.Join(a.Literal, ",")`). The rule that the maintainer believed was self-contradictory — and therefore dead, and therefore safe to leave in the table as a documented "this should never fire" guard — instead normalizes to a live, matching row. In production, an artifact reaches exactly the tag-set that satisfies the "impossible" guard, and the resolver returns a plan the reviewer never approved reaching. Because this defect "trips zero load categories" by the RDR's own analysis (A13 "If wrong"), no error is ever logged. The only trace is a git-blame-able transition-table diff that looked, to every reviewer who read it, like a defensive guard against an edge case that could never occur.

The third failure is organizational rather than functional. Implementation of Phase 2 stalls for weeks because RDR 0007's kernel reshape — Final on paper, unimplemented in `internal/resolve` — is a separate, unscheduled body of work that this RDR's Prerequisites correctly flag but that nobody outside the RDR-reading discipline notices until an engineer sits down to write the normalizer's atom-to-`Row` handoff and discovers `Row.Guard` is still a bare `string`. The team either (a) blocks RDR 0002 implementation on RDR 0007 implementation, silently doubling the critical path length nobody budgeted for, or (b) improvises a stopgap `Guard string` shape that approximates the block-keyed routing this RDR specifies, ships it, and creates exactly the kind of undocumented deviation the project's "no amendment, only new RDRs" convention exists to prevent — except now there are two implementations of the guard seam in flight and no RDR describing which one is real.

## 5. Acceptance tests that would have caught each failure at RDR-review time

**AT-1 (catches 1a / C-1): Write-value join-collision, run against the promoted evidence artifact itself, not just future code**
```
Given the promoted normalizer spike at evidence/spikes/iter-2/main.go
And its output at evidence/spikes/iter-2/output.txt
When a reviewer greps output.txt for any set-valued write field
Then no rendered write value may be ambiguous between a single-member set
  containing the delimiter and a multi-member set without it
And if `renderValue` or `literalString` is found to join a slice with a
  delimiter anywhere in the promoted spike, the file MUST NOT be labeled
  "canonical" or "normative fixture" until the join is replaced with a
  sequence-preserving representation
```
This test would have caught C-1 before it was ever quoted as the desk-trace's own confessed CONTRADICTION — the RDR already self-detected this via the desk trace, but shipped the contradicting artifact as the canonical fixture anyway rather than regenerating it clean.

This is a mechanical, automatable check — the mismatch (`identity`/`row_identity`, `source`/`source_locator`, `writes`/`write`) would have been caught by a five-line script diffing the two lists.
