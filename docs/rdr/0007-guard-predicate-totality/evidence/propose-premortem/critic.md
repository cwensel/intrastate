## 1. Prospective hindsight — the failure narrative, as accomplished fact

It shipped in Q3. The evaluator was implemented by the other team against the spec, on schedule, with a clean test run. Two incidents followed, and together they are the two horns of the same design.

**Incident one (the refusal storm).** A recognizer upgrade narrowed the recognized-tag set; the view assembler, merging owned/observed/recognized provenances, began silently omitting a tag key that a dozen transition tables' guards referenced. Per the domain rule, every value-comparing atom over that key went unevaluable; per the combination rule, every containing guard went unevaluable; per the refusal rule, the result was the non-escapable refusal — in every table, on every run. Because non-escapability was the point, no author could model a recovery row. The CLI said only that the guard was unevaluable; it could not say which key, which provenance layer dropped it, or that the state in fact existed on disk. The fleet was hard-stopped for a day by a bug in a component the spec never constrained, and the design's own safety property was what removed every recovery path. Operators learned the lesson the wrong way: "unevaluable" came to mean "the assembler is broken again," and pressure mounted to make it escapable — reopening the exact masking hole the RDR closed.

**Incident two (the quiet plan).** A table author added a broad fallback row guarded only by existence atoms — reasonable under the new doctrine, since existence is the one total operator. Months later a value tag became unreadable for a subset of artifacts. The specific high-priority row went unevaluable. The kernel — unchanged, per claim 5 — walked its selection loop, which predated three-valued verdicts and treated everything non-TRUE as non-candidate. The unevaluable row contributed nothing; the fallback row was decided true from presence alone; a plan was produced. The output was byte-for-byte indistinguishable from a healthy resolution. The honest answer was "I could not tell," and the system said "here is your plan." This is precisely the failure the problem statement names, reintroduced not by the evaluator (which conformed) but by the aggregation layer the spec never pinned down and the kernel branch nobody was forced to revisit.

## 2. Obstacle negation — each claim negated, with a domain-consistent scenario

**Negation of claim 1** — *Non-escapable unevaluable does NOT close the masking path.* The refusal rule binds a single guard's verdict to a refusal, but resolution selects one row from many. Scenario: table with row A (priority 1, guard references tag `phase`) and row B (priority 2, guard is `exists(artifact)`). View lacks `phase`. Row A: unevaluable. Row B: true. If the kernel's aggregation treats unevaluable rows as non-candidates, B is selected and a plan ships — masking achieved without any escape row, because the mask is sibling-row selection, not escape. The approach must state the aggregation rule explicitly: an unevaluable row whose priority would let it win must poison the whole resolution into the non-escapable refusal; a decided-true row may only win over unevaluable rows it would outrank anyway. The brief does not say this; "an unevaluable guard becomes a ... refusal" is ambiguous between per-guard and per-resolution.

**Negation of claim 2** — *FALSE-pruning DOES mask something.* Under strong-Kleene, F ∧ U = F. Scenario: row guard is `status = active AND regoin = us-east` (note the typo in `regoin`). The typo'd key is never present, so that atom is permanently U — but whenever `status ≠ active`, the guard decides FALSE from the present tag and the row prunes cleanly. When `status = active`, the guard goes U and refuses — but if `status = active` is rare in the rollout window, the row simply "never applies" for months. The pruning is safe for owned-state obligations only if obligations were purely post-guard; but the masked thing is the author's error itself: FALSE-domination guarantees the unevaluable atom is invisible exactly when the guard has any other reason to fail. Additionally, if any existing validation used the row's required-owned-keys to sanity-check guard inputs, claim 6's narrowing removed it, so nothing at authoring time catches `regoin` either. The defect has no runtime signal and no review-time signal.

**Negation of claim 3** — *Absence DOES contribute truth — through the door the design itself opened.* Strong-Kleene over partial value operators is sound: U propagates, ¬U = U, and truth only comes from present tags. But the design's sole total operator converts absence to a definite verdict on purpose: `¬exists(lock)` is TRUE precisely when the view lacks the key. That is correct only under claim 7. Scenario: merge precedence lets an owned-layer tombstone (or a partial observed-layer read) drop `lock` from the assembled view while the lock genuinely holds; a row guarded `¬exists(lock)` decides TRUE and the kernel emits a plan that violates the lock. No refusal of any kind fires — the failure mode the whole RDR exists to prevent, routed through the one operator exempted from partiality. Separately, if the "negative/exclusion guard list" is implemented by the later team as "excluded condition not satisfied ⇒ pass" rather than as ¬(atom) under Kleene, an absent tag vacuously passes the exclusion — a divergence only a conformance vector for "exclusion atom over absent key" would catch (see P-10).

**Negation of claim 4** — *Existence does NOT suffice; expressiveness is lost.* The common legitimate pattern is default-value semantics: "row applies when `mode` is absent OR `mode = standard`." Under Kleene with disjunction this works (`¬exists(mode) ∨ mode = standard`), but the environment implies a conjunction-of-atoms grammar with a separate exclusion list — no per-row disjunction. Then the pattern requires two cloned rows differing only in guard, with duplicated actions and obligations that drift under maintenance; or, worse, authors of the upstream writers adopt the workaround that actually happened in systems like this: stamp a sentinel (`mode=""`) on every artifact so the key is never absent. Sentinels defeat partiality wholesale — value comparisons now decide true/false against placeholder values, and "absent" ceases to mean anything. The design must either confirm the grammar admits disjunction, or explicitly bless and lint the two-row pattern, or accept that its safety property erodes at the authoring layer.

**Negation of claim 5** — *The kernel DOES need change, and the enum does not carry the contract.* Two sub-failures. (a) The selection loop: an enum with three values does not force three-way branches; any `if verdict == TRUE` / `else` in the existing kernel collapses U into prune — semantically identical to the rejected "absence = not satisfied," and invisible to every test whose fixtures have fully-populated views. (b) Refusal-kind arithmetic: the refusal set is closed at five, two escapable. Either the unevaluable refusal reuses an existing non-escapable kind — in which case the user-facing promise ("told plainly that the artifact state needed to decide was missing") is broken, because the refusal is generic — or it is a new sixth kind, in which case the "closed five-kind set" invariant and every exhaustive consumer of it breaks, which is a kernel change by definition. The claim cannot be true in both directions at once; the brief does not say which horn is intended.

**Negation of claim 6** — *Narrowing required-owned-keys DOES lose safety.* Before narrowing, the declaration was the only machine-readable statement of which keys a row's guard consumes. That declaration is what a vocabulary lint checks (`every referenced key is a declared tag key`), what a view assembler could use to know which keys it must attempt to carry, and what distinguishes "key not carried because nothing needed it" from "key needed and missing." After narrowing, guard inputs are declared nowhere; the domain rule handles runtime semantics but nothing handles authoring-time or assembly-time coverage. Scenario: P-4's typo'd key, or a key renamed in the vocabulary while three tables still reference the old name — every affected row is forever unevaluable (or forever shadowed), and the refusal cannot name the missing key as a *known* key versus a *nonexistent* one.

**Negation of claim 7** — *Absent-from-view is NOT genuine absence.* The view is merged from three provenance layers by a component outside this spec. Version skew in the recognizer (drops unrecognized keys), merge precedence (owned tombstone hides observed value), and partial read failure (observed layer times out, merge proceeds) all produce views missing keys that exist. The design's semantics are exactly right *conditional on* claim 7, and claim 7 is a property of someone else's code with no stated contract. Both failure horns follow: non-escapable refusal storms with no recovery path (P-1) when value operators hit the gap, and silent wrong plans (P-5) when the total existence operator hits it. Worse, the single-bit view interface (present/absent) makes the two indistinguishable to the evaluator forever: it cannot refuse differently for "read failed" versus "never existed."

## 3. Consumer artifacts — what would have caught each, at review time

- **P-1 / P-9 / P-11** — *User journey: "Recognizer downgrade drill."* A staged run where the view assembler is fed a recognizer that drops one known-present tag key; acceptance criterion: the refusal names the missing key and its expected provenance, and an operational (non-table) recovery path is documented. Also: a written **view-assembly contract** clause obligating the assembler to distinguish (or explicitly declare it cannot distinguish) "read failed" from "absent," reviewed alongside this RDR.
- **P-2 / P-12** — *Named kernel test: `TestResolution_UnevaluableRow_YieldsUnevaluableRefusal_NotNoMatch`.* Fixture: one row, guard over an absent key, no other rows. Asserts the refusal kind is the unevaluable kind, not the no-applicable-row kind. A second fixture with a decided-false row plus an unevaluable row asserts the same. These two tests are the only thing that stops an `else`-branch collapse from passing CI.
- **P-3** — *Named kernel test: `TestResolution_UnevaluableHigherPriorityRow_BlocksLowerTrueRow`.* Fixture: row A (priority 1) unevaluable, row B (priority 2) true. The expected outcome must be written into the spec first — this test forces the aggregation rule to exist.
- **P-4 / P-8** — *Named lint + test: `TestTableLint_GuardAtomKeysInDeclaredVocabulary`.* Every tag key referenced by any guard atom (positive and exclusion list) must resolve against the declared tag vocabulary; a misspelled key fails table load, not production resolution. This artifact is the replacement for the safety that claim 6's narrowing removed; without it, the narrowing is not safe.
- **P-5** — *Named conformance vector: `NotExists_OverDroppedButRealKey`* in the assembler test suite: assembler must never emit a view lacking a key the underlying artifact carries in any provenance layer, or must mark the view degraded so existence atoms refuse rather than decide. Plus kernel test `TestGuard_NegatedExistence_RequiresHealthyView`.
- **P-6** — *User journey: "Author writes a default-value row."* Walkthrough in the table-authoring guide: express "applies when `mode` absent or standard." If the grammar cannot express it in one row, the journey must show the blessed pattern and a lint that flags sentinel-stamping upstream. If the journey cannot be written, the expressiveness claim is false.
- **P-7** — *Named test: `TestRefusalKinds_ExhaustiveSwitch`* over the closed kind set, plus a spec table mapping the unevaluable refusal to a kind and stating the user-visible message including the missing key name. Review question forced: five kinds or six?
- **P-10** — *Deliverable: a golden conformance vector suite* shipped with the spec (every operator × present/absent × Kleene pair combinations × exclusion-list atoms × row aggregation), which the later-implemented evaluator must pass verbatim. Named file, versioned with the spec. Prose contracts across team boundaries do not survive; vectors do.

## 4. Refutation targets — the class that survives premortems on specs like this

A spec whose implementer is a different party, evaluating over a view assembled by a third party, characteristically survives premortem review with its **interior semantics** perfect and its **boundary semantics** unstated. Premortems on such specs naturally attack the logic (is Kleene right? does absence leak truth?) because the logic is what is written down; the failures that escape are the ones living in the three unwritten seams:

1. **The aggregation seam** (guard verdict → row selection): fully interior to the kernel, assumed unchanged, and the one place a three-valued verdict can be collapsed back to two without violating any written rule. Hunted here: found live (P-2, P-3). This is the highest-probability escape.
2. **The conformance seam** (spec prose → other team's evaluator): U-producing inputs are rare in development data, so the other team's evaluator can diverge on exactly the U-cases and ship green. Hunted here: no conformance vector suite is named as a deliverable (P-10). Until one exists, claim 5's "only a future evaluator must conform" is unfalsifiable.
3. **The assembly seam** (world → view): the spec defines the meaning of absence with precision while leaving the *production* of absence entirely unconstrained (P-9, P-11). The design is conditionally correct on claim 7, and claim 7 is the one claim nobody on this spec can enforce.

Everything in the ledger was re-checked against these three seams before acceptance; P-2, P-3, P-10, and P-11 are members of the escape class and are therefore the findings to weight most heavily, independent of how convincing the interior logic reads.

## Verdict rationale

The core doctrine — partial value operators, a total existence operator, strong-Kleene combination, non-escapable unevaluable refusal — survives every interior attack: absence cannot manufacture truth through value operators, and the modeled-escape masking path is genuinely closed *at the single-guard level*. What does not survive unamended: the unspecified row-aggregation rule (P-3), the assumption of an unchanged kernel (P-2, P-7), the loss of guard-input declaration without a replacement lint (P-8), the expressiveness gap for absent-or-equals (P-6), and the unconditioned trust in view assembly combined with a total ¬exists (P-5, P-9, P-11). None forces a different approach; each requires a folded mitigation. Absent those mitigations, the design will fail in production by the two-horn narrative above.
