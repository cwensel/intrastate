## 1. Three most likely failures

1. **The read-side carrier gate as specified cannot be implemented — it type-switches on a type nothing ever constructs.** A8 and C1 both assert the registry's read-construction yields `*flowbind.Reader` / `*cmdbind.Reader` (pointer types) and that the verb's type-switch admits only `*flowbind.Reader`. `internal/cli/flowbind/registry.go:48-51` constructs `Reader{Path: acc.Path}` and `cmdbind.Reader{Accessor: acc, ...}` — value types, assigned directly to `var binding accessor.Binding`. Both `Reader` types implement `Read` on value receivers (`flowbind.go:189`, `cmdbind.go:1123`), so nothing pointer-typed is ever created on the read side (contrast the write side, which does construct `&Writer{...}` at `registry.go:62`, matching A7's `*flowbind.Writer` claim correctly). A `case *flowbind.Reader:` type-switch arm, as literally specified, never matches the dynamic type actually stored in the interface. If implemented as written, every model — including the ordinary S1 fixture — refuses at the read-carrier gate, because the only reachable arm is the refusal one.
2. **A8's "If wrong" fallback does not name this failure mode**, so Stage 8 has no guardrail steering an implementer away from transcribing the pointer spelling verbatim from the RDR text. A8's evidence section explicitly defers the read-construction check ("To verify: read the registry's READ-construction branches as A7's evidence read the write loop") — the deferral is honest, but the assumption's headline claim (pointer types, mutually exclusive and exhaustive) was written before that verification ran, and the verification that did run for this pass shows the headline claim is false on the type-identity axis.
3. **Everything downstream inherits the same wrong type.** C1's carrier-scope paragraph, the mini-checks `authority` table's "Read carrier" row, the `oracle` table's row 10, the `trace` table's "carrier check" row, and S10's third row (command-backed reader behind a file-backed writer) all restate `*flowbind.Reader`/`*cmdbind.Reader`. None of these is a second, independent confirmation — they are the same unverified claim copied across five locations, so the record's redundancy creates an illusion of cross-checked consensus around a claim that was never checked against source.

## 2. Section most likely to be rewritten in 6 weeks

C1's new "The carrier gate is over BOTH capabilities" paragraph and A8, together. Once Stage 8 implementation actually writes the type-switch, the pointer/value mismatch surfaces immediately (either a compile-time exhaustiveness gap noticed by a careful implementer, or a test failure the moment S10's third row or even S1 is exercised, since the value-typed `Reader` would fall into the "refuse" default on every model). The fix is mechanical — switch on `flowbind.Reader` and `cmdbind.Reader` (values), not pointers — but it touches C1's normative text, A8's evidence, and every table cell listed above, which is a wide rewrite blast radius for what is a one-line implementation fix. Recommend fixing the pointer spelling now, before lock, rather than deferring to Stage 8 discovery.

## 3. Assumption least likely to survive first contact

A8, as currently worded. Its "mutually exclusive and exhaustive" claim about the two read-construction types is very likely correct in substance (registry.go:46-51 does show exactly two arms with no third), but the claim is bundled with the wrong Go type spelling, and a Pending assumption that ships an incorrect type in its own claim text is not in a position to be promoted to Verified without a rewrite of the claim itself, not just its evidence.

## 4. Premortem — six weeks post-launch, what broke

"We implemented `init-state` exactly per C1's type-switch. Every model refused at the read-carrier gate, including our own MVV fixtures (S1-S9), because `case *flowbind.Reader` never matched the value-typed binding the registry actually builds. CI caught it before merge, but only because the MVV steps are mandatory — a less disciplined validation pass would have shipped a verb that refuses on every input, discovered when the first real flow model tried to use it in production." This is a compile-and-immediately-fail class of defect, not a subtle one, so the actual "failure" here is schedule cost (spec rewrite + re-review) rather than a shipped incident — but it is exactly the kind of finding a second pass exists to catch before Stage 8 burns a cycle on it.

## 5. Acceptance test that would have caught this

A source-grounded spike identical in spirit to A7's, run against the READ side rather than assumed by analogy to it: `go vet`-verifiable or a one-line Go snippet asserting `reflect.TypeOf(binding)` for a constructed read Definition equals `flowbind.Reader{}`'s type, not `*flowbind.Reader`. Equivalently, before promoting A8 past Pending, the resolve step should have done what A7's did — read the actual construction lines and record the literal type spelling, receiver kind included — rather than asserting the read side "holds the same" pattern as the write side by structural analogy (initializer + N-arm switch) without checking whether the *pointer-ness* of the construction also matched. The two are not the same: the write loop builds `&Writer{}` (line 62) while the read loop builds `Reader{}` (line 48) — same file, eight lines apart, different addressability.
