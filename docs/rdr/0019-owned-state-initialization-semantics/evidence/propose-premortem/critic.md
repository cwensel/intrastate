# Premortem critique — `[initial]` as runtime bootstrap via `flow init-state`

Hostile review. Written as if the approach shipped. Every finding is stated as an accomplished production failure, then traced back to the claim that licensed it and the artifact that would have caught it at review time.

## 1. Prospective hindsight — the failure narrative, as accomplished fact

`flow init-state` shipped. The first-run wall closed for the demo model and reopened, differently, for everyone else.

The first reports came from operators whose models lint clean and whose `[initial]` blocks contain nothing exotic. `flow init-state` refused to seed, exiting with a read-back verification failure naming a key whose declared initial value was `2`. The artifact, inspected by hand, contained `2`. The accessor had read back `2`. What differed was type: the `--write` path that the read-back equality check was built for takes an argv string and coerces it through the CLI value parser before handing it to the accessor; the `init-state` path took TOML's already-typed `int64` and handed it straight through. The two rendered to different canonical wire forms — one JSON number, one JSON string, or in the datetime cases a TOML datetime versus the RFC3339 string every existing artifact carried. Claim 2 had asserted these paths converge. Nobody had run a value through both. The fix was the canonicalizer the clause said was unnecessary, and it landed as a patch release after the verb was already in three teams' bootstrap scripts.

The teams whose seeds *did* canonicalize hit P-4 next. A model declared an `[initial]` for a key whose only declared accessor was a reader — legal, because the lint guarantee is about reachability roots, not about writability, and the operator had declared the initial precisely so the reachability walk would certify the flow. `init-state` planned a write for it, reached the writer-routing helper, and found no route. Because the plan was executed key-by-key with commit-time read-back per key rather than as a single transaction, the failure landed after three of five keys had already been committed. The operator was left with a half-seeded artifact and an internal routing error, on a model the tool had certified.

They followed the documented recovery: re-run. This is where P-10 bit. Re-running seeds only absent keys. Three keys were present, so they were skipped — correctly. But a fourth team's failure had been a read-back *mismatch*, not a routing failure, and a read-back mismatch means the accessor wrote something. The key was present and wrong. The re-run skipped it, printed `skipped: 1`, and exited zero. The corrupt value survived every subsequent `init-state`, was never surfaced by any read verb (which faithfully reported what the artifact held), and was found six weeks later when a resolution took a branch nobody could explain. Claim 7's recovery argument had assumed failure leaves keys absent. The one failure the read-back check exists to catch leaves them present.

Meanwhile P-7 was accumulating quietly and at larger blast radius. `init-state` had been advertised as idempotent-on-re-run, so every consumer did the obvious thing and put it in the bootstrap path — the deploy script, the container entrypoint, the CI job that stands up a fixture environment. The verb's write predicate is "key is absent." The locked guarantee is that a cleared key reads back absent. These are the same observable. Operators who cleared a key to model a real-world reset — the exact use the clear semantics exist for — found the value back after the next deploy. The record had rejected implicit read-fallback on the grounds that "a cleared key would silently resurrect." The shipped verb resurrects cleared keys, on a schedule, under a banner of idempotence, and reports it as a successful seed. The rejection reason applies verbatim to the chosen approach; only the location moved.

Two smaller failures closed the set. First, P-9: a team whose model owned conditionally-present keys ran `init-state`, saw `seeded: 4`, ran `flow next`, and still got `unknown[].reason: absent`. Lint's guarantee covers the always-present subset; the seed set inherits exactly that scope; the operator's first-run wall was only partly the always-present keys. They filed the original bug again against the verb that was supposed to fix it. Second, P-5/P-6: the new verb was not in the CLI-contract's closed verb enumeration and its four new failure classes were not in the locked error-code taxonomy. The override was recorded citing a precedent — and when the peer record was actually opened during the incident review, the precedent had overridden a *behavioral* clause, not a closed enumeration, and said nothing about enumeration extension. The citation was to a file that existed, not to text that supported the claim. Shell completion never learned the verb; the read-back-mismatch failure exited with a code mapped, in the taxonomy, to a different condition entirely; and the scripts that had been written to branch on that code branched wrong.

None of these are exotic. Each is the negation of a claim the record asserted without verifying.

## 2. Obstacle negation — each load-bearing claim, negated

**Claim 1 — "No runtime code reads Initial; sole runtime consumption conflicts with nothing."**
Negation: the claim conflates "no *CLI verb* code references it" with "nothing consumes it." Lint's reachability walk consumes it. Any normalized-graph export, model fingerprint, or diagnostic that serializes the parsed model consumes it. Failure scenario: the reachability walk treats `[initial]` keys as roots with specific semantics (e.g. it does not require a writer for a root); `init-state` treats the same keys as write targets. A model that satisfies the first and violates the second lints clean and cannot be seeded — P-4. The two consumers now hold incompatible readings of one field, and the clause created the second without reconciling it against the first. Additionally the claim is a snapshot with no invariant behind it (P-13): nothing prohibits a future loader fallback, and the operator pain that motivated this record is exactly the pressure that produces one.

**Claim 2 — "Model-sourced initial renders to the same canonical wire form as `--write`; existing read-back equality passes."**
Negation: the two inputs enter at different stages. `--write` is argv — an untyped string that must pass through the CLI's parse/coerce stage before reaching the accessor. TOML `[initial]` is already typed by the TOML decoder: `int64`, `float64`, `bool`, `time.Time`, `[]any`, `map[string]any`. Unless the verb explicitly routes the decoded value back through the same coercion the argv path uses — which the approach does not state — the paths diverge on every type that has more than one wire spelling. Failure scenario A (P-2): read-back inequality on a correct model; seeding is impossible and the error implicates the accessor. Failure scenario B (P-3), worse because it is silent: read-back passes but the persisted form differs from what an equivalent `set-state` would persist, so seeded and manually-set artifacts are not interchangeable and downstream wire-form-sensitive matching diverges. Note this is the seeded *refuted licensing premise* class: a filter/equality decision licensed on a normalization assumption that the shipped normalizer does not honor.

**Claim 3 — "Every `[initial]` key is served by exactly one declared write accessor."**
Negation: neither half is established. (a) *Existence*: lint certifies that `[initial]` establishes every always-present owned key for reachability. Reachability is a read-side property. Nothing quoted requires that an `[initial]` key have a declared *writer*. A key that is observed/derived, or whose accessor set is read-only by design, is a legal reachability root with zero write routes. (b) *Uniqueness*: "exactly one" is asserted, not cited. If two accessors can write a key (different transports, different scopes), routing is ambiguous. Failure scenario: mid-plan routing failure on a lint-certified model, after partial commit — compounding into P-10's unrecoverable state. The verb must either (i) cite the lint clause that makes writer-existence-and-uniqueness a certification requirement, (ii) add that requirement to lint so the failure is caught at lint time rather than at seed time, or (iii) plan-and-validate the *entire* write set before committing any key, so an unroutable key aborts with zero writes.

**Claim 4 — "Extending the closed verb enumeration is recordable as an override, per existing precedent."**
Negation: the precedent is cited by existence, not by text. A closed enumeration and a behavioral clause are different lock kinds; an override precedent for one does not license the other. Closed enumerations are typically locked because consumers depend on closure — verb-admission rejection, completion generation, help/doc generation, error-taxonomy mapping. Failure scenario: the override is recorded, the verb ships, and the enumeration's *consumers* (which the override did not update) reject or ignore it. This is the seeded *borrowed authority* defect exactly: the record must quote the peer clause's own extension provision, or obtain an amendment to the peer record, not point at an unrelated override.

**Claim 5 — "Absent-only seeding on explicit invocation is safe under 'a cleared key reads back absent'."**
Negation: the locked guarantee constrains *readers*; `init-state` is a writer, and its write predicate is literally the observable a clear produces. The verb is definitionally unable to distinguish "never seeded" from "cleared." The "explicit invocation" mitigation is dissolved by the verb's own advertised idempotence, which invites unconditional automation. Failure scenario: cleared key resurrects on the next deploy, reported as a successful seed. The record rejected implicit read-fallback for causing precisely this; the chosen approach causes it too, just later and with a success message attached. The approach needs either a distinguishable tombstone (cleared ≠ never-set at the artifact level), or a refusal to seed a key that has ever been written, or an explicit written acknowledgement that clear-then-init resurrects and that the rejection reason for the read-fallback alternative does not, therefore, distinguish the two.

**Claim 6 — "Lint's always-present check guarantees the seed set is complete for the always-present subset."**
Negation: the claim is true and insufficient — it guarantees completeness over a subset while the problem statement's outcome is stated over "every candidate." Failure scenario: `init-state` succeeds, `flow next` still reports `unknown[].reason: absent` for conditionally-owned keys, and the operator's first-run wall is unmoved for the models that have any conditional structure. The clause must state what happens to conditional keys: are they in `[initial]` at all, are they out of scope, and does the verb's success report distinguish "all owned keys seeded" from "all always-present owned keys seeded"? A success message that does not disclose its own scope is the failure.

**Claim 7 — "Multi-writer partial failure is recoverable because re-running seeds exactly the missing keys."**
Negation: recovery assumes the failure leaves each key either verified-written or absent. Read-back mismatch — the failure class the verification exists to detect — leaves the key **present and wrong**. The absent-only filter then skips it forever, and reports it under `skipped`, the same label used for legitimately pre-existing keys. Failure scenario: re-run reports success, corruption persists, no reader ever flags it. The approach needs read-back mismatch to either roll the key back to absent (if the accessor supports it), or be reported as a distinct terminal class that re-running does *not* clear, with the key named and the operator told that `init-state` cannot repair it.

## 3. Consumer artifacts — what would have caught each at review time

Named, runnable, consumer-facing. Not opinions.

- **P-1 / P-13 — `TestInitialFieldConsumers_Enumerated`**: a test that enumerates every code path reading the parsed model's Initial field and asserts the set equals `{lint reachability walk, init-state planner}`. Fails when a third consumer appears. Paired with **`TestNoLoadPathSynthesizesInitial`**: load an artifact absent a key whose model declares an initial, assert `read-state` reports absent — pinning the "no fallback" property as a checkable invariant rather than a snapshot.

- **P-2 / P-3 — `TestSeedAndSetStateProduceIdenticalArtifactBytes`**, table-driven over every TOML scalar and container type an `[initial]` may hold (int, float, bool, string, offset datetime, local date, array, inline table): for each, (i) `flow init-state` into a fresh artifact, (ii) `flow set-state --write` the equivalent value into a second fresh artifact, (iii) assert the two artifacts are byte-identical. This catches the hard failure (P-2) and the silent divergence (P-3) in one assertion, and it fails today if the coercion stages differ.

- **P-4 — `TestInitStateOnLintCertifiedModelWithNoWriterForInitialKey`**: fixture model that lints clean and declares an `[initial]` for a key with no declared write accessor. The test forces the decision: either lint must reject the model (then the test asserts the lint finding), or `init-state` must abort with zero writes committed (then the test asserts the artifact is unchanged). Sibling: **`TestInitStateAbortsBeforeAnyCommitWhenPlanUnroutable`** — assert atomicity of *planning*, which is achievable even though cross-writer commit atomicity is not.

- **P-5 / P-6 — `TestVerbEnumerationClosureIncludesInitState`**: assert `init-state` is present in whatever structure enforces the closed enumeration, and that completion/help output lists it. Plus **`TestInitStateErrorCodesAreInTaxonomy`**: drive each of the four new failure classes and assert every emitted code is a member of the locked taxonomy with the correct semantic. Review artifact, not a test: **a quoted excerpt of the peer record's extension provision** pasted into the record — the seed defect is citation-by-existence, and the cure is citation-by-text.

- **P-7 / P-8 — user journey `journey/clear-then-bootstrap.md`**, executed as an integration test: operator seeds, operates, deliberately clears one key to model a reset, then the deploy pipeline runs `flow init-state` unconditionally (as the idempotence guarantee invites). Assert the cleared key is **still absent** afterward. If the approach cannot make this pass, the record must say so in the same paragraph that rejects implicit read-fallback, because the rejection reason no longer distinguishes them.

- **P-9 — `TestInitStateThenFlowNextHasNoAbsentUnknowns`** over a fixture model with *conditionally* owned keys: run `init-state`, then `flow next`, assert zero `unknown[].reason: absent`. If it cannot pass, the companion **`TestInitStateReportDisclosesUnseededOwnedKeys`** asserts the success report names the owned keys it did not seed and why — so the operator's next step is visible instead of guessed.

- **P-10 — `TestReRunAfterReadBackMismatchDoesNotSilentlySkip`**: inject an accessor whose read-back returns a value differing from the write, run `init-state` (fails), re-run, and assert the second run does **not** exit zero with the key under `skipped`. Assert instead a distinct terminal class naming the key as present-and-unverified.

- **P-11 — `TestInitStateOnDecisionTableModel`** asserting the exact exit code and message, plus **`journey/batch-bootstrap-mixed-classes.md`**: a directory of state-machine and decision-table models bootstrapped in one loop, asserting the documented aggregate behavior (abort vs skip). Forces the refusal *placement* decision the clause left open.

- **P-12 — a payload-shape contract test** pinning `init-state`'s report schema (`seeded[]`, `skipped[]`, and the P-10 unverified class) against `set-state`'s request-echo schema, so the grammar cost the alternative was rejected for is at least paid explicitly and once.

## 4. Refutation targets — the three seeded defect classes, located in *this* approach

**Borrowed authority — Claim 4 (P-5), and it is the same defect verbatim.** The record breaks a locked closed enumeration and rests that break on "an existing precedent where a later record overrode a locked clause of an earlier one." That sentence names a shape, not a text. The seeded defect was "a citation to a file that existed, not to text that supported the claim" — and this citation does not even name the file. Two distinct gaps must close before this claim carries weight: (i) the precedent must be quoted, and the quote must show the peer's lock admits extension of an *enumeration* (a lock whose whole content is closure) and not merely of a behavioral clause; (ii) the enumeration's downstream consumers — verb admission, completion, help, error-taxonomy mapping — must be enumerated and shown to pick up the new member, since a "closed" enumeration is usually locked *because* of them. Secondary borrowed authority in the same claim: the error-code taxonomy is a separate locked record (P-6) that the clause never mentions, while introducing at least four new failure classes.

**Unverified / refuted licensing premise — Claim 2 (P-2, P-3), and secondarily Claims 5 and 7.** Claim 2 is structurally identical to the seeded normalizer defect: a decision (reuse the existing read-back equality check; add no canonicalizer) is *licensed* on a normalization property ("renders to the same canonical wire form") that the shipped pipeline may not honor, because the two inputs enter at different stages — argv-string-then-coerce versus TOML-decoded-typed. Just as the shipped normalizer emitted two atoms where the record assumed one, the shipped value pipeline plausibly emits two wire forms where the record assumes one. The exact inversion the seed warns about is present: the read-back check exists to guarantee writes land as intended, and under this premise it *blocks* correct seeds (P-2) or *passes* divergent ones (P-3) — failing in the direction the mechanism was built to prevent. Claim 5 carries a second unverified premise: that "explicit invocation" is a durable property, when advertised idempotence makes automated invocation the expected usage. Claim 7 carries a third: that failure leaves keys absent, when the flagship failure class leaves them present and wrong.

**Missing veto clause — Claim 3 (P-4) and Claim 6 (P-9).** The seeded defect was a classification made without citing the locked clause that turned that class into a veto, leaving a partition unreachable in shipped control flow. Here, Claim 3 classifies every `[initial]` key as writable-through-exactly-one-accessor without citing any locked lint clause that makes writer-existence — let alone writer-uniqueness — a certification requirement. If no such clause exists, the class "lint-certified model with an unroutable `[initial]` key" is non-empty, and the verb's happy path assumes it is empty. Claim 6 is the same shape in the other direction: it cites a lint guarantee scoped to always-present keys and then relies on it for an outcome stated over all keys, leaving the conditional partition unhandled and undisclosed. In both cases the fix is the same as the seed's: quote the locked clause that actually governs the class, or add the clause, or handle the partition explicitly.

**One cross-cutting observation.** The record rejects implicit read-fallback because "a cleared key would silently resurrect," and rejects `--from-initial` because two write-plan sources muddy the payload grammar. The chosen approach resurrects cleared keys (P-7) and introduces a divergent payload grammar (P-12). Both rejection reasons apply to it. That does not make the alternatives better — it means the comparison that selected this approach did not price the chosen option on the same axes it priced the rejected ones, and the record should either re-price all four on both axes or state why the axes bind differently here.
