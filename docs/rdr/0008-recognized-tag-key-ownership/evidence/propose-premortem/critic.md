## 1. Failure narrative (prospective hindsight)

We shipped it in September. The normalizer landed with the reserved-key rule exactly as specified: recognized-provenance declarations must be named `recognized`, owned/observed declarations must not be, violations refused at load in the new "reserved tag key" category. The kernel was untouched, as promised. The conformance test asserted that the normalizer's literal matched the string in the design record. Demos were clean; the original bug — author names the recognizer tag `outcome_result`, row never fires — was now caught at lint with a refusal. We called the problem closed.

The first incident came from a team migrating tables written before the reservation existed. Their tables used an observed tag named `recognized` — a boolean flag from an upstream enrichment feed meaning "this entity was recognized by the fraud service," nothing to do with our recognizer. The upgrade refused their whole table set at load. The refusal said `reserved tag key: recognized`. It did not say what the reservation was for, what provenance the name demanded, or what to rename. Their batch pipeline was down for a day while they guessed. They renamed the declaration to `fraud_recognized` and the tables loaded.

But renaming the declaration did not rename the data. The upstream feed kept emitting observed tags under the key `recognized`, and observed tags arrive at resolve time as data — no declaration, no lint, no normalizer in the path. The kernel did exactly what its locked contract says: on key collision, owned > observed > recognized. The observed feed value seized the reserved key in the assembled evaluation view. Every row in every table that matched on `recognized` — rows that had passed the new validation, rows the design record held up as the fixed case — now matched against the fraud service's stale boolean instead of the recognizer's outcome. No refusal, no warning, no log line. It was not a no-match; rows fired, transitions happened, on the wrong values.

It was noticed three weeks later by an audit reconciling transition history against recognizer logs: state machines had advanced through outcomes the recognizer never produced. The postmortem's finding was one sentence: we wrote a design record declaring that the kernel owns the identity of the key `recognized`, on top of a locked kernel whose precedence rule hands that key to anyone else who uses it, and we validated only the one input surface (declarations) that was never the dangerous one (data).

A second, quieter failure surfaced in the same quarter: a kernel-side refactor changed the internal spelling constant during an unrelated cleanup. The cross-package conformance test compared the normalizer's literal to the design record's literal — doc against doc — and stayed green. Every recognized-tag row in the fleet went dark simultaneously. Discovery took four days because "row doesn't fire" was, by then, a symptom everyone had learned to blame on their own tables.

## 2. Obstacle negation — the seven claims

### Negation of Claim 1 — the tag path is not secondary; it is the only path for anything compound

The first-class Outcome field gates on one outcome. The moment an author needs the outcome inside a guard predicate combined with other tags ("outcome is X AND retry_count < 3"), or needs outcomes from two recognizer contexts, or needs the previous step's outcome in a multi-step flow, the tag path is the only mechanism — and the reservation makes it a singleton. One fixed key can carry exactly one outcome with unspecified freshness semantics (this resolve? the last one? which recognizer?). **Scenario:** an author writes a guard over two recognizers' outcomes; the second outcome has no key it is permitted to occupy, because the only recognized-provenance name is taken and owned/observed names are forbidden from carrying recognizer meaning by construction. The design must answer: what is the declared semantics of the singleton, and what is the story when there is more than one outcome in scope?

### Negation of Claim 2 — lint catches the wrong-name case, not the wrong-provenance case

The validation fires only when the author declares provenance `recognized` under the wrong name. The problem statement's author did not know provenance mattered — that is the whole discovery problem. That author declares an observed tag named `result` (or `outcome`, or anything) intending to match the recognizer's output. Every check passes: provenance is observed, name is not reserved. The row never fires. The silent no-match the design exists to eliminate survives intact, now behind a passing lint that actively tells the author the table is well-formed. Intent is invisible to a name-and-provenance check. **Scenario:** as above; additionally, any path that hands normalized tables to the kernel without passing through the normalizer's lint (test fixtures, other producers, older normalizer versions) sees no validation at all.

### Negation of Claim 3 — "extensible list" is true of the text and false of the consumers

The wording permits a new category; the ecosystem around categories does not automatically. Refusal renderers, exit-code mappings, remediation documentation, and tests that assert the category set will route an unknown category to a generic bucket. The one thing this category exists to communicate — "the name is fixed, here is the fixed name, here is who owns it" — is exactly what a generic bucket strips. **Scenario:** author hits the new refusal through a CLI whose error table predates the category and reads "table validation failed (unrecognized category)". The original complaint — nothing tells them the two names had to agree or which wins — recurs one layer up.

### Negation of Claim 4 — a normative literal in prose plus a doc-vs-doc test is not a drift guard

With no exported constant, the "cross-package conformance test" can only be one of two things. If it compares the normalizer's hardcoded literal to a hardcoded expectation, it verifies the doc against itself; the kernel's internal spelling is not in the loop and can drift (refactor, case change, normalization) with all tests green. If it instead runs the kernel and inspects the assembled view, it is an end-to-end behavioral test — which the claim does not require anyone to write, and which is the only version that works. **Scenario:** kernel cleanup renames an internal constant's value; conformance test green; fleet-wide silent no-match on every recognized-tag row. The design must either mandate the end-to-end form by name or concede the exported constant.

### Negation of Claim 5 — validated tables are not the only input, and precedence contradicts the ownership story

Two independent breaks. First, the kernel consumes normalized tables and resolve-time tag data from any producer; "a table that passes validation" bounds only one input surface. Observed and owned tags arrive as data at resolve time with arbitrary keys — no declaration, no lint. Second, and worse: the precedence order resolves the collision against the declared owner. The design's thesis is "the carrier owns the key's identity"; the carrier's own locked rule says owned and observed values seize that key on contact. The "deterministic backstop" is deterministic in the wrong direction — it converts non-conforming input into a silent wrong-value match rather than a refusal, which is strictly worse than the no-match that motivated the RDR. **Scenario:** the P-1 narrative — an observed feed emitting key `recognized` shadows every recognizer outcome in the view, forever, silently. The design must state what stands between resolve-time data and the reserved key, given that the kernel cannot change.

### Negation of Claim 6 — "only surface" is asserted, not demonstrated

The claim holds only if match patterns and guard predicates provably read the identical assembled view, and no other surface (trace/explain output, refusal payloads, write-effect targets, any future interpolation) exposes tag keys with different assembly. Guards are the classic divergence point: a guard evaluator wired to the raw tag store pre-injection sees no `recognized` key while the pattern matcher on the same row sees it. **Scenario:** row whose pattern matches `recognized = accepted` and whose guard tests `recognized != stale` behaves as if the guard read a different world; author files a bug against their own table. Separately: can a row's write-effect target the reserved key? The provenance rule forbids declaring an owned tag named `recognized`, which should close it — but only if write targets are checked against the same declaration rule, which the brief does not state.

### Negation of Claim 7 — the declaration conforms, but the declaration space now has a structural collision

Forcing all recognized-provenance declarations to one name means any table with two of them (two recognizer contexts, staged flows, or plain copy-paste composition of table fragments) declares `recognized` twice. Is that a duplicate-tag refusal, a legal merge, or undefined? The brief is silent, and whichever category the duplicate lands in, it will not be the reserved-key category, so the author gets an error that never mentions the actual constraint. There is also a namespace-convention cost: shops that prefix every tag (`app_*`) now have exactly one tag that cannot follow the house convention, which every table linter and style checker they own must special-case. **Scenario:** merged table fragments each declaring `recognized`; load refuses with a duplicate-key error from an unrelated category; author deletes one declaration and silently changes which rows were intended to gate on the outcome.

## 3. Consumer artifacts — what would have caught each scenario at review

- **P-1 / P-6 — `TestResolve_ObservedDataKeyRecognized_ShadowsInjection`** (kernel-consumer integration test): feed the kernel a fully validated table plus resolve-time observed data under key `recognized`; assert what the assembled view holds and whether any diagnostic fires. Writing this test forces the review to see that the answer today is "observed wins, silently."
- **P-2 — user journey "two recognizers, one row"**: a written walkthrough of an author gating one row on two recognizer outcomes. The journey cannot be completed under the reservation as specified; drafting it surfaces the singleton-semantics gap before lock.
- **P-3 — `TestLint_ObservedTagIntendedAsOutcome_PassesButNeverMatches`**: a lint-gap fixture — observed-provenance declaration, innocent name, row matching it, recognizer producing the value — asserting lint passes and the row does not fire. Its existence forces the draft to document the residual and consider a heuristic warning (tag matched but never written by any row and never observed in sample data).
- **P-4 — `TestRefusalCategories_Exhaustive`** plus a golden-file test on the reserved-key refusal text: enumerate every consumer switch over categories; golden text must contain the offending name, the required name, and the provenance rule.
- **P-5 — `TestRecognizedKeySpelling_EndToEnd`**: run the real kernel resolve, assert the reserved key appears in the assembled view under the exact normalizer-side spelling. Named in the RDR as the mandated form of the conformance test; a doc-vs-doc literal comparison must be called out as non-conforming at review.
- **P-7 — `TestGuardAndPattern_SeeIdenticalView`**: one row whose pattern and guard both reference `recognized`; assert both observe the injected value in the same resolve.
- **P-8 — `TestLint_DuplicateRecognizedDeclarations`**: two recognized-provenance declarations in one table; assert which category refuses (or that merge is defined) and that the message cites the reservation.
- **P-9 — user journey "innocent pre-existing `recognized` tag"**: migration walkthrough for a legacy table using the name as an ordinary observed tag, including the upstream data feed that lint cannot see. Drafting it exposes that renaming the declaration does not rename the data, and that the refusal needs migration guidance.
- **P-10 — `TestLint_ReservedKeyNormalization`**: table-driven cases for `Recognized`, `"recognized"`, `recognized ` (trailing space), dotted forms; assert the validation's comparison rule is defined (exact-bytes vs normalized) and documented.
- **P-11 — golden refusal text review item**: the RDR must quote the refusal string verbatim; reviewers check it answers "which name wins" without leaving the message.
- **P-12 — `TestLint_UndeclaredMatchOnReservedName`**: match `recognized` with no declaration; assert the error mentions the reserved-key rule and the required provenance, not just "undeclared tag".

## 4. Refutation-target hunt — the defect class this decision ships anyway

No escaped-defect ledger exists, so the hunt is by class. Reserved-name/ownership decisions have a well-known survivor profile: the premortem argues about who owns the name, everyone agrees, and what ships anyway is (a) **the innocent-collision break** — real users were already using the word for something unrelated, the reservation refuses them with a message written for the guilty case, and the migration path is undefined (P-9); (b) **the boundary the validator cannot see** — reservation enforced on declarations while the same key arrives through a data channel no lint touches, so enforcement covers the surface where the mistake was annoying and misses the surface where it is silent (P-1, the narrative's core); (c) **near-spelling escape** — reservation compared as one exact literal while the input format admits case, quoting, and whitespace variants that humans read as the same word (P-10); and (d) **the refusal that names the rule but not the resolution** — the new error category exists, fires correctly, and still fails to tell the author which name was supposed to win, reproducing the original UX defect inside the fix for it (P-11, P-4).

Hunting that class in this brief: (a) is live — the brief has no migration story and the reservation lands on a common English word; (b) is live and is the strongest finding — the precedence backstop actively resolves the unseen-boundary collision against the declared owner; (c) is live — the brief says "named exactly `recognized`" without defining the comparison against TOML's key forms; (d) is live — the category is specified, the message content is not, and the problem statement's own complaint was about message content. All four members of the survivor class are present and none is answered by the approach as written; all four are answerable inside it.

## Verdict rationale

Every failure found is survivable within the chosen approach: none requires abandoning the reserved-keyword design, but P-1/P-6 (resolve-time data shadowing under an ownership story the precedence rule contradicts) must be answered in the draft — most plausibly by mandating reserved-key sanitization or refusal at the boundary that assembles resolve-time observed/owned input, outside the locked kernel — and the class-(a)–(d) mitigations must be folded in as normative text and named tests.
