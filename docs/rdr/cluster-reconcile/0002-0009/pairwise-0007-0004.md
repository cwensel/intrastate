## Test of 0007's cited reasoning about RDR 0004

The prompt asked three questions. Answering them first, because two findings
fall directly out of the answers.

**(1) Do RDR 0004's `indeterminate` and RDR 0007's `GuardUnevaluable` refer to
the same thing, collapse, or conflict?** Neither the same thing nor in
conflict — they are *disjoint*, and 0007 says so correctly. RDR 0007's A8
Evidence is careful: "The seams are distinct and this one is not pre-empted:
0004's gate accessor *reports* indeterminate as an execution outcome, whereas
this RDR *derives* unevaluability from an absent key in the assembled view —
0004 states no absent-key rule." That reading is confirmed by RDR 0005, which
normatively forbids the one route by which the two could ever meet: `flow next`
"MUST NOT invoke gate accessors or coerce gate allow, deny, or indeterminate
results into tag values." Because an indeterminate gate result can never become
a tag in the assembled view, it can never be an operand a guard atom is
unevaluable over. **A8 survives the test.** 0007 borrows RDR 0004's *no-collapse
principle* — an undecided third value must be a refusal class, not folded into a
boolean — as a house-rule precedent, and it explicitly disclaims borrowing
0004's *rule*. That is legitimate use of a sibling and is recorded here as a
non-finding, deliberately, since the prompt raised it as a candidate conflict.

**Is there an unstated mapping between the two?** No, and none is needed —
but the *absence* of a mapping is itself unstated on 0004's side, which matters
for Finding 3. RDR 0004's gate accessor is one of exactly three capabilities its
own contract closes over: "Every accessor definition MUST declare exactly one
capability: read, gate, or write." Nothing in RDR 0004 says what a caller does
with an `indeterminate` at the resolver seam; it hands the classification to the
CLI ("RDR 0005 later maps those results to the user-facing CLI"). RDR 0007 never
claims otherwise. So the two third values coexist without a mapping and without
needing one — but also without either RDR stating that they are unrelated, which
means an implementer building 0004's executor while reading 0007's A8 citation
of it has no text on 0004's side confirming the seams are distinct.

**(2) Is the thing A6b needs actually absent from RDR 0004, and does RDR 0004
acknowledge the obligation anywhere?** The thing is absent, and the obligation is
unacknowledged. Verified two ways. First, 0007's characterization of the governing
clause is exactly right: RDR 0004's entire read-accessor normative surface is the
two sentences "A read accessor MUST return typed tag values or a typed refusal.
It MUST NOT mutate authoritative artifacts." There is no third sentence, and no
other normative block in RDR 0004 mentions reads except the write-path read-back
clause. Second, 0007's claim that 0004's failure taxonomy has no read-side
partial-failure member is confirmed verbatim against 0004's Failure Modes:
"unknown accessor, capability mismatch, artifact unavailable, timeout, execution
failure, gate denied, gate indeterminate, write attempted for a non-owned tag,
and read-back mismatch" — nine classes, every one of which is either a
whole-invocation failure or a write-path failure. A partially-read artifact takes
none of them. And 0004's own definition of silent failure is scoped exactly as
0007 says: "Silent failure would mean a write command reported success but the
owned tag did not change as expected" — write path only.

**So 0007 is unilaterally assigning work to a locked sibling that does not know
about it.** That is Finding 1. Note the asymmetry with the honest half of 0007's
own record: 0007's Prerequisites checkbox for this obligation is marked `[x]`
("Read-completeness obligation routed for A6b"), i.e. *discharged from 0007's
side*, while the work itself sits undone and unrecorded on 0004's side. 0007
concedes the mechanism ("RDR 0004 is Final and is not amended; the obligation
lands on its implement stage, not on its text") but does not concede that an
obligation landing on a stage no document mentions is an obligation binding
nobody — the same structural defect this cluster already recorded in
`pairwise-0009-0004.md` Finding 1, and the second instance of it against the
same locked peer.

**(3) Does RDR 0004's read-accessor clause / error channel support the
read-failed vs genuinely-absent distinction?** No. The clause is a bare
disjunction with no completeness requirement on the values branch, exactly as
0007 states. Worse, RDR 0004's *Technical Design* actively works against the
distinction being recoverable later: each accessor definition declares "expected
tag keys", which is the one piece of data from which a partial read could be
detected — and no normative clause anywhere in RDR 0004 requires the executor to
compare the returned tag set against the declared expected keys. Validation uses
the field structurally ("Validation records capability, artifact role, and tag
keys"), never as a runtime completeness oracle. The discriminator 0007 needs
therefore *exists as declared data in RDR 0004* and is left unused — which
raises this from "unstated" to "unstated despite the input being present." That
sharpens Finding 1's severity and is the reason Finding 3 is a round-trip
finding rather than a duplicate of it.

## FINDING 1

TYPE: gap

A-QUOTE: "**Read-completeness obligation routed for A6b** —
      destination named at Stage 6: **RDR 0004's implement
      stage**, which owns the accessor executor and is where
      the read-accessor contract (\"typed tag values or a
      typed refusal\") is realized in code. That stage must
      state whether the \"typed tag values\" branch carries a
      completeness guarantee — i.e. whether a partially-read
      artifact MUST take the refusal branch — since a
      truncated snapshot and a genuine absence are currently
      byte-identical at the kernel boundary (`Input.Owned`
      has no error channel). RDR 0004 is Final and is not
      amended; the obligation lands on its implement stage,
      not on its text."

B-QUOTE: silent

EXPLANATION: RDR 0007 files a normative obligation on RDR 0004's implement stage
and marks it `[x]` discharged in its own Prerequisites, while RDR 0004 — Final,
unimplemented, and the only document its implementer will read — mentions RDR
0007, completeness, absence, or partial reads exactly zero times across its
Normative Contracts, Prerequisites, Capability Dependencies, MVV, Testing
Strategy, and References, so the obligation binds nobody and will not be
discovered at the stage it was routed to.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: RDR 0004's Phase 2 ("Executor Boundary") and its MVV scenario 2. 0004's
implementer builds the read path from 0004's own Testing Strategy, whose only
read scenario is "Invoke read and gate accessors that succeed, time out, return
an execution failure, or return gate indeterminate" with the expectation
"Successful reads return typed tag values" — no partial-read case, no
completeness assertion, no fixture. Absent a clause, the natural implementation
returns whatever keys parsed and reports success, which is precisely the branch
0007 needs closed. It simultaneously blocks 0007 from ever closing A6b: A6b is
the only assumption in RDR 0007 carried non-Verified to lock, and its stated
resolution path terminates in a document that does not know it exists. Concretely
it blocks trusting *negative existence atoms* in production — 0007's own
Scenario 6 blesses `exists = false` over an absent key as deciding TRUE, and a
truncated read makes that atom decide TRUE against state that exists, producing a
plan rather than a refusal (0007's own P-5/P-9 failure mode). The test this
prevents: no fixture on either side can assert "a read accessor that parsed 3 of
5 declared expected tag keys MUST take the refusal branch," because neither RDR
states which branch it takes.

## FINDING 2

TYPE: contradiction

A-QUOTE: "RDR 0004's named
    failure taxonomy (\"artifact unavailable, timeout,
    execution failure, gate denied, gate indeterminate,
    write attempted for a non-owned tag, and read-back
    mismatch\") covers whole-artifact failure but not a
    corrupt or partially-parsed artifact where some tags
    read and others did not"

B-QUOTE: "Each definition declares a stable name, capability, artifact
role, expected tag keys, timeout policy, and whether read-back verification is
required."

EXPLANATION: RDR 0007 diagnoses the read-completeness gap as a *taxonomy* gap —
a missing refusal class — when RDR 0004 already carries the discriminator as
declared model data ("expected tag keys") and simply never obligates the executor
to compare a read's returned key set against it, so the two RDRs disagree about
what is actually missing: 0007 asks for a new failure class that must be invented,
while 0004's contract needs only a comparison clause over a field it already
mandates.

SEVERITY: risks-impl

OWNERSHIP: joint

BLOCKS: The design decision for how A6b is discharged, and therefore the shape of
0004's Phase 1 validation. An implementer reading 0007's framing will conclude
the fix requires a new refusal class threaded through `clierr` (0004's A3
territory, which explicitly enumerates the classes it verified as mappable and
does not include this one); an implementer reading 0004 alone has the data to
enforce completeness but no instruction to. The two paths produce different
contracts — a new refusal class versus reusing `artifact unavailable` or
`execution failure` for a partial read — and nothing decides between them. It
also blocks 0007's own Testing Strategy "Out of scope here" note, which asserts
"Testing it requires the accessor contract A6b leaves open": that is true of the
kernel seam but not of the accessor seam, where a test is writable today against
declared expected tag keys — so 0007 records as untestable something that is
testable one layer over, and neither RDR schedules the test.

NOTE ON WHY THIS IS A CONTRADICTION AND NOT A GAP: the two documents make
incompatible claims about the *same* surface. 0007 says of RDR 0004's read clause
"This is a disjunction with **no completeness requirement** on the 'typed tag
values' branch: nothing says the returned values are the complete tag set" —
true of the normative block in isolation, and false of RDR 0004 read whole, where
the definition schema fixes an expected tag key set per accessor and validation
"records … tag keys". 0007's negative is over-broad: what RDR 0004 lacks is the
*runtime comparison*, not the *specification of completeness*. A6b's evidence is
therefore verified against a subset of RDR 0004 rather than against RDR 0004.

## FINDING 3

TYPE: round-trip

A-QUOTE: "Because `Input.Owned []Tag` carries no error
    channel, a truncated snapshot and a genuinely-absent
    tag are byte-identical at the kernel boundary — so
    A6a's faithfulness is faithfulness *to the tuple*, and
    does not rescue A6b."

B-QUOTE: "`write -> read = expected owned-tag value identity + protected non-owned tag
identity`: after a write accessor reports command-level success, reading the
same caller-supplied artifact role named by the write binding must return the
expected owned-tag values, and any observed or recognized tag values present
before the write must remain unchanged. This is not an undo or byte-for-byte
artifact invariant; it is the minimum safety invariant for the authoritative tag
values and protected non-owned tag values this RDR can observe at the accessor
boundary."

EXPLANATION: RDR 0004's only round-trip invariant is existentially quantified
over the tags it expected to write and the non-owned tags it happened to observe
pre-write, never universally quantified over the artifact's key set, so a read
accessor that silently drops keys round-trips **successfully** — the write's
expected owned-tag values come back, no *observed* value changed because the
dropped key was never observed to begin with, read-back reports success — and the
same truncation that 0004's invariant certifies as safe is the one 0007 declares
undetectable at the kernel boundary, meaning the fidelity loss is invisible on
both sides of the seam simultaneously.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: RDR 0004's Phase 3 read-back comparison and the correctness of its
Failure Modes claim "the mandatory read-back check is the guard against that
case." The round trip is not idempotent in the direction that matters: `read →
(assemble, resolve) → write → read` can lose a key at step 1 and the loss is
certified clean at step 4, because step 4 re-reads through the *same* accessor
whose truncation caused the loss. RDR 0004's own Cross-Cutting Concerns claims
"Determinism: the RDR claims stable replay disposition" and A4 verifies replay
via `TestAccessorReplayDisposition` — but a *deterministically* truncating
accessor replays stably and identically, so the replay oracle cannot detect the
fidelity loss either. Concretely this prevents the one test that would close A6b
end to end: an MVV scenario asserting that a read accessor returning a proper
subset of its declared expected tag keys is a refusal rather than a success. It
is unwritable under 0004's current Testing Strategy (scenario 2 asserts only
"Successful reads return typed tag values"), and 0007 has already ruled it out of
its own scope ("Out of scope here"). Neither RDR owns the test, and each cites
the other's boundary as the reason.

NOTE ON WHY THIS IS NOT FINDING 1 RESTATED: Finding 1 is the missing *obligation*
— nobody is told to state a completeness rule. This finding holds even if the
obligation were honored on the read path in full: 0004's write-side round-trip
invariant would still certify a truncated re-read as a match, because it compares
only the expected owned-tag values and the pre-write-observed non-owned values,
both drawn from sets the truncation is free to preserve. The repairs differ:
Finding 1 wants a completeness clause on the read branch; this one wants the
round-trip invariant re-quantified (or an explicit statement that it is
plan-relative and does not certify artifact fidelity), which RDR 0004 gestures at
in the sentence "This is not an undo or byte-for-byte artifact invariant" without
naming truncation as the case it fails to cover.

## Enumeration discipline

Escalation to exhaustive enumeration was considered and declined. Findings 1 and
3 are both blocks-impl and both fixable in isolation: Finding 1's repair is to
give the obligation a home on RDR 0004's side (a Capability Dependency row naming
RDR 0007, plus one MVV scenario), and Finding 3's repair is a re-quantification
of a single stated invariant. Neither repair requires knowing the rest of the
seam, so the top-3 scope holds.

Candidates dropped as non-findings, recorded so the pass is reproducible:

- **A8 / the `indeterminate` ↔ `GuardUnevaluable` question.** Tested at length
  above and *not* a finding. The two third values are disjoint by construction,
  0007's A8 says so explicitly and accurately, and RDR 0005's "MUST NOT … coerce
  gate allow, deny, or indeterminate results into tag values" independently
  forecloses the only path by which a gate outcome could become a guard operand.
  0007 borrows the principle, not the rule, and labels the borrowing correctly.
  The residual — that RDR 0004 nowhere confirms the seams are distinct — is real
  but cosmetic, and is folded into Finding 1's note rather than counted twice.
- **Refusal-taxonomy divergence.** RDR 0004's nine accessor refusal classes sit
  entirely outside RDR 0001's closed five-kind resolver taxonomy that RDR 0007
  works to keep closed (0007 rejects a sixth kind `guard_input_missing` by name).
  This looks like a collision and is not: 0004's classes are accessor-layer
  values mapped through `clierr.ExitCodeFor`, never resolver dispositions. Both
  sides are consistent. (Same non-finding recorded in `pairwise-0009-0004.md`;
  noted here for cross-file consistency, not re-litigated.)
- **A13's characterization of RDR 0004.** 0007's A13 states "RDR 0004's only
  normative clauses touching observed tags are output-side: a write accessor
  'MUST NOT write observed or recognized tags', and read-back must find them
  unchanged." Verified exactly true against 0004's normative blocks. Not a
  finding.
