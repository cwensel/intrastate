- B-QUOTE (0005:601-614, the "Minimum stable code strings" table; accessor rows only): "| accessor cannot run because its environment is unavailable | `flow-accessor-unavailable` | `GroupEnvUnavailable` | / | accessor gate result is indeterminate | `flow-gate-indeterminate` | `GroupUserEnv` | / | write read-back does not confirm expected owned tags | `flow-write-readback-mismatch` | `GroupUserEnv` |" — and 0005:178-180 (A5): "Stable CLI error codes can distinguish bad input, unknown outcome, zero-match, multi-match, unavailable accessor, gate-indeterminate, and write-readback-mismatch failures."

- BLOCKS: 0004 MVV scenario 5 (0004:885-891, "the CLI layer can map them through `respond.Fail` and `clierr.ExitCodeFor`") and 0005 MVV scenario 5 (0005:714-717) cannot be written for the unmapped classes; the exit-group of `timeout`/`execution_failure`/`incomplete_read` is undecided (see F3).

### F2 — `read_back_incomplete` / post-mutation `timeout` collapse into `flow-write-readback-mismatch`

- TYPE: contradiction
- A-QUOTE (0004:337-342, fenced): "If it cannot read a key it must compare, the write MUST be reported as `read_back_incomplete` — the verification did not run — and MUST NOT be reported as `read_back_mismatch`, which asserts the artifact is wrong, nor as success." and 0004:344-348 (fenced): "`read_back_incomplete` and a post-mutation `timeout` are reported after the write command already ran. The refusal MUST be understood as \"the mutation may have been applied and was not verified\" — it MUST NOT be represented to callers as a write that did not occur."
- B-QUOTE (0005:614): "| write read-back does not confirm expected owned tags | `flow-write-readback-mismatch` | `GroupUserEnv` |" — the only write-side code; and 0005:479-480: "`set-state` looks successful when read-back did not prove the owned tags changed."
- EXPLANATION: 0005's single write refusal describes exactly the case 0004 forbids conflating: "does not confirm expected owned tags" covers both "read-back ran and the artifact is wrong" (`read_back_mismatch`) and "read-back could not run" (`read_back_incomplete`), and carries no applied-but-unverified sense; an implementer mapping 0004's two classes onto 0005's one row violates 0004's fenced MUST NOT, and a skill branching on `flow-write-readback-mismatch` reads a possibly-applied write as a failed one — the recovery inversion 0004's A10 exists to prevent (0004:722-729).
- SEVERITY: risks-impl
- OWNERSHIP: single-RDR (0005) — 0004's clauses landed 2026-08-21 under §D3/A9/A10; 0005's table predates them and was not re-walked.
- BLOCKS: 0004 MVV scenario 8 (0004:903-909) has no CLI code to assert; 0005 scenario 4 (0005:708-713) tests only "read-back verification proves the expected owned-tag values".
- LEDGER: NET-NEW (§D3 fixed read completeness, not the CLI carriage of the post-mutation classes).

### F3 — `flow-accessor-unavailable` (exit 3) has no producing class in 0004; `execution_failure` merges caller error with environment failure

- TYPE: gap
- A-QUOTE (0004:449): "| Artifact role not supplied | refusal | `execution_failure` | loud | `output.txt:4` |" and 0004:742-743: "An unsupplied or unreadable artifact role is **not** a separate class — it is `execution_failure`".
- B-QUOTE (0005:310-311): "External/accessor unavailability uses `GroupEnvUnavailable` when the environment, not the model, is unavailable." and 0005:612: "| accessor cannot run because its environment is unavailable | `flow-accessor-unavailable` | `GroupEnvUnavailable` |".
- EXPLANATION: 0005's only exit-3 code presupposes an "environment unavailable" refusal that 0004's disposition table (0004:440-457) never mints — 0004 folds an unreadable artifact into `execution_failure`, the same class it uses for a caller who forgot `--artifact`, so the one remedy distinction the exit integer can carry (0001:280-282: "the only remedy distinction an exit code can carry is exit 3") has no source at the accessor boundary.
- SEVERITY: risks-impl
- OWNERSHIP: joint — this is the exit-3 call §JD-8 leaves open ("an accessor that could not read the artifact is what `GroupEnvUnavailable` already means", `0001:281-282`); neither RDR alone decides whether `execution_failure` splits.
- BLOCKS: 0005 scenario 5's "read accessor unavailable" refusal (0005:714) has no accessor input class that produces it.
- LEDGER: §JD-8 (exit-3 arm) — STILL-OPEN at the home; 0005's Status carries the `§JD-8` qualifier.

### F4 — "produced by a successful transition" has no enforcer at the `set-state` boundary

- TYPE: gap
- A-QUOTE (0004:324-326, fenced): "A write accessor MUST apply only planned owned-tag writes produced by a successful transition. It MUST NOT write observed or recognized tags."
- B-QUOTE (0005:393-397, fenced): "flow set-state MUST invoke only declared write accessors over caller-supplied `role=path` artifact bindings and planned owned-tag `--write name=value` mutations. […] It MUST NOT treat context-only `--tag` values as writes." and 0005:322-323: "`flow set-state` accepts planned owned-tag mutations as `--write name=value`".
- EXPLANATION: 0005's `set-state` takes the write set from caller flags with no link to a prior `flow resolve` plan, so "produced by a successful transition" is unverifiable by 0004's executor (it sees only key/value pairs) and unasserted by 0005 — the accessor layer can only enforce the owned-provenance half (0004:233-234 "writes to non-owned tags" validation), leaving 0004's MUST held by caller discipline; 0005's own premortem names the resulting failure ("`set-state` is mistaken for an orchestration command", 0005:587) without closing it.
- SEVERITY: risks-impl
- OWNERSHIP: joint — whether `set-state` trusts the caller or requires a plan artifact is a shared boundary decision neither RDR states.
- BLOCKS: 0004 Desk Trace step 4's assertion "write applies only planned owned-tag writes from a successful transition" (0004:532) has no CLI-path test.
- LEDGER: NET-NEW.

### F5 — Read-back scope: non-owned collateral mutation is a mismatch in 0004, unnamed in 0005

- TYPE: duplication
- A-QUOTE (0004:329-334, fenced): "verify the expected owned-tag values and that observed and recognized tag values present before the write are unchanged. […] A read-back mismatch MUST be reported as a write failure." and 0004:454: "| Write succeeds, non-owned tag changed | refusal | `read_back_mismatch` |".
- B-QUOTE (0005:395-396, fenced): "It MUST report success only after the accessor layer's read-back verification confirms the expected owned-tag values." and 0005:421-423: "The equality is value-for-value over the owned tags the write planned to mutate".
- EXPLANATION: 0005 restates the read-back invariant over owned tags only, while 0004 (A7, landed since) widens it to protected non-owned tags; the two are compatible (0005 defers semantics to 0004 at 0005:424) but 0005's code description "does not confirm expected owned tags" (0005:614) under-describes the class it maps.
- SEVERITY: cosmetic
- OWNERSHIP: single-RDR (0005)
- BLOCKS: nothing; text-only drift.
- LEDGER: NET-NEW.

### F6 — Absent requested keys are omitted at the seam; 0005's `read-state` payload gives the consumer no requested-key set to detect the omission against

- TYPE: gap
- A-QUOTE (0004:293-296, fenced): "a read accessor MUST return the tag set for exactly the keys it was asked for — no requested key missing, no unrequested key added — or take the refusal branch. […] absence is a value, unreadability is a refusal." and 0004:311-315 (fenced): "what crosses the seam MUST leave the key absent from the owned snapshot".
- B-QUOTE (0005:339-340): "`read-state`: selected flow/model identity, artifact role bindings, read accessor identities, and read tags."
- EXPLANATION: under 0004 a genuinely-absent key is simply missing from the returned set, so a JSON consumer of `flow read-state` cannot distinguish "absent from the artifact" from "not a requested key" unless the payload also carries the definition's requested-key set, which 0005's minimum `data` shape omits.
- SEVERITY: cosmetic
- OWNERSHIP: single-RDR (0005)
- BLOCKS: nothing normative; a payload ergonomics gap.
- LEDGER: §D3 adjacent (the seam rule is RESOLVED; the CLI rendering of it is NET-NEW).
