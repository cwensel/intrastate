### F-1 — `<clear>` crosses to the write accessor as a value in the unreserved tag-value space

TYPE: round-trip (0002 emits, 0004 applies and re-reads)
A-QUOTE (0002:673-677, fenced): "Normalization MUST populate the next-state tags with the tag values the rule's write block and clear list produce, and the writes with the owned-tag writes the accessor layer applies — the same rendered set, including `<clear>` entries." and (0002:936-938, Round-Trip): "the `<clear>` sentinel is not reserved in the tag-value space, so an authored value of `<clear>` renders identically to a cleared tag"
B-QUOTE (0004:324-325, fenced): "A write accessor MUST apply only planned owned-tag writes produced by a successful transition." and (0004:329-332): "the executor MUST re-read the same caller-supplied artifact role named by the write binding and verify the expected owned-tag values" — `clear` / `<clear>` occur nowhere in 0004.
EXPLANATION: 0002 puts `<clear>` into the kernel's `Writes` field (the set "the accessor layer applies") while stating the sentinel is unreserved in the value space; 0004 has no clause distinguishing "remove key" from "write the string `<clear>`", and its read-back verifies expected *values* present, whereas a clear's expected outcome is the key's *absence* (which 0004's own completeness clause, 0004:296-298, makes a value on the success branch). Input class that breaks identity: any rule with a `clear` entry — an implementer of 0004 that writes the literal passes read-back (the literal is "present as expected"), which is a success-shaped result over unverified state, exactly the class 0004:748-750 says it enumerates.
SEVERITY: risks-impl
OWNERSHIP: joint (0002 owns the rendered write set; 0004 owns application and verification)
BLOCKS: 0004 MVV Scenario 3 for a clearing rule; the choice of how a clear is encoded on `resolve.Row.Writes` (sentinel vs. separate field), which is the kernel row 0001 owns.
LEDGER: NET-NEW.

### F-2 — Accessor definition metadata 0004 requires has no authorable home under 0002's strict layout

TYPE: contradiction
A-QUOTE (0002:437-440, fenced): "An `[accessors.<id>]` entry carries `mode` and `path`, as the spike fixtures author it; this RDR validates only that a referenced accessor id resolves to a declared entry (`unknown accessor` otherwise) — RDR 0004 owns the entry's semantics and execution." and (0002:465-467, fenced): "The decoder MUST reject unmapped keys so an unknown schema field is a stable refusal rather than a silent no-op."
B-QUOTE (0004:226-229): "Accessor definitions live beside the transition model as data consumed by the loader/validator. Each definition declares a stable name, capability, artifact role, expected tag keys, timeout policy, and whether read-back verification is required." and (0004:287-289, fenced): "Every read accessor definition MUST declare the requested key set as validated metadata." and (0004:359-361, fenced): "Missing or non-positive timeout metadata MUST fail validation before execution."
EXPLANATION: 0004 mandates five definition fields (capability, artifact role, requested keys, timeout, read-back flag) and validation failures for their absence; 0002 fixes the `[accessors.<id>]` entry at `mode` + `path` and strict-decodes, so a `timeout`/`role`/`keys` key authored there is an `unknown schema field` refusal. Neither says whether 0004's definition is the 0002 entry (then the layout is wrong) or a separate registry (then 0004's "beside the transition model" and its `(flow id, accessor name, capability)` identity, 0004:370-372, have no named carrier and 0002's `mode` has no stated relation to `capability`).
SEVERITY: risks-impl
OWNERSHIP: joint (0002 owns the wire layout; 0004 owns the required metadata)
BLOCKS: 0004 MVV Scenario 1 (eight validation arms) cannot be authored in a document 0002's loader accepts; 0006 A1's "accessor references … as normalized identifiers" input depends on which carrier.
LEDGER: NET-NEW.

### F-3 — Tag value shape across the read seam: 0004's "typed" has no named type source

TYPE: gap
A-QUOTE (0002:808-817, fenced): "A tag declaration also carries its **type model** — value kind, and optionally a finite domain … RDR 0003 is the normative home of that model … This RDR … requires normalization to carry every declared field through to the normalized model without loss, so lint (RDR 0006) and the guard proof (RDR 0003) read the same declaration the author wrote."
B-QUOTE (0004:282, fenced): "A read accessor MUST return typed tag values or a typed refusal." and (0004:414-416, Load-Bearing): "the artifact did not parse, the transport truncated, the key's value failed type coercion, permission was denied — is *unreadable*"
EXPLANATION: 0004 makes "failed type coercion" an `incomplete_read` trigger but never names what a value is coerced *to*; 0002 carries 0003's value kind through normalization for lint and the guard proof only, and its accessor entry carries no kind. The kernel `Tag` is a two-string pair (0004:149), so "typed" at the seam is either 0003's declared kind (then 0004 owes a citation and 0002 owes carriage to the accessor binding) or Go-typedness only (then "type coercion" is undefined). RDR 0003's conformance clause (`0003:982-993`) explicitly does not cover this: its evaluator "never reads the tag view", and the view-level check is booked as 0003 A18 with no producer at the accessor boundary.
SEVERITY: risks-impl
OWNERSHIP: joint (0003 owns kind; 0002 owns carriage; 0004 owns the coercion branch)
BLOCKS: the `incomplete_read` oracle for the type-coercion arm (0004 Scenario 2); whether a wrong-kind value is refused at the accessor or reaches `assemble` and fails `guard_unevaluable`/`uncomparable` under §D4.
LEDGER: NET-NEW (adjacent to 0003 A18, no home entry).
