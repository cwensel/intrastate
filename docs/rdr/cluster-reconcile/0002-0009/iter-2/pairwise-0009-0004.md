### F1 — `<clear>` writes reach the write accessor; 0004 has no clear semantics

TYPE: gap
A-QUOTE (0009:826-829, fenced): "(Authored clears normalize to `<clear>` writes per RDR 0002, so the Writes predicate carries both \"no writes\" and \"no clears\" at the kernel boundary.)"
A-QUOTE (0009:1663-1666, Phase 3): "one canonical authored-clear case pins the `<clear>`-sentinel-write representation identically for the kernel suite and the normalizer suite, so the two enforcers of one invariant cannot drift."
B-QUOTE: silent — the string "clear" does not occur in 0004. Nearest clauses: 0004:324-325 (fenced) "A write accessor MUST apply only planned owned-tag writes produced by a successful transition." and 0004:329-332 (fenced) "the executor MUST re-read the same caller-supplied artifact role named by the write binding and verify the expected owned-tag values".
Context (producer side, 0002:675-677, fenced): "the writes with the owned-tag writes the accessor layer applies — the same rendered set, including `<clear>` entries."
EXPLANATION: the only representation of "clear this tag" that reaches `Plan.Writes` is a `Tag{Key: k, Value: "<clear>"}` entry, and 0004 — re-locked after iteration 1 — still defines no write-accessor or read-back behavior for it; a literal-minded implementation writes the string `<clear>` as the tag value and read-back verification ("expected owned-tag values") passes green while the tag was never removed.
SEVERITY: blocks-impl
OWNERSHIP: joint (0002 emits, 0004 applies; 0009 relies on the reduction only for its kernel predicate)
BLOCKS: 0004 Phase 3 (write read-back) for any transition that clears a tag; 0004's `write -> read` invariant (0004:426-432) is not statable for a clear until the accessor knows whether "expected value" for `<clear>` means absent.
LEDGER: 0009-0004 F2 (JD-12) — see ledger trace: the home's JD-12 entry was re-purposed and never answered this.
