# Pairwise reconcile — RDR 0009 × RDR 0005

- **RDR_A**: `docs/rdr/0009-escape-row-shape-conformance-ownership.md` (Final, unimplemented)
- **RDR_B**: `docs/rdr/0005-skill-integration-cli-contract.md` (Final, unimplemented)
- **Seam**: kernel breach error → `flow` verb → `clierr.CLIError` envelope → exit code
- **Verdict**: BLOCK (2 blocks-impl, 1 risks-impl)

Scope note: 0009's claim was tested, not trusted. Two of the three sub-questions
posed in the task resolved against 0009's self-assessment; the third (programmer
error vs. user error) resolved in 0009's favour on exit code but produced a
separate group/taxonomy gap recorded as F1.

---

## F1

TYPE: contradiction

A-QUOTE: "the verb MUST wrap it into a
*clierr.CLIError carrying a stable Code, Group GroupInternal
(exit 2), the offending row identity, and a Hint stating the
remedy"

B-QUOTE: "`ExitCodeFor` maps existing groups to exit 2 for
user/model/input refusals, exit 3 for environment unavailability, and 130
for interruption."

EXPLANATION: RDR 0005 enumerates its exit-code taxonomy as exactly three
buckets and never names `GroupInternal`, and its complete Failure Modes code
table assigns every one of its twelve stable codes to `GroupUserEnv` or
`GroupEnvUnavailable` — so the group RDR 0009 routes through is one RDR 0005's
declared mapping does not contain, even though the shipped `clierr.ExitCodeFor`
does contain it.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Whether `flow`-verb conformance tests assert `GroupInternal` (0009's
requirement) or the `GroupUserEnv`/`GroupEnvUnavailable` pair that is the only
grouping 0005 declares. Because both groups exit 2, no exit-code test can
discriminate, so 0009 scenario 11's "asserted on the `Code`, never on the exit
code alone" is the only tripwire — and 0005 never authorizes the group that
tripwire asserts alongside. RDR 0005 must add `GroupInternal` to its declared
taxonomy (or 0009 must route through `GroupUserEnv`) before the `flow` verb's
error taxonomy can be implemented.

Supporting detail — testing 0009's claim rather than accepting it:
0009 A2 cites RDR 0005's Key Discovery "without requiring new exit-code groups
beyond the current `clierr.ExitCodeFor` taxonomy" as pre-authorization. That
sentence is about *not adding groups to `ExitCodeFor`*, which is true and which
0009 honours. It is not a statement that RDR 0005's own taxonomy already routes
through `GroupInternal`. RDR 0005's Technical Design sentence 0009 also cites
— "Internal parse or invariant failures use the existing internal/user-env
mapping unless Resolve finds a need for a narrower group" — names the
*mapping*, and 0005's Resolve stage then pinned (A6, Failure Modes table) a
twelve-row code table containing no internal-group row. The pre-authorization
0009 leans on was superseded by 0005's own A6 pin.

## F2

TYPE: contradiction

A-QUOTE: "The chosen carrier is
a NEW omitempty field added under the type's own \"Extend with
new optional fields as needed\" allowance — NOT the existing
Detail"

B-QUOTE: "Add stable refusal codes as needed; no new envelope fields or exit groups required."

EXPLANATION: RDR 0005's Existing Infrastructure Audit records "no new envelope
fields" as the decided Spec Impact for the failure-rendering surface it owns,
and RDR 0009 requires exactly such a new field on `clierr.CLIError` to carry
row identities to the wire.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Whether the `omitempty` row-identity field can land at all, and
therefore whether 0009 scenario 11 ("the assertion reads the identities off the
JSON output") is implementable. Also blocks 0005's Phase 4, which is scoped to
"update the CLI output contract only if the existing envelope needs an
append-only field" — a conditional 0009 silently converts into a certainty
without 0005 recording it.

Supporting detail — 0009 A9 anticipates this and argues the row is narrower
than a prohibition: "its reuse-audit \"no new envelope fields required\" row
scopes 0005's own MVP verbs and is not a prohibition." That reading is not
supported by 0005's text. The Audit row's Needed Capability is "Failure
rendering" and its Existing Surface is `internal/cli/respond::Fail` and
`internal/cli/clierr::CLIError` — the whole failure-rendering surface, not a
verb-scoped payload. The one place 0005 *does* scope append-only extension to
its own verbs is Cross-Cutting Concerns, and it scopes it to the success side
only: "verb-specific JSON `data` payloads are append-only under the existing CLI
output envelope." The sentence 0009 cites in its favour — "Error envelopes stay
append-only through `CLIError` fields" — establishes the *mechanism* by which a
field would be added, not permission for this RDR to add one. Append-only is a
compatibility property, not an authorization. Note also that `clierr.go`'s own
type comment does authorize the extension, so the *code* is permissive and only
the *RDR* is not: this is an RDR-level ownership contradiction that will not
show up as a compile or test failure, which is precisely why it must be settled
in text.

Corollary the two RDRs jointly leave unowned: RDR 0005 lists
`docs/cli-output-contract.md` first among its References and its Wire/byte
format Load-Bearing Decision binds rendering to that file. RDR 0009's
Prerequisites assign the update of that same file to 0009's implementer
("updates `docs/cli-output-contract.md`'s error-envelope field list alongside").
Two Final RDRs therefore hold write authority over one normative doc's envelope
field list with no precedence rule.

## F3

TYPE: gap

A-QUOTE: "The stable
Code is \"escape-row-shape-breach\"."

B-QUOTE: "the minimum
`flow-*` code strings in Failure Modes as this RDR's implementation contract.
The rejected alternative is leaving grammar, payload fields, or error-code
spelling to implementation-time invention."

EXPLANATION: RDR 0005's A6 pins `flow-`-prefixed spelling as the naming
contract for every stable code surfaced by a `flow` verb and explicitly rejects
codes invented outside that contract, while RDR 0009 pins an unprefixed code
that a `flow` verb must emit — and neither RDR states whether the `flow-` prefix
is a namespace rule that binds non-0005-owned failures.

SEVERITY: risks-impl

OWNERSHIP: joint

BLOCKS: The spelling assertion in 0009 scenario 11 and any code-prefix
convention test. 0005's twelve pinned codes are uniformly `flow-*`; a thirteenth
code reaching an operator from the same verb group under a different naming
scheme either breaks a namespace convention 0005 never wrote down as a rule, or
reveals that the prefix was only ever incidental. An implementer cannot tell
which, and the choice is one-way once operators branch on the string.

Note this is a genuine gap and not merely a style question, because 0005's
Failure Modes explicitly makes the code the operator's branch point
("Diagnosis starts from the error code") and 0009 makes it the *only* tripwire
for a correct wrap ("conformance MUST be asserted on the `Code`, never on the
exit code alone"). Both RDRs load-bear on the same string and neither owns its
namespace.

## Round-trip / inverse invariants across the seam

Checked against RDR 0005's `Round-Trip / Inverse Invariants` section, which
declares exactly one invariant ("`set-state` followed by `read-state` must
return the expected owned-tag values"). RDR 0009 has no such section.

**R1 — kernel `RowRef` → wire → consumer is fidelity-losing, and both RDRs are
individually correct.** RDR 0009 requires the kernel error to carry
`Ref RowRef` plus `Count int` per identity, then requires the wire carrier to be
"a clierr-local representation (plain strings or a small row-identity struct
declared in clierr) and MUST NOT be resolve.RowRef." RDR 0005 is silent on any
kernel-to-wire identity round trip. The conversion is therefore one-way by
construction and no clause on either side requires the serialized form to be
re-readable as the value the kernel produced. This is a fidelity-losing
round-trip at the seam rather than a prose error, so it is recorded as a
`contradiction` per the task's instruction — but it does **not** rise to
blocks-impl, because 0009 pins the loss deliberately (to keep `clierr` a leaf,
A9(d)) and no consumer is specified that needs the inverse. It is recorded so
that a later consumer wanting to reconstruct `[]RowRef` from JSON does not
discover the loss at implementation time.

TYPE: round-trip
A-QUOTE: "the field's type MUST be a clierr-local
representation (plain strings or a small row-identity struct
declared in clierr) and MUST NOT be resolve.RowRef"
B-QUOTE: silent
EXPLANATION: The kernel→wire identity conversion has no declared inverse and
neither RDR requires the serialized identities to round-trip back to the
`RowRef` values the kernel reported.
SEVERITY: cosmetic
OWNERSHIP: single-RDR (0009)
BLOCKS: Nothing at implementation time; blocks only a future consumer that
needs to reconstruct kernel row identities from the envelope.

**R2 — collapse+Count is deliberately non-invertible and correctly so.** 0009
collapses equal `RowRef`s to one entry carrying pre-collapse `Count`. The
original row multiset is not recoverable (three rows sharing `RowRef{"",""}`
and three rows sharing it in a different table are indistinguishable). 0009
argues this explicitly — "collapsing loses no actionable information" — and A8
records the rejected per-row-entry branch. Not a finding: the loss is the
intended semantics, the multiplicity is preserved via `Count`, and the
alternative reintroduces the REQ-2/REQ-10 ordering defect.

**R3 — 0005's declared `set-state`/`read-state` invariant is untouched by
0009.** 0009's predicate is `Writes`-only and A4 settled that `NextTags` cannot
reach owned state, so a conforming escape plan hands the write accessor an empty
work set and the value-for-value equality 0005 requires is unaffected. No
finding.

**R4 — text/JSON parity across the new field.** 0005 requires both renderings be
derived from one typed result and lists divergence as a named risk. 0009's new
identity field is specified only for the JSON path; `clierr.EmitText` renders
`Detail` and `Hint` only, so an operator in `--as=text` sees the code and hint
but not the row identities. Not raised as a separate finding because it is
subsumed by F2 — it is the same unowned envelope-extension decision, and
resolving F2 must settle the text rendering alongside.

## Sub-questions posed in the task, answered

1. **Does 0005's refusal taxonomy have a slot for an escape-row shape
   conformance failure?** Partly. The *five-kind refusal taxonomy* is RDR 0001's,
   not 0005's, and 0009 correctly never touches it — Alternative 2 is rejected
   on exactly this ground and RDR 0007's precedent is cited. So on the question
   as literally posed, 0009's claim survives. But 0005's own closed surface is
   the twelve-row `flow-*` code table plus its two-group mapping, and *that*
   surface has no slot: see F1 (group) and F3 (code spelling). 0009 conflates
   "RDR 0001's taxonomy stays closed" (true, verified) with "RDR 0005 needs no
   change" (false).

2. **Can 0005's envelope carry the failure without a new field?** No. 0009
   requires a new field and says so plainly; 0005's Audit says none is required.
   See F2. 0009's A9 attempt to scope 0005's row narrowly does not hold against
   0005's text.

3. **Is this a programmer error, and does 0005 distinguish programmer from user
   errors in a way that changes the exit code?** It is a programmer error —
   0009's grounding on RDR 0001's reserved error path is sound and independently
   verifiable in `internal/resolve/resolve.go::Resolve`. The exit code does not
   change: `clierr.ExitCodeFor` maps `GroupUserEnv` and `GroupInternal` both to
   2 (`case GroupUserEnv, GroupInternal: return 2`), so 0009's "exit 2" claim is
   correct and 0009 is right that the exit code cannot discriminate. But 0005
   never declares the programmer/user distinction at the group level at all —
   which is F1. The distinction 0009 needs exists in the shipped code and not in
   the RDR that owns it.

## Disposition

RDR 0009's headline claim — "no new refusal code, exit group, or RDR 0005
change" — is **half true and half false**, and the two halves must be separated:

- **True**: no new *exit group* (`GroupInternal` already exists and already maps
  to 2), and no new *refusal kind* (RDR 0001's five stay closed).
- **False**: "no RDR 0005 change." A2's verdict rests on treating an additive
  envelope field and an undeclared error group as non-changes to RDR 0005. Both
  land on surfaces RDR 0005 names as its own — the failure-rendering audit row
  and the pinned A6 code/group table. A9 already conceded the adjacent case
  (the `Cause` doc comment "normative home is RDR 0005") and drew the line at
  code comments; the same reasoning applied one step further reaches the audit
  row and the group table.

Recommended resolution, smallest change first: amend **RDR 0005** — add
`GroupInternal` to its declared exit-code mapping, add one row to the Failure
Modes table for the internal-breach class, and restate the Audit row's Spec
Impact as "no new exit groups; envelope fields extend append-only under
`CLIError`'s own allowance." That closes F1 and F2 without moving any decision
0009 made, and it also fixes 0005's own internal inconsistency (its Technical
Design already contemplates internal failures that its code table omits). F3
resolves alongside by stating whether `flow-` is a namespace rule.

Per project convention RDRs are not amended; the resolution above is therefore
recorded as the required content of a successor decision, not as an edit to
either file.
