### F4 — idempotent clear (0004, §D5) is unreachable from a kernel plan under 0007's `RequiresOwned` definition; neither RDR names the case that reaches it

- TYPE: gap
- A-QUOTE (0007:1613-1616, fenced): "Row.RequiresOwned names the owned tag keys the row's post-guard transition depends on — the keys its `Writes` require, which per RDR 0002 includes an authored clear (normalization renders it as a `<clear>` write)." And 0007:1633-1635 (fenced): "The owned-state scan runs over survivors, so an unevaluable row's RequiresOwned keys DO raise owned_state_unavailable".
- B-QUOTE (0004:361-362, fenced): "Clearing a key the artifact does not hold MUST succeed." And 0004:353-354 (fenced): "A write accessor MUST apply only planned owned-tag writes produced by a successful transition." Disposition row 0004:508: "Write clears a key the artifact does not hold | success | — (idempotent clear)"; MVV 0004:983-988 Scenario 9 "against an artifact that holds the key, one that does not".
- EXPLANATION: a cleared key is in `RequiresOwned` (0002:1125-1127, 0007:1615), so a row whose clear target is absent from the owned snapshot is refused `owned_state_unavailable` by the kernel and never yields a plan; since 0004's write accessor executes only from a successful plan, the "clear a key the artifact does not hold" success row is reachable only when the artifact loses the key between the accessor read and the write (or when the accessor is driven outside a resolver plan, e.g. Scenario 9's direct fixture). Neither RDR says so; 0004 presents the row as an ordinary input class. No value is lost and no clause is falsified — the two rules compose (kernel refuses first; accessor is idempotent if the world moved) — so this is a gap in stated reachability, not a contradiction.
- Fenced: both quoted clauses are fenced, but the gap is between them, and no fenced text needs to change to close it (a one-line reachability note in 0004's Disposition table or 0007's `RequiresOwned` clause would).
- Meaning change: no.
- Mechanical check: none decides the composition — 0004 Scenario 9 tests the accessor alone; 0007 row 13/15 test the kernel alone. A test driving a `<clear>` plan through the kernel against an artifact lacking the key would show `owned_state_unavailable`, not the accessor's idempotent success.
- SEVERITY: cosmetic
- OWNERSHIP: joint — the composition of §JD-3 (CLOSED: clears ∈ `RequiresOwned`) with §D5 (idempotent clear); belongs to no open JD.
- BLOCKS: nothing; a reader may expect 0004's idempotent-clear row to be exercised by an end-to-end flow and find the kernel refusing first.
