supposition is false and is recorded here so it is not re-derived.** RDR 0005 L611 already
enumerates `| guard cannot be evaluated from supplied facts | flow-guard-unevaluable | GroupUserEnv |`.

## FINDING 1 — `owned_state_unavailable` has no CLI refusal code

TYPE: gap

A-QUOTE: "Among surviving rows, absent owned state is reported BEFORE
an undecidable guard: a survivor set carrying both MUST refuse `owned_state_unavailable`. This is the shipped
ordering (`resolve.go::gate` runs `missingOwned` before the undecidable loop) and is pinned here because no test
currently contends the two within one survivor set."

B-QUOTE: silent

EXPLANATION: RDR 0007 makes `owned_state_unavailable` the *normatively preferred* refusal whenever a
survivor set carries both failures, but RDR 0005's closed twelve-row code table has no row for it —
a sweep of RDR 0005 for `owned-state|owned_state|flow-owned|state-unavailable` returns zero hits — so
the single most frequently-emitted kernel refusal under RDR 0007's own ordering rule has no user-facing
spelling, no group, and therefore no exit code.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Implementing `flow resolve`'s kernel-refusal mapping at all. RDR 0005 L278 requires it to "map
kernel refusals to stable `CLIError.Code` values", and RDR 0005 A5 claims the codes "distinguish bad
input, unknown outcome, zero-match, multi-match, unavailable accessor, gate-indeterminate, and
write-readback-mismatch failures" — a list that silently omits owned-state. Of the five kernel kinds,
RDR 0005 covers four (`flow-zero-match`, `flow-multi-match`, `flow-outcome-unknown`,
`flow-guard-unevaluable`) and drops the fifth. An implementer must either invent a code string
(exactly what RDR 0005 A6 exists to prevent: "The rejected alternative is leaving grammar, payload
fields, or error-code spelling to implementation-time invention") or wrongly collapse it into
`flow-fact-missing`, which is defined for *supplied* facts and would erase the escapable/non-escapable
distinction RDR 0007 exists to protect. Also blocks any test asserting RDR 0007's owned-before-guard
precedence through the CLI, since the two refusals are indistinguishable at the CLI boundary.

## FINDING 2 — `flow-guard-unevaluable` is scoped to *supplied facts*; RDR 0007 scopes it to the *assembled view*, provenance-blind

TYPE: contradiction

A-QUOTE: "PRESENCE IS PROVENANCE-BLIND. \"Present in the assembled
view\" means the tag key is in the view under ANY
provenance — `ProvenanceOwned`, `ProvenanceObserved`, or
`ProvenanceRecognized` (`resolve.go`). A guard atom
MUST NOT be decided differently according to how a tag
reached the view"

B-QUOTE: "| guard cannot be evaluated from supplied facts | `flow-guard-unevaluable` | `GroupUserEnv` |"

EXPLANATION: RDR 0005 defines the refusal as a property of what the *caller supplied* — and files it
under `GroupUserEnv`, exit 2, "bad input" — while RDR 0007 defines the identical condition as a property
of the *assembled view* including accessor-produced owned state the caller never supplied and cannot
supply, so the same refusal is classified as a user-input error by one RDR and an artifact-state error
by the other.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: The user-facing meaning of exit 2 for this refusal, and the operator runbook. RDR 0007 Failure
Modes is explicit that recovery is *not* an input fix — "Recovery: make the artifact state readable, or
rewrite the guard with an explicit existence atom if absence was intended" — and that operators "should
treat the refusal as 'inspect the artifact and accessor,' not 'retry'". RDR 0005's framing tells the
caller their flags were wrong. This is not cosmetic: `GroupEnvUnavailable` (exit 3) exists precisely for
"a required external facility" and is what RDR 0005 already assigns to `flow-accessor-unavailable`. A
guard unevaluable because an artifact could not be read is far closer to the exit-3 case than to
`flow-tag-invalid`. Neither RDR decides this, because RDR 0005 wrote its row believing guards read only
supplied facts, and RDR 0007 never checked RDR 0005's row. Blocks writing the exit-code test.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Deciding whether RDR 0007's diagnostic payload reaches the user, and therefore whether RDR 0007
delivers its stated user outcome at all. RDR 0007 pins the element type precisely because "the clause

it holds" — but at the CLI there is nowhere to put a `[]RowRef`. RDR 0005 A5 asserts resolver refusals

## Round-trip / inverse invariant check

Checked as instructed, treating fidelity loss as a `contradiction` even where neither prose is wrong.

**The `set-state` → `read-state` round-trip is sound and is NOT a finding.** RDR 0005's invariant —
"`set-state` followed by `read-state` must return the expected owned-tag values for the artifact role
that was written. The equality is value-for-value over the owned tags the write planned to mutate, not
byte-identical artifact content" — is correctly scoped to owned tags. RDR 0007 touches only guard
*reads*, never writes, and RDR 0007 A6a independently verifies the kernel-side view assembly is
presence-monotone: "no tag key present in the input tuple is ever dropped from the assembled view by
merge precedence or provenance override. Presence is monotone in the input; shadowing changes a value,
never a key's presence." The two are consistent. Recorded so a later pass does not re-open it.

**One genuine round-trip defect was found, and it is reported below rather than as a fourth ranked
finding only because it shares a root cause with Finding 2 (provenance blindness at the CLI seam).** It
is included because it is independently blocks-impl and the instructions require round-trip findings be
surfaced.

TYPE: round-trip

A-QUOTE: "an operator can unstick a
`guard_unevaluable` refusal by supplying the missing tag
on the command line, producing a plan whose `Writes` are
computed from caller input rather than artifact state —
the ADV-4/ADV-5 defect reintroduced one seam over, with
no test contending it."

B-QUOTE: "`flow set-state` accepts planned owned-tag mutations as
`--write name=value`; those writes are distinct from `--tag`, which remains
context already known to the caller."

EXPLANATION: The `read-state` → `resolve` → `set-state` loop is **not fidelity-preserving across
provenance**: `read-state` returns a tag-set with no provenance marking (RDR 0005's payload is
"read accessor identities, and read tags"), so a caller round-tripping those tags back in via `--tag`
silently re-enters them as `ProvenanceObserved` rather than the `ProvenanceOwned` they were read as —
and under RDR 0007's provenance-blind presence rule they then decide guards that should have refused,
producing a plan whose `Writes` derive from caller input rather than artifact state.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Whether RDR 0007's "non-escapable" guarantee means anything at the CLI. RDR 0007 concedes the
guarantee "is a weaker guarantee than it reads: it is unroutable *around within the table*, not
unbypassable by the caller", and states the exposure "becomes live at RDR 0005's CLI handoff" — RDR 0005
is the RDR that opens it and is silent on it. The kernel already refuses this substitution on the
owned-state path (`TestAdv4_ObservedTagsMustNotShadowTheOwnedSnapshot`,
`TestAdv5_ObservedTagCannotSatisfyAnOwnedStateRequirement`); the guard path has no equivalent, and RDR
0005 provides no channel to restore the distinction because it has **no concept of provenance at all** —
a sweep of RDR 0005 for `observed|provenance|Observed` returns **zero hits repo-wide in that document**,
confirming RDR 0007 A13's claim. Worse, RDR 0005 affirmatively blesses the channel: `flow next` "MUST
NOT invent guard facts that were neither supplied nor produced by a declared gate accessor" makes
supplied facts legitimate guard input by construction. RDR 0007 seeds this against RDR 0005 as an
explicit **non-blocker** — "Whether the `--tag` channel should be constrained, or guard-relevant observed
tags required to originate from a declared gate accessor, is RDR 0005's question and is seeded rather
than decided here" — but that disposition was reached against A13's bound "**Exposure is currently
unreachable**", which holds only while no CLI exists. Implementing RDR 0005 *is* the event that voids
the bound, so the deferral cannot survive into RDR 0005's implementation: the seed must be resolved
before or with it, not after.

## Assessment of RDR 0007's dependence on unspecified RDR 0005 behavior

The task asked whether RDR 0007 depends on RDR 0005 behavior RDR 0005 does not specify. **It does, and
RDR 0007 is accurate about it.** Both cited passages were located and verified verbatim:

- L935–943 (A13 Evidence) and L1889–1899 (Failure Modes) and L1963–1972 (Prerequisites) all assert
  "RDR 0005 never mentions observed tags" and characterize `--tag` as normatively unconstrained
  "context already known to the caller". **Independently confirmed**: `rg -c "observed"` against RDR 0005
  returns no hits, and RDR 0005 L323–324 carries the quoted phrase exactly.
- RDR 0007 L2025–2034 records the follow-up seed against RDR 0005 as "(not a lock blocker)".

RDR 0007's *characterization* of RDR 0005 is therefore correct and honestly recorded. The defect is not
misrepresentation — it is that RDR 0007 discharged three real cross-seam obligations onto RDR 0005 as
non-blocking seeds and named-elsewhere obligations, while RDR 0005 is Final and, per project doctrine, is
never amended. The obligations land on RDR 0005's *implement* stage with nothing in RDR 0005's own text
carrying them, which is the same unenforced-obligation pattern RDR 0007 already flags against RDR 0003
and records as "**Residual status: UNMITIGATED, not partially mitigated.** Nothing in this repo fails if
RDR 0003 never instantiates the harness." The identical residue exists here against RDR 0005 and is not
recorded in either document.
