# Pairwise contradiction scan — RDR 0008 × RDR 0009

- **RDR_A** = `docs/rdr/0008-recognized-tag-key-ownership.md` (Final, unimplemented)
- **RDR_B** = `docs/rdr/0009-escape-row-shape-conformance-ownership.md` (Final, unimplemented)
- **Shared locus**: the RDR 0001 ↔ 0002 seam; both add an entry precondition to
  `internal/resolve/resolve.go::Resolve` and both extend RDR 0002's
  validation-category surface.
- **Scan date**: 2026-08-11

Both RDRs are new foundational cross-RDR producers on the same declared seam.
0009 itself records the adjacency: "both sit at the 0001↔0002 seam, but this
decides the structural validity of a row *value* while 0008 decides the identity
of a *name*. Disjoint answer spaces, no ordering dependency." That disjointness
claim is the thing this scan tests, because 0008's block 5 widened its predicate
to read `in.Table.Rows` **after** 0009 wrote that assessment.

> - **Method**: Peer RDR

>   0009 (case-sensitive, whole file).

**B-QUOTE** (RDR 0009, Normative Contracts, the kernel-precondition block):

> The kernel enforces the same obligation as an entry
> precondition of Resolve. Resolve's signature is UNCHANGED —
> `func Resolve(in Input) (Result, error)`, one parameter — and
> the checked table is the one already reached through the input,
> `in.Table`; the precondition adds no parameter and takes no

**EXPLANATION**: 0008's A6 rests on a falsifiable, mechanically checkable
negative-existential — "the string `Input` appears **zero** times in RDR 0009

times in the current 0009 text (lines 424, 509, 736, 741, 742, 857), including

```

```

The count was true of the `Draft` 0009 that 0008 read (0008 records the
dependency qualification: "0009 is an original Draft at pre-Resolve (all seven
of its assumptions `Pending`)"). 0009 has since gained A10 — "Raised by:
repeatability (Pre-Lock), diff finding D-1 (run-1 reconstructed a two-parameter

and 0009 then locked to Final. **0008's A6 is Verified against a superseded
revision of its sibling.**

The same staleness invalidates 0008's line citations to 0009. 0008 block 4

Note carefully what is and is not falsified. 0008's *design conclusion* — that

the Final peer. An assumption one RDR makes about a sibling must be re-verified
against the sibling's locked text, and this one fails that re-verification.

**SEVERITY**: blocks-impl

**OWNERSHIP**: single-RDR (0008 must re-verify A6 and repair its 0009 citations;
0009 requires no change)

**BLOCKS**: Re-verification of A6 and A11 against Final 0009. It also blocks the

## FINDING 2

**TYPE**: gap

**A-QUOTE** (RDR 0008, Normative Contracts, block 4):

> RDR 0009 writes a structurally identical clause over the same
> entry point — "the conformance predicate MUST be exported by
> the kernel package … and Resolve's entry precondition MUST be
> that same function — one predicate, two call sites"
> (`0009…md:510-517`) — over a disjoint subject (`resolve.Row`
> shape, not `Input`). Two entry preconditions therefore land on
> one `Resolve`, and neither RDR alone can settle their order.
> This RDR binds only what it owns. […]
> Which breach a doubly-breaching caller *sees* is an ordering
> question, and `Resolve` returns a single `error`, so one of
> the two necessarily reports. That order is a cross-RDR
> decision neither RDR may take unilaterally; it is reconciled
> at Stage 7.1 (A11). Until then the implementable rule is:
> **apply this predicate at entry and report its breach; if the
> table also breaches RDR 0009's shape rule, either error is
> conforming.**

**B-QUOTE** (RDR 0009): **silent** on any peer precondition. 0009's nearest
statements assert exclusivity in the opposite direction:

> - *Precedence* — the breach error precedes every modeled
>   disposition, `unmodeled_outcome` included.

and

> - *Placement* — the call is `Resolve`'s first statement,
>   `in.Table.CheckValid()`, above the existing
>   `view := assemble(in)`, so a breaching
>   table costs no view assembly.

**EXPLANATION**: 0008 knows about the collision and writes a deliberate
interim licence for it; 0009 does not know about it at all and pins its own
check as `Resolve`'s **first statement**, so the two RDRs cannot both be
satisfied by a naive implementer without a precedence rule neither owns.

The asymmetry is what makes this a gap rather than a resolved deferral. 0008
carries the reconciliation item explicitly (A11: "report order remains a Stage
7.1 item by design"). 0009 carries **no** corresponding item — its own
"Joint-check: clear (7 peers)" and its Background's "Disjoint answer spaces, no
ordering dependency" both predate 0008's block 5 widening, which 0008 itself
flags:

> Note the ordering consequence for A11: this widens
> the `Input` predicate to read `in.Table.Rows`, so it is no
> longer decidable without reading the table, and the
> independence half of A11 must be re-checked against RDR
> 0009's row-shape precondition rather than assumed.

So 0009's "no ordering dependency" self-assessment is stale for the same reason
A6's string count is: it describes a 0008 that had not yet widened to
`in.Table.Rows`. Two Final RDRs now both mandate a whole-table entry
precondition on one `Resolve`, and only one of them says so.

The **independence** half is genuinely fine and I re-derived it rather than
trusting either RDR: 0008's predicate reads `Input.Owned`, `Input.Observed`, and
each row's `RequiresOwned`; 0009's reads each row's `Escape` and `Writes`. The
field sets are disjoint and both are pure reads, so neither can change the
other's verdict. What is missing is only the **report order**, plus one concrete
structural conflict the prose ordering question hides:

- 0009 mandates `Table.CheckValid()` as "a METHOD ON Table taking no arguments"
  whose doc comment "MUST also name the ONE property checked — escape-row shape
  conformance — and state that nothing else is checked".
- 0008 mandates a predicate over `Input` that "reads `Input.Owned`,
  `Input.Observed`, and each row's `RequiresOwned` reached through
  `Input.Table.Rows`".

These are two different receivers (`Table` vs `Input`) making two whole-table
passes, and 0009's doc contract affirmatively forbids `CheckValid` from being
the carrier for 0008's rule ("nothing else is checked"). That is a real design
constraint neither RDR states: 0008 cannot fold its check into `Table.CheckValid`
even though both scan the same rows.

**SEVERITY**: blocks-impl

**OWNERSHIP**: joint

**BLOCKS**: The implementation order of `Resolve`'s entry preconditions, and the
test for a doubly-breaching input. 0009's scenario 4 ("Breach precedence over
each modeled disposition, run once **per refusal kind**") is exhaustive over the
five refusal kinds but has **no** case for a peer precondition, and 0008's
scenario 6 has no doubly-breaching variant. Neither RDR's test suite can be
written to assert the combined behavior, and 0009's "precedes every modeled
disposition" plus 0008's "detected whenever present" are jointly unsatisfiable
as written when both fire, because `Resolve` returns a single `error`.

## FINDING 3

**TYPE**: round-trip

**A-QUOTE** (RDR 0008, Phase 2 and A4's migration inventory):

> Also in Phase 2: rename the three committed
> recognized-provenance declarations and **all six** of their
> tag-predicate reference sites (A4's inventory — five
> `[rule.match.outcome]` plus `[rule.guard.all.rewind_target]`

and, from A8's blast-radius sweep:

> *Blast radius, in-repo*: a sweep of

> `Key: "recognized"` returns exactly one hit —
> `fixtures_test.go:237`, inside
> `recognizedTagSensitiveTable`'s `Row.Match` — which is a

**B-QUOTE** (RDR 0009, scenario 5, the frozen-suite oracle):

> **Expected**: Every assertion still passes. The comparison
> baseline is the A3 spike's **conformed** run
> (`a3-conformed.out`: 154 PASS, 0 FAIL), restricted to the
> tests existing at that revision — **not** `a3-baseline.out`
> (the pre-conformance tree) and not the raw post-Phase-2
> count, which necessarily exceeds 154 because this RDR adds
> tests. The oracle is the sorted outcome set over that
> pre-existing test set, which must be identical.

**EXPLANATION**: The two RDRs both mutate the same frozen fixture tree in
`internal/resolve/*_test.go`, and 0009's conformance oracle is defined as an
**identical sorted outcome set** over the pre-existing tests — a property that
is not preserved under composition with 0008's changes. The round-trip does not
close in either order:

*Order 0009 → 0008*: 0009 Phase 2 strips `Writes` from `escapeRow` and its two
override sites, then pins the resulting outcome set as the oracle (154 PASS,
identical sorted outcome set). 0008 then lands its `Input` entry precondition.
0008's A8 sweep concludes "No existing fixture constructs an `Input` that would
trip the precondition" — but that sweep searched for the literal
`Key: "recognized"`, and 0008 itself scopes the sweep's reach: "the sweep finds
Go *literals*". More importantly, 0008 **adds** `resolve_test.go` scenarios 3,
6, 8, and 9 and a new view-capturing guard seam "added alongside
`internal/resolve/fixtures_test.go::fixtureGuards`". 0009's oracle explicitly
anticipates its *own* added tests ("the raw post-Phase-2 count … necessarily
exceeds 154 because this RDR adds tests") but is silent on a *peer* adding tests
to the same package. Re-running 0009's scenario 5 after 0008 lands compares a
tree neither RDR's oracle describes.

*Order 0008 → 0009*: worse, because 0009's oracle artifact `a3-conformed.out`
was generated from a spike run at a revision **before** 0008's fixture rename.
0008's Phase 2 renames `[tags.outcome]` → `[tags.recognized]` across three
committed fixtures and six reference sites, and 0008 states the rename changes
observable behavior: "the rename makes those fixtures *newly* functional against
the kernel — the predicate key `outcome` cannot match `assemble`'s injected key
`recognized` today and can afterward." A fixture that goes from not-matching to
matching changes the sorted outcome set of any test that exercises it. 0009's
scenario 5 has a regeneration escape hatch — "re-run the frozen suite at the
implementation's base commit immediately before Phase 1 lands and diff sorted
outcome sets over the tests existing at that commit — the spike file records an
instance of the oracle, not its definition" — which makes the oracle
*order-dependent*: the same two RDRs applied in the two orders produce two
different legitimate oracles, and neither RDR says which base commit is
authoritative.

This is the fidelity loss that makes it a round-trip finding rather than a
scheduling note: **0009's central non-regression guarantee ("zero disposition
change for conforming tables", asserted as an identical sorted outcome set) is
not invariant under 0008's landing, and 0008's A8 "no existing fixture … would
trip the precondition" is not invariant under 0009's fixture strip.** Each RDR's
evidence base is valid only against a HEAD that the other RDR moves. Neither
prose is individually wrong; the composition is.

Compounding it, both RDRs claim the same `resolve_test.go:748` anchor from
opposite directions — 0008 requires "the existing empty-`Input{}` case
(`resolve_test.go:748`), which the new precondition MUST keep green", while
0009's mutation check *Mutant A* concedes "after Phase 2 no pre-existing fixture
breaches, so the frozen suite alone cannot detect the check's removal." Two
entry preconditions on one `Resolve`, each of whose non-vacuity argument assumes
it is the only new check on that path.

**SEVERITY**: risks-impl

**OWNERSHIP**: joint

**BLOCKS**: Whichever RDR implements second cannot run its own frozen-suite
oracle as specified. Concretely it blocks 0009 scenario 5 (identical sorted
outcome set), 0009 scenario 6 Mutant A/B (non-vacuity, whose premise is that no
pre-existing fixture breaches), and 0008 scenario 6's conforming-`Input`
nil-error pin. The cluster must fix an implementation order and name one
authoritative base commit for the outcome-set oracle, or re-generate 0009's
oracle after 0008's rename.

## Ownership overlap check (probed, no separate finding)

The task asked whether the two RDRs' "single normative home" claims overlap.
**They do not.** Only 0009 makes the claim, and it is scoped:

> Ownership: **this RDR is the single normative home of the
> escape-row shape rule.** RDR 0002's normalizer *implements*
> the load-time half […]; RDR 0001's kernel *implements* the
> backstop half […]

0008 makes no competing "single normative home" claim for anything 0009 owns; it
uses the phrase only to *cite* RDR 0007's claim over `RequiresOwned` semantics
("its 'single normative home' clause covers the *guard-decidability domain
rule*"), and its own ownership claim is over the tag-key **name**. 0008 also
states the non-inheritance affirmatively in block 4: "The obligation is NOT
inherited from RDR 0009, whose obligation is a *different rule* (escape-row
shape) even where it reads the same `resolve.Row` values". Clean.

## Recognized-tag × escape-row interaction (probed, no separate finding)

The task asked whether 0009's "no owned-state mutation on an escape row" rule
governs the recognized-provenance tag. **It does not, and the two RDRs are
consistent here** — verified rather than assumed:

- The recognized tag is injected by `assemble` from `Input.Recognized`, never
  written by a row. 0008 A2's package sweep pins `::assemble` as "the sole
  injection point."
- 0009's predicate is `Writes`-only and does not widen: "The predicate is
  Writes-only and does NOT extend to NextTags: A4 settled that owned state is
  reachable only through a write accessor, which RDR 0004 scopes to 'planned
  owned-tag writes'".
- A row cannot legally write the recognized key anyway: 0008 routes that to a
  pre-existing peer rule — "what rejects it is RDR 0002's `write to non-owned
  tag` category (`0002…md:346`), because a recognized-provenance tag is not
  owned."

So an escape row bearing a recognized-provenance write is unrepresentable by
0002's grammar before 0009's predicate is reached. `grep -n "recognized"` over
0009 returns three hits, none of them normative (lines 467, 520, 744). No
governance gap.

## Validation-category collision check (probed, folded into Finding 2)

Both RDRs extend RDR 0002's data-level validation-category list, but into
**different categories**, and each cites the same extensibility fence:

- 0008 adds a new category: "`reserved_tag_key`", licensed by A1 against 0002's
  "including at minimum" fence.
- 0009 adds **no** category — it reuses 0002's pre-existing one: "an authored
  escape rule carrying a write block or clear list MUST be rejected at table
  load under RDR 0002's 'malformed escape declaration' validation class".

No collision at the category level. The ordering need is on the **kernel entry
preconditions**, not the lint categories, which is why it is folded into
Finding 2 rather than raised separately.
