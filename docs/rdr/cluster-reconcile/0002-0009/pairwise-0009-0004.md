# Pairwise reconcile: RDR 0009 (escape-row shape conformance ownership) × RDR 0004 (accessor execution safety model)

Both Final, both unimplemented. RDR_A = 0009. RDR_B = 0004.

## Test of 0009's cited reasoning about RDR 0004

The prompt asked three questions about the reasoning 0009 runs around A4. Answers first,
because two of the three findings below fall out of them.

**(1) Is "no writes, no clears" enforceable at the RDR 0004 accessor boundary?** No. It is
enforceable *only* upstream, at normalize time (RDR 0002) or kernel entry (RDR 0001's
`Resolve`), which is exactly where 0009 puts it. RDR 0004's write accessor is scoped by the
*provenance of the tag* ("planned owned-tag writes produced by a successful transition …
MUST NOT write observed or recognized tags"), never by the *provenance of the edge* that
produced the plan. A write-bearing escape plan carries owned-tag writes attached to a
transition the executor sees as successful, so every one of RDR 0004's validation clauses
passes and the executor applies it. 0009's guarantee therefore rests entirely on upstream
enforcement — which 0009 concedes in A4's *Carried forward* note and in Prerequisites, and
which RDR 0004's text does not carry anywhere. That asymmetry is FINDING 1 (gap) and its
round-trip consequence is FINDING 3.

**(2) Does 0004's "clear" semantics match 0009's "clears"?** There is no 0004 clear
semantics to match. Verified mechanically: `grep -n -i "clear" 0004-accessor-execution-safety-model.md`
returns **zero** lines. The same sweep returns zero for `escape`, `NextTags`, `next state`,
and `owned state`. So the feared vocabulary mismatch between two locked RDRs on the word
"clear" is not a mismatch — it is a one-sided vocabulary, and that is worse in one specific
way, recorded as FINDING 2: 0002 normalizes an authored clear into a `<clear>` *sentinel
write value*, and RDR 0004 — the layer that applies write values — has no clause telling it
that sentinel is a deletion rather than a literal string.

**(3) Is there a gap where an escape row's plan reaches the accessor layer and 0004 has no
obligation to refuse it?** Yes, and it is FINDING 1. Note the gap is narrower than it looks
under 0009's own Phase 1–2 scope (the kernel entry check makes such a plan unemittable *by
`Resolve`*), but RDR 0004 accepts plans as inputs and never re-derives them, so any producer
that hands 0004 a plan without traversing `Resolve` — which 0004's own contract permits,
since it names no plan-validity precondition — reaches the harm with no refusal.

**On 0009's positive reasoning from silence.** 0009's A4 argues from "the string `NextTags`
(and 'next state') appears **nowhere** in RDR 0004" to the conclusion that `NextTags` cannot
mutate owned state. The premise is true (verified above). The inference is not sound on its
own — absence of a term is not a prohibition — but 0009 does not rest on it: A4's links (1)
and (2) carry the argument from 0004's *positive* capability scoping, and 0009 explicitly
downgrades the residual to "a peer-contract dependency, not a predicate gap." That is
honest, and the A4 verdict survives. What does *not* survive is the assumption that a
dependency recorded on one side is a dependency that binds — see FINDING 1's severity.

## FINDING 1

TYPE: gap

A-QUOTE: "RDR 0004's implement stage keeps the write accessor
      scoped to *planned owned-tag writes* — the peer contract
      A4's verdict rests on. This RDR guarantees an escape plan
      carries no `Writes`; it does **not** guarantee anything
      about a plan's `NextTags`, so an implementer who widened
      \"apply the plan\" beyond planned writes would reintroduce
      the exact user symptom this RDR exists to prevent
      (A4, *Carried forward*). Recorded as a binding obligation
      rather than a note because RDR 0004 is the layer where
      the harm actually occurs. The obligation has a test form
      0004's implement stage copies: a write accessor handed an
      escaped plan with empty `Writes` and non-empty `NextTags`
      applies zero owned-tag mutations"

B-QUOTE: silent

EXPLANATION: RDR 0009 writes a *binding obligation on RDR 0004's implement stage*, complete
with a mandated test form, into RDR 0009's own Prerequisites checklist — a list that gates
0009's completion, not 0004's — while RDR 0004 names neither the obligation, the test, nor
RDR 0009 anywhere in its Prerequisites, Capability Dependencies, MVV, Testing Strategy, or
References, so the single load-bearing cross-RDR dependency in this pair is asserted
unilaterally by the RDR that does not own the enforcing layer.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: RDR 0004's Phase 3 ("Write Read-Back Verification") and its MVV scenario 3. 0004's
implementer builds the write path from 0004's own Testing Strategy, which specifies exactly
one write-success oracle — "the re-read owned-tag value equals the transition plan's expected
value and … pre-write observed and recognized tag values on the same artifact role remain
unchanged" — and has no scenario, fixture, or normative clause covering an escaped plan.
0009's mandated test ("a write accessor handed an escaped plan with empty `Writes` and
non-empty `NextTags` applies zero owned-tag mutations") therefore has no home: it cannot be
written into 0009's implementation (0009's own Testing Strategy scopes scenarios 1–7, 9, 10,
10b to its build and does not list this one at all — it is not even among the two it marks
DEFERRED), and 0004's implementer has no instruction to write it. The obligation is
unfalsifiable as filed, so nothing detects the widening that A4's entire verdict rests on.

NOTE ON WHY THIS IS NOT DISCHARGED BY CITATION: 0009 anticipates the objection and answers
it by *escalating the record* ("Recorded as a binding obligation rather than a note because
RDR 0004 is the layer where the harm actually occurs"). Escalating the wording does not
create an obligation on a locked peer. RDR 0004 is Final; 0009's Overrides field says
"None superseded" and scopes its narrowing to RDR 0001 and RDR 0002 only, never naming 0004
— so by 0009's own accounting it has not touched 0004's normative surface, which means the
obligation binds nobody.

## FINDING 2

TYPE: contradiction

A-QUOTE: "(Authored clears
normalize to `<clear>` writes per RDR 0002, so the Writes
predicate carries both \"no writes\" and \"no clears\" at the
kernel boundary.)"

B-QUOTE: "A write accessor MUST apply only planned owned-tag writes produced by a
successful transition. It MUST NOT write observed or recognized tags."

EXPLANATION: 0009 collapses "no clears" into "no writes" by relying on RDR 0002's
normalization of a clear into a `<clear>` *sentinel write value*, which is sound at the
kernel boundary where only emptiness is tested, but it pushes an unresolved sentinel into
RDR 0004's write accessor, whose contract speaks only of applying "planned owned-tag writes"
and contains the string "clear" zero times — so the layer that actually mutates the
authoritative artifact has no clause distinguishing "set this tag to the literal value
`<clear>`" from "delete this tag."

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: RDR 0004's Phase 3 and its Round-Trip / Inverse Invariant, which is stated as
"expected owned-tag value identity": for a planned `<clear>` write there is no expected
*value* to re-read — the correct post-state is the tag's absence — so 0004's read-back
comparison is unwritable for the clear case. It also blocks 0002's own guarantee "Absence
from both the write block and the clear list MUST NOT imply deletion," whose contrapositive
(presence in the clear list MUST imply deletion) has no enforcer at the only layer that
deletes. An implementer following 0004 verbatim writes the four-character string `<clear>`
into the artifact and reports read-back success.

NOTE ON SCOPE: this finding is *reachable* independently of escape rows — it is the ordinary
authored-clear path — but 0009 is the RDR that asserts the equivalence load-bearingly and
the RDR whose predicate correctness depends on it ("the Writes predicate carries both 'no
writes' and 'no clears'"). 0009's Phase 3 gets closest to noticing, requiring "one canonical
authored-clear case pins the `<clear>`-sentinel-write representation identically for the
kernel suite and the normalizer suite" — two enforcers named, and the third, the one that
applies it, omitted.

## FINDING 3

TYPE: round-trip

A-QUOTE: "Positive: no write-bearing escape plan can be emitted by
  any producer path — the ADV-2b \"kernel guessing at
  persistence\" class is closed before RDR 0004 can apply an
  unsanctioned write."

B-QUOTE: "`write -> read = expected owned-tag value identity + protected non-owned tag
identity`: after a write accessor reports command-level success, reading the
same caller-supplied artifact role named by the write binding must return the
expected owned-tag values, and any observed or recognized tag values present
before the write must remain unchanged."

EXPLANATION: RDR 0004's sole round-trip invariant verifies the write against *the plan it was
handed* — expected owned-tag values in, same values back out — so it is fidelity-preserving
with respect to the plan and structurally blind to whether the plan was sanctioned, meaning
an unsanctioned escape-borne write round-trips **successfully**: `write -> read` returns the
expected value, no observed or recognized tag changed, read-back reports success, and the
user's originating symptom ("afterwards an owned tag has a value no rule in their table ever
set") is reached through a green invariant rather than a failing one.

SEVERITY: risks-impl

OWNERSHIP: joint

BLOCKS: The premortem check on 0004's own stated silent-failure guard. 0004 asserts "Silent
failure would mean a write command reported success but the owned tag did not change as
expected; the mandatory read-back check is the guard against that case" — but the escape-borne
write is the *inverse* silent failure (the tag changed exactly as the plan expected, and the
plan was illegitimate), which read-back cannot see by construction. This prevents 0009 from
claiming defense in depth: 0009's Failure Modes says the silent failure was "previously
constructible and downstream-applied by RDR 0004 with no symptom until owned state diverged,"
correctly conceding 0004 provides no symptom, yet 0009's Consequences line above still reads
as though closing the emit path closes the harm. It closes it only for plans that traverse
`Resolve`, and neither RDR states that traversal as a precondition on 0004's input.

NOTE ON WHY THIS IS NOT MERELY FINDING 1 RESTATED: Finding 1 is the missing obligation on
`NextTags`. This finding holds even if that obligation is honored in full — a write accessor
perfectly scoped to planned owned-tag writes still applies a `Writes`-bearing escape plan,
because `Writes` *are* planned owned-tag writes. The two findings need different fixes:
Finding 1 wants a clause in 0004 about plan fields it must ignore; this one wants a clause
about plan *legitimacy* it cannot verify, which likely resolves as an explicit statement in
0004 that plan validity is a precondition owned upstream and NOT checked at the accessor
boundary — currently stated on neither side.

## Enumeration discipline

Escalation to exhaustive enumeration was considered and declined. Finding 1 is the
blocks-impl finding, and it is fixable in isolation: the repair is to give the obligation a
home on RDR 0004's side (a Capability Dependency row plus an MVV scenario), which requires no
enumeration of the remaining seam. Finding 2 is separately blocks-impl and separately
fixable. Neither repair depends on knowing the full contradiction set, so the top-3 scope
holds.

Two candidate findings were dropped as non-findings and are recorded here so the pass is
reproducible:

- **0009's "appears nowhere in RDR 0004" inference** — verified true as a fact and correctly
  downgraded by 0009 itself to a peer-contract dependency rather than a proof. Not a finding
  in its own right; its live residue is Finding 1.
- **Refusal-vocabulary divergence** — 0004 enumerates its own refusal classes (timeout,
  execution failure, gate indeterminate, read-back mismatch, capability mismatch) entirely
  outside RDR 0001's closed five-kind taxonomy that 0009 works so hard to keep closed. This
  looks like a taxonomy collision but is not: 0004's classes are accessor-layer values mapped
  through `clierr`, never resolver dispositions, and 0009's concern is strictly the resolver
  taxonomy. Both sides are consistent; recorded as a non-finding.
