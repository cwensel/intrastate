## FINDING 1

TYPE: contradiction

A-QUOTE: "PRESENCE IS PROVENANCE-BLIND. \"Present in the assembled
view\" means the tag key is in the view under ANY provenance —
`ProvenanceOwned`, `ProvenanceObserved`, or `ProvenanceRecognized`
(`resolve.go`). A guard atom MUST NOT be decided differently according
to how a tag reached the view, and `exists` MUST decide TRUE for an
observed- or recognized-supplied key exactly as for an owned one."
— 0007, Normative Contracts

and (same RDR, the value-operator block):

"Value-comparing guard operators (equality, membership, bounded integer
comparison, set containment) are PARTIAL over the assembled evaluation
view: an atom whose referenced tag key is absent from the view MUST
evaluate to unevaluable — never to false and never to true."

B-QUOTE: "The reservation holds unconditionally — the key is reserved
whether or not a given resolve binds it — while the binding obligation
is scoped to resolves that carry an outcome: `assemble` injects only for
a non-empty `Input.Recognized`, so an absent outcome yields a view with
no `recognized` key."
— 0008, Normative Contracts block 1

EXPLANATION: 0008 normatively guarantees that a resolve with an empty
`Input.Recognized` produces a view with **no `recognized` key**, and
0007 normatively requires any value-comparing guard atom over an absent
key to return `GuardUnevaluable` — so a table that guards
`[rule.guard.all.recognized] eq = "…"` refuses the *entire resolution*
with the non-escapable `guard_unevaluable` on every unrecognized-outcome
resolve, which is the ordinary steady-state case, and neither RDR says
this is intended.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: The 0003 evaluator implementer cannot decide whether an absent
`recognized` key is 0007's `owned_state_unavailable`/`GuardUnevaluable`
domain (state the view does not carry) or 0002/0008's plain no-match.
It also blocks 0008's Phase 2 fixture rename: 0008 renames
`[rule.guard.all.rewind_target]` (`guard-fixture.toml:72`) into the
reserved-key family, and under 0007's rule that renamed guard becomes
`guard_unevaluable` — table-wide, non-escapable — on every resolve
without that outcome. No test in either RDR contends it: 0007's Testing
Strategy rows 4–8 quantify over "operators × present/absent" with no
recognized-provenance row, and 0008's scenario 3 asserts only
`Lookup("recognized") == (in.Recognized, ProvenanceRecognized, true)`
— i.e. the **present** case only.

Why this is a genuine contradiction and not merely a gap: 0007's
aggregation clause makes the consequence table-wide, not row-local —
"if any surviving candidate row's guard is GuardUnevaluable, the
resolution MUST refuse guard_unevaluable — a decided-GuardTrue sibling
row MUST NOT be selected while an unevaluable candidate exists" — and
0008's own Failure Modes commits to the opposite disposition for this
exact key: "input that bypasses both lint and the producer obligation
shadows the recognized value under D3 and surfaces as a deterministic
`no_match` refusal." `no_match` is escapable per RDR 0002 L292;
`guard_unevaluable` is not. Two locked RDRs therefore predict two
different, user-visible refusal classes for the same absent reserved
key.

Note the additional asymmetry the two RDRs create by accident: 0008
explicitly declines to require the declaration — "this RDR imposes **no
lower bound** — a model that declares no recognized-provenance tag at
all is conforming here" — so 0008 treats the recognized tag as an
optional affordance, while 0007's domain rule treats any reference to a
then-absent key as a hard, non-escapable refusal of the whole table.
Optional affordance and non-escapable veto do not compose.

## FINDING 2

TYPE: gap

A-QUOTE: "The existence operator is the sole TOTAL operator: it MUST
decide true or false from the presence or absence of its referenced tag
key alone. … Its verdict is `presence == literal`: `exists = true`
decides TRUE when the key is present, and `exists = false` decides TRUE
when the key is ABSENT."
— 0007, Normative Contracts

B-QUOTE: "The checked positions are the `[tags.<tag>]` declaration keys
only. Reserved-name uses in predicate positions
(`[rule.match.<tag>]`, `[rule.guard.all.<tag>]`,
`[rule.guard.unless.<tag>]`) need no separate reserved-key check: a
conforming model declares `recognized` and those references resolve to
it, while a model that does not declare it already fails RDR 0002's
`unknown tag` rule."
— 0008, Normative Contracts block 2

EXPLANATION: 0008 rules that a guard reference to `recognized` is
legal-by-fall-through the moment the declaration exists, and never
considers that 0007 gives `exists` on that key a *decided* verdict
computed from `Input.Recognized`'s emptiness — making
`[rule.guard.all.recognized] exists = false` a legal, lint-clean,
author-visible predicate meaning "no outcome was recognized this
resolve," a control-flow affordance neither RDR states, owns, or tests.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Whether `exists` over the reserved key is a sanctioned authoring
affordance or an unintended backdoor around `Row.Outcome` gating.
0008's Key Discoveries insists "Outcome gating never reads the key: the
gate is `row.Outcome != in.Recognized` plus the outcome-alphabet check,
so the tag-key path is a secondary affordance" — but under 0007 the
absence of the key becomes a *decidable* guard fact, so a row can now
gate on the negation of recognition without using `Row.Outcome` at all.
0008's A2 sweep enumerated exactly five `Input.Recognized` reads and
concluded `Row.Outcome` is "a first-class non-tag field unaffected by
any reserved tag-key rule"; that conclusion is sound about the reads and
unsound about the consequence, because 0007 adds a sixth *derived*
observable (key-absence) that A2's read-sweep methodology cannot see.
No scenario in either RDR encodes it: 0008 scenario 4's near-miss row
`[tags.result]` is a declaration test, not a guard test; 0007's
existence scenarios (row 6, `all … exists = false`) are generic and
never instantiate the reserved key.

## FINDING 3

TYPE: round-trip

A-QUOTE: "This is deliberately NOT the kernel's owned-state predicate:
`resolve.go::missingOwned` tests `view.has(key, ProvenanceOwned)`
because `owned_state_unavailable` is about the owned snapshot
specifically. Guard decidability is the broader question and takes the
broader test — `TagSet.Lookup`'s provenance-blind `ok`. The two
predicates answer different questions and MUST NOT be conflated."
— 0007, Normative Contracts (PRESENCE IS PROVENANCE-BLIND block)

B-QUOTE: "**Expected**: the key is reported missing and the resolution
refuses `owned_state_unavailable` with `MissingOwned` containing
`recognized` — pinning that the unreserved case is reachable, not
hypothetical (`::missingOwned` tests `view.has(key, ProvenanceOwned)`;
`::TagSet.has` is provenance-specific)."
— 0008, Testing Strategy scenario 9

EXPLANATION: For one and the same view holding `recognized` under
`ProvenanceRecognized`, 0007's provenance-blind presence test says the
key IS present (so `exists = true` decides TRUE and a value atom is
decidable) while 0008 scenario 9 pins the kernel reporting that same key
as MISSING via `MissingOwned` — so "present" does not survive the
round-trip through the two predicates, and a refusal payload that names
`recognized` as missing is emitted for a key that 0007 normatively
requires guards to read as present.

SEVERITY: risks-impl

OWNERSHIP: joint

BLOCKS: The diagnostic contract for a single resolve that trips both
paths. 0007 pins the ordering — "Among surviving rows, absent owned
state is reported BEFORE an undecidable guard: a survivor set carrying
both MUST refuse `owned_state_unavailable`" — so on the
package-internal path 0008 scenario 9 exercises, a row that both names
`recognized` in `RequiresOwned` and guards on it emits
`owned_state_unavailable` naming `recognized` as missing, while 0007's
own rule holds the guard read it as present. That refusal is not
idempotent under the obvious operator remedy either: the operator is
told the reserved key is missing, but supplying it is *forbidden* by
0008's block 4 ("Producers of kernel `Input` MUST NOT supply an owned or
observed tag keyed `recognized`"), so acting on the refusal's own
diagnosis converts a refusal into a Go-error programmer-mistake — a
fidelity-losing round trip through the diagnosis→remedy→re-resolve
cycle.

Both RDRs individually license their half. 0008 A7 explicitly clears
itself of encroachment ("it touches neither the post-guard
write-dependency definition nor the provenance-blind-vs-owned-only test
distinction 0007 pins") and 0007's block does state the distinction —
but neither states what the *combined* observable is, and 0008's block 5
narrows rather than removes the path ("It stays a documented residual on
that narrowed path"). The residual is exactly where the round-trip
breaks.

## Verdict

BLOCK. Findings 1 and 2 are `blocks-impl` and are joint-ownership: no
single-RDR edit closes them, because 0007 owns the verdict for an absent
key and 0008 owns whether the key is absent. Since this project does not
amend RDRs, the disposition is a cluster-level decision routed to the
Stage 7.1 owner, or a successor RDR that fixes the recognized-key
evaluation-domain boundary explicitly.
