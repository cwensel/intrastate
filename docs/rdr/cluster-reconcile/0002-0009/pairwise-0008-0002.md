# Pairwise reconcile — RDR 0008 (A) × RDR 0002 (B)

RDR_A = `docs/rdr/0008-recognized-tag-key-ownership.md` (Final, unimplemented)
RDR_B = `docs/rdr/0002-transition-table-as-reviewable-data.md` (Final, unimplemented)

Seam under test: RDR 0008 governs the *name* of the recognized-provenance tag
key that RDR 0001's kernel (`internal/resolve/resolve.go::assemble`) emits into
the assembled view, and that RDR 0002's declared model / normalizer must declare
and match on. Emit side is implemented; consume side is not.

Verdict: **NEEDS_DECISION**. RDR 0008's "narrows nothing in either peer" claim is
false in one respect and unsupported in another. The `reserved_tag_key` category
addition survives the test (RDR 0002's list is genuinely open); the *name
constraint* does not (it lands in a different, closed normative block and it
does narrow RDR 0002's author-naming rule). Separately, the emit/consume seam has
a real round-trip identity break on one input class.

---

## TOP 3 FINDINGS

### Finding 1

TYPE: round-trip

A-QUOTE: "When a resolve carries a freshly recognized outcome, the
assembled evaluation view MUST bind it under exactly the tag
key `recognized`
(`internal/resolve/resolve.go::recognizedTagKey`). The key
is a reserved kernel keyword: table authors conform to it
and MUST NOT rebind it. The reservation holds
unconditionally — the key is reserved whether or not a given
resolve binds it — while the binding obligation is scoped to
resolves that carry an outcome: `assemble` injects only for a
non-empty `Input.Recognized`, so an absent outcome yields a
view with no `recognized` key."

B-QUOTE: "The model MUST declare every tag it matches or writes, including each
tag's provenance: owned, observed, or recognized."

EXPLANATION: The declaration channel is total (a declared `recognized` tag always
exists in the model) but the emit channel is conditional (`assemble` injects the
key only when `Input.Recognized != ""`), so on the empty-outcome input class a
row matching on the reserved tag sees *no key at all* rather than the declared
tag with an empty value — the consume side cannot distinguish "outcome absent"
from "outcome present and empty", and `TagSet.matches` fails closed on both.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: The normalizer cannot decide whether a declared recognized-provenance tag
is a *total* tag (always present in the view, possibly empty) or a *partial* one
(absent when no outcome is in flight). That decision governs whether
`[rule.match.recognized]` with an empty-string predicate is a satisfiable row, an
`unknown tag` lint error, or a permanently-dead row — and it prevents writing
scenario 1's "row fires against a recognized outcome" test for the empty-outcome
input class at all.

**Input-class breakdown across the seam** (does a row matching on the reserved
tag see exactly the key+value the kernel emits, value-for-value?):

| Input class | Kernel emits | Table row matching on `recognized` sees | Identity holds? |
| --- | --- | --- | --- |
| `Input.Recognized = "round-clean"` (in alphabet) | key `recognized`, value `"round-clean"`, `ProvenanceRecognized` | same key, same value | **Yes** — identity holds |
| `Input.Recognized = ""`, alphabet excludes `""` | *no key emitted* (`assemble:151`) | key absent; `matches` returns false | **No — fidelity loss** |
| `Input.Recognized = ""`, alphabet *includes* `""` | *no key emitted*; `Table.models("")` passes via `slices.Contains` | key absent, yet resolve proceeds past the alphabet gate to selection | **No — outright failure** |
| `Input.Recognized` shadowed by owned/observed tag keyed `recognized` | key `recognized` present but carrying the *owned/observed* value under the wrong provenance (D3 last-writer-wins, `assemble:157-162`) | wrong value, wrong provenance | **No — outright failure on the bypass path** |

The third row is the one RDR 0008 names and then declines to close: it states the
degenerate alphabet entry "would pass the alphabet gate (`Table.models` is a
plain `slices.Contains` ...) and resolve with no reserved key in the view;
nothing in this RDR or RDR 0002 forbids that alphabet entry" and elects to leave
it "unforbidden rather than silently assumed away". RDR 0002 is silent — its
alphabet contract is only "Recognized outcome alphabet: the closed set of outcome
tags that the recognizer may emit for the flow", which does not exclude `""`.
Neither RDR's prose is individually wrong, which is exactly why this is filed as
a contradiction-class round-trip finding rather than a defect in either document:
the composition is non-total.

The fourth row is contained by RDR 0008's block 4 predicate for callers going
through `Resolve`, but RDR 0008 itself concedes the residual survives on the
package-internal path ("input that reaches `assemble` without passing the
precondition"). That residual is a *fidelity loss* not an outright failure,
because D3 makes it deterministic.

### Finding 2

TYPE: contradiction

A-QUOTE: "extends RDR 0002's tag-declaration
surface with a name constraint on recognized-provenance
declarations and one additional data-level validation
category (`reserved tag key`, within its \"including at
minimum\" extensible list). Narrows nothing in either
peer."

B-QUOTE: "The source schema MUST use the Resolve spike field layout: root `outcomes`,
`[model]`, `[tags.<tag>]`, `[accessors.<id>]`, `[context.<id>]`, `[[rule]]`,
and `[dump]`."

EXPLANATION: The "narrows nothing" claim is false for the name-constraint half —
RDR 0002's `[tags.<tag>]` grammar admits any tag name and carries no
extensibility fence, so forbidding `[tags.outcome]` with `provenance =
"recognized"` strictly narrows the set of models RDR 0002 accepts, and it
invalidates all three of RDR 0002's own canonical fixtures.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: Whether an RDR 0002 implementer may accept a model that RDR 0002's own
normative text and canonical fixtures accept. Until resolved, the two RDRs
license two different normalizers, and the "canonical examples implementation
tests must promote" instruction in RDR 0002 conflicts directly with RDR 0008
Phase 2's rename of those same fixtures.

**Testing the extensibility claim hard, as instructed — the claim splits in two
and only one half survives:**

*Half one (the validation category) — RDR 0008 is correct.* RDR 0002's list is
genuinely open. Its wording is "Validation failures MUST retain stable
data-level categories before CLI mapping, including at minimum malformed TOML,
unknown schema field, missing recognized outcome alphabet, unknown tag, unknown
context, write to non-owned tag, unknown accessor, unsupported version, malformed
escape declaration, and ambiguous overlap." "including at minimum" is a floor.
The corroboration RDR 0008's A1 offers is sound and I confirmed it independently:
RDR 0002 writes closure explicitly when it means closure — "Recognized outcome
alphabet: the closed set of outcome tags", "Version `1` is the only version this
RDR accepts", "An `escape` list MUST contain only resolver failure classes". A
document that distinguishes "only"/"closed set" from "including at minimum" in
adjacent contracts is not accidentally open. **A1 is Verified and holds.**

*Half two (the name constraint) — RDR 0008's Overrides field overclaims.* RDR
0008's own A1 Scope limit concedes this precisely: "A1 licenses the new
*category* but not the new *constraint on tag names*; that half is licensed by
this RDR's Overrides field". But an `Overrides` field is a claim, not a license —
and RDR 0008's own A12 establishes that the field is inert: "The `Overrides`
field is **never read by the engine**: `grep -rn \"Overrides\"` over
`$RDR_HOME/prompts/ stages/ skills/` returns no matches". So the name constraint
is licensed by a field that nothing reads, asserted over a normative block that
carries no extensibility fence, against a peer that is already `Final`. The
Metadata claim "Narrows nothing in either peer" is therefore **not sustainable as
written** and should read "narrows RDR 0002's `[tags.<tag>]` naming freedom for
exactly one provenance value."

*Does the name constraint conflict with RDR 0002's rule that authors name their
own tags?* Yes, though the conflict is with RDR 0002's design ethos and worked
examples rather than with an explicit "authors may choose any name" sentence —
RDR 0002 never writes that sentence, which is what lets RDR 0008 slip through on
a literal reading. The conflict is nonetheless concrete and evidenced: RDR 0002's
fixture declares `[tags.outcome]` / `provenance = "recognized"`
(`rdr-fixture.toml:25-27`), and RDR 0002 designates the fixtures "the canonical
examples implementation tests must promote". RDR 0008 acknowledges the collision
honestly in A4 ("**three violations at HEAD**") and in its Problem Statement
("all three committed recognized-provenance declarations chose an author name
(`outcome`, `outcome`, `rewind_target` — A4), so every author observed so far
exercised the freedom this RDR withdraws"). The disclosure is exemplary; the
Metadata summary contradicts it.

### Finding 3

TYPE: gap

A-QUOTE: "**The carried half is handed to 0002 explicitly** — this
      RDR's Normative Contracts are a named input to RDR
      0002's Stage 8 run, or a pointer to this RDR lands in
      0002's own surface as a cross-RDR edit. Not optional and
      not automatic"

B-QUOTE: silent

EXPLANATION: RDR 0002 carries zero occurrences of `0008`, no pointer from its
`[tags.<tag>]` grammar block, and no `reserved_tag_key` in its enumerated
category list, so an RDR 0002 implementer reading RDR 0002 alone ships a
normalizer that accepts any `[tags.<name>]` and the entire authoring-time
diagnosis — the Problem Statement's actual outcome — never arrives.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: The choice between the two repair forms RDR 0008 offers (named-input vs.
cross-RDR edit into RDR 0002's surface). RDR 0008 explicitly routes this to
Stage 7.1 and refuses to decide it unilaterally — "Which of the two forms is used
is a Stage 7.1 call; that one of them happens is a gate here" — so this is a
decision the cluster read owes, not a defect either RDR can fix alone. It also
blocks any claim that RDR 0008 is implementable in isolation: RDR 0008 itself
states "every scenario that delivers the Problem Statement's outcome ... is in the
carried half" and that "this RDR can reach 'implemented' with its user-facing
outcome still unshipped".

Note this is a *gap* rather than a duplication or contradiction: RDR 0008 has
already refuted its own A12 ("**Refuted as stated** — the assumed mechanism does
not exist") and converted the finding into an explicit Prerequisite. The document
work is done; what remains is the cross-RDR action, which is unperformed and
which nothing in RDR 0002 records.

## Escalation judgment

Exhaustive enumeration **not** required. The three blocks-impl findings above are
each fixable without listing the remainder:

- Finding 1 needs one sentence in whichever RDR locks last, settling whether the
  reserved tag is total or partial in the view, plus a decision on the
  empty-string alphabet entry.
- Finding 2 needs the Metadata `Overrides` sentence corrected (per project
  doctrine RDRs are not amended, so this lands as a cluster-reconcile note and a
  correction in whichever RDR moves next), and the fixture-rename ownership
  settled.
- Finding 3 needs the Stage 7.1 form choice made.

None of the three requires enumerating the rest of the pairwise surface to
repair.
