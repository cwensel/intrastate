# Pairwise reconcile: RDR 0007 (guard predicate totality) × RDR 0002 (transition table as reviewable data)

Both Final, both unimplemented. RDR_A = 0007. RDR_B = 0002.

Scope note on the framing question posed to this pass: **0007 does NOT need an escape
route or a table-level declaration that 0002's closed grammar refuses.** 0007's whole
design depends on `guard_unevaluable` being *inexpressible* in an `escape` list, and
0002's L292 closure delivers exactly that by construction. That leg is coherent and is
recorded here as a non-finding. The real damage is elsewhere: 0002's resolver-flow
prose, its escape-rule shape, and its normalization round-trip predate the third verdict
value 0007 introduces, and none of the three was widened to carry it.

---

## FINDING 1

TYPE: contradiction

A-QUOTE: "Aggregation is resolution-level, not merely per-guard: if
any surviving candidate row's guard is GuardUnevaluable,
the resolution MUST refuse guard_unevaluable — a
decided-GuardTrue sibling row MUST NOT be selected while
an unevaluable candidate exists."

B-QUOTE: "Runtime matching is deliberately priority-free: the resolver evaluates
non-escape candidate rows against the supplied tag-set and succeeds only when
exactly one row matches. If zero or multiple non-escape rows match, the resolver
may return a modeled escape disposition only when exactly one escape row matches
the same tag-set and its `escape` list contains the corresponding failure class;
otherwise it returns the kernel-owned typed refusal."

EXPLANATION: 0002 states the resolver's escape-reachability condition as a total
function of the *match count* over non-escape rows ("If zero or multiple non-escape
rows match"), leaving no state in which a table with exactly one matching row fails to
transition, whereas 0007's aggregation veto refuses before any counting happens and can
kill a table where exactly one row matches and is decided TRUE, purely because an
unevaluable sibling also matched.

SEVERITY: blocks-impl

OWNERSHIP: joint

BLOCKS: The normalizer/resolver handshake in 0002 Phase 4 ("Connect the normalized rows
to RDR 0001's exact-one matching contract"). An implementer reading 0002 builds a
two-stage match-then-escape resolver with no pre-count veto stage; an implementer
reading 0007 builds a three-stage gate-then-count resolver. It also prevents writing
0002's Testing Strategy Scenario 4 ("Run exact-one selection over one matching ordinary
tag-set …"), because 0002's stated expectation — "The matching ordinary tag-set resolves
to one transition row" — is now conditional on no sibling row being unevaluable, a
qualifier 0002's scenario does not carry and cannot express.

NOTE ON NON-RESOLUTION BY CITATION: 0007 anticipates a version of this and answers only
the *escape* half ("Counting zero-versus-multiple survivors is NOT part of this contract
and does not happen inside the gate: RDR 0001 owns it"). That defers counting to RDR
0001, not to 0002 — but 0002 L237–L241 states the counting rule in its own voice as
part of its own Technical Design, and 0002 is the document a table author reads. The
deferral does not reach the text that contradicts.

## FINDING 2

TYPE: gap

A-QUOTE: "An unevaluable ESCAPE row yields
guard_unevaluable in place of the candidate-set refusal:
the kernel MUST NOT claim the escape failed to rescue when
it could not decide the escape at all."

B-QUOTE: "Each transition rule MUST contain a stable rule id, zero or more shared-context
references, and a local match block. An ordinary transition rule MUST contain a
write block and MAY contain a rule-level explicit clear list. A write block MAY
assign more than one tag. An escape rule MUST contain an `escape` list and MUST
NOT contain a write block or clear list."

EXPLANATION: 0007 makes an escape row's *guard verdict* load-bearing enough to override
the entire candidate-set refusal, but 0002's escape-rule shape contract enumerates what
an escape rule must and must not contain and never says whether an escape rule may carry
`[rule.guard.all.<tag>]` / `[rule.guard.unless.<tag>]` at all — so the row shape 0007's
strongest escape clause quantifies over is not granted by the format that owns row shape.

SEVERITY: blocks-impl

OWNERSHIP: joint — 0002 owns row shape; 0007 owns the verdict consequence.

BLOCKS: 0007 Testing Strategy Scenario 5(a), "an unevaluable escape row over a `no_match`
candidate set", cannot be encoded as a *table* until 0002's schema admits a guarded
escape rule. It equally blocks 0002 Phase 3's "validation rules for … escape
declarations": the validator cannot decide whether `[rule.guard.all]` beside
`escape = ["no_match"]` is a well-formed rule or a "malformed escape declaration"
(0002's own mandatory validation category). Today the answer is unwritten in both
directions, so two implementers will pick opposite defaults and one of them silently
deletes 0007's escape-gating contract.

CORROBORATION THAT THE SHAPE IS UNGRANTED RATHER THAN MERELY UNSTATED: 0002's canonical
fixture escape rule carries a match block and no guard block —
`id = "draft-no-match-escape"` / `use = ["draft"]` / `escape = ["no_match"]` /
`[rule.match]` `outcome.eq = "round-clean"` — and 0002 elevates that fixture to
normative status: "The RDR and kata spike fixtures are the canonical examples
implementation tests must promote." The one canonical escape row in the tree is
unguarded, so the fixture corpus supplies no witness for the shape 0007 requires.

## FINDING 3

TYPE: round-trip

A-QUOTE: "Row.RequiresOwned names the owned tag keys the row's
post-guard transition depends on — the keys its `Writes`
require, which per RDR 0002 includes an authored clear
(normalization \"renders as a `<clear>` write\", so the kernel
`Row` carries no separate clear list)."

B-QUOTE: "`parse ∘ normalize ∘ dump = expanded-table value identity` on valid transition
model fixtures: dumping the normalized model and reading the dump as a table
view must preserve the candidate-row set, including row identity, source
locator, row kind, predicates, writes, and escape failure classes."

EXPLANATION: 0002's round-trip invariant enumerates the fields normalization must
preserve across the seam — identity, locator, kind, predicates, writes, escape classes —
and `RequiresOwned` appears in neither that list nor anywhere else in 0002, so the
normalizer that *emits* candidate rows is under no obligation to produce the field the
kernel that *consumes* them now treats as normative, and a dump/reload cycle is permitted
to be fidelity-losing on exactly the field 0007 redefines.

SEVERITY: blocks-impl

OWNERSHIP: joint — 0002 owns the emitted row value and its preservation set; 0007 owns
the field's meaning.

BLOCKS: The `owned_state_unavailable` half of 0007's ordering contract. 0007 pins
"Among surviving rows, absent owned state is reported BEFORE an undecidable guard: a
survivor set carrying both MUST refuse `owned_state_unavailable`" — an assertion over
`RequiresOwned` contents. If normalization derives `RequiresOwned` from `Writes` (0007's
reading) the field survives the round-trip derivatively; if it is a kernel-side input the
table never supplies, the ordering clause quantifies over an always-empty set and 0007's
Phase 2 "owned-state ordering gap" vector is unwritable. Nothing in either RDR says
which.

WHY THIS IS A ROUND-TRIP FINDING AND NOT MERELY A GAP: the failure is a fidelity loss
*across the seam*, not a missing sentence on one side. B's stated inverse-pair
(`normalize` emits → `dump`/reload reconstructs) is asserted to be value-identity, and A
adds a field to the value that B's identity does not cover. The composition is therefore
non-identity on every input class carrying a clear or a multi-tag write — precisely the
classes B calls first-class ("Multi-tag writes are first-class because RDR rewinds and
kata lifecycle moves need to set both the next stage/state and side-channel scope tags in
one edge"). Neither RDR's prose is individually wrong; the pair does not compose.

SECOND-ORDER FIDELITY LOSS ON THE SAME SEAM: 0007 derives `RequiresOwned` through the
clear-to-write rewrite — B's "Clearing a tag MUST be represented by an explicit
rule-level `clear` entry that normalization renders as a `<clear>` write. Absence from
both the write block and the clear list MUST NOT imply deletion." A `<clear>` write is a
write whose owned-key dependency is the key being *removed*, not written; folding it into
the same `RequiresOwned` set as an ordinary assignment makes the two indistinguishable
downstream, so even a normalizer that does emit the field emits a lossy one. 0007 asserts
the fold ("the kernel `Row` carries no separate clear list") as a settled reading of
0002; 0002 never states that the kernel `Row` shape drops the distinction — it states
only what the *dump* renders.

## Escalation check

Not escalated to exhaustive enumeration. Each of the three blocks-impl findings above is
fixable in isolation — Finding 1 by 0002's implement stage restating its resolver flow as
gate-then-count, Finding 2 by 0002's implement stage ruling on guarded escape rules,
Finding 3 by naming `RequiresOwned`'s producer and adding it to the preservation set —
and none requires listing the remainder to state its fix. Per instruction, the tail is
not enumerated.

## Non-findings recorded deliberately

- **Escape-class closure is sound, not contradictory.** A: "The kernel maps
  GuardUnevaluable to the refusal kind `guard_unevaluable`, which is not a modelable
  escape class (RDR 0002)." B: "An `escape` list MUST contain only resolver failure
  classes that RDR 0001 allows the table to model: `no_match` and `ambiguous_match`."
  These compose correctly and in the direction 0007 needs. 0007 requires the closed list
  to *stay* closed and requires no new member, no escape route, and no table-level
  declaration. 0002 needs no change for this leg, and any future widening of the escape
  list to admit a third class would silently destroy 0007's core guarantee — that
  coupling should be recorded at 0002's implement stage as a do-not-widen constraint.
- **Empty-`unless` identity is cleanly owned.** 0007 A9 establishes 0002's silence and
  takes the identity itself, citing 0002's analogous write-side rule as evidence that
  0002 states such identities when it means to. No duplication and no contradiction; the
  ownership split is explicit on the 0007 side and harmless on the 0002 side.
- **Guard block representation is not duplicated.** Both RDRs speak about
  `all`/`unless`, but 0002 fixes representation and combination timing ("Guard predicates
  MUST be represented as positive `all` predicates and negative `unless` predicates.
  Normalization MUST combine both into one candidate-row predicate set before ambiguity
  checks") while 0007 fixes truth values over that shape. Adjacent, not overlapping.
