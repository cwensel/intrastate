## FINDING 1

**TYPE**: contradiction

**A-QUOTE** (RDR 0007, Normative Contracts, SURVIVOR MEMBERSHIP block):
> "This RDR fixes three ordering facts and no others —
> guard-FALSE prunes first (D8), absent owned state is
> reported before an undecidable guard among survivors, and
> the aggregation veto below. `no_match` / `ambiguous_match`
> sit downstream of all three by RDR 0001's selection rule."

**B-QUOTE** (RDR 0009, Normative Contracts, kernel entry-precondition block):
> "The precondition is evaluated over the WHOLE table before any
> evaluation step: a breach surfaces even when no resolution
> path reaches the offending row, and it precedes every
> modeled disposition (a malformed table is malformed as a
> value, independent of the input tuple)."

and (RDR 0009, Testing Strategy scenario 4):
> "Breach precedence over each modeled
> disposition, run once **per refusal kind** — a breaching
> row coexisting with a table state that would otherwise
> yield `unmodeled_outcome`, `no_match`, `ambiguous_match`,
> `owned_state_unavailable`, and `guard_unevaluable`
> respectively."

**EXPLANATION**: 0009 inserts a fourth, higher-priority ordering fact — a
whole-table shape breach that outranks `guard_unevaluable` — directly ahead of
the three-fact chain 0007 declares closed with "and no others," so a row that
is both a write-bearing escape row and an unevaluable-guard row has two
independently-locked normative answers (0009: Go error, zero `Result`; 0007:
`guard_unevaluable` refusal naming the row) and no stated precedence in 0007.

**SEVERITY**: blocks-impl

**OWNERSHIP**: joint — 0009 alone cannot claim precedence over a peer's
closed ordering enumeration, and 0007's "no others" cannot stand while a
sibling RDR at the same locus adds a fact; the precedence rule is a shared
decision.

**BLOCKS**: RDR 0009 Testing Strategy scenario 4's `guard_unevaluable` leg
cannot be written against RDR 0007's Testing Strategy scenario 5 (escape-set
scoping) — the two demand opposite dispositions from the same table. Also
blocks the Phase 1 decision on whether `Table.CheckValid()` runs before or
inside `gate`'s ordering chain.

**NOTE (not a separate finding)**: the two clauses are *reconcilable* — a
whole-table structural precondition legitimately precedes every verdict-level
ordering fact — but the reconciliation is nowhere written. 0009 never cites
0007's ordering enumeration and 0007 never contemplates a step-0 precondition.
The fix is one sentence naming 0009's precondition as step 0 upstream of
0007's three facts, recorded on both implement stages.

## FINDING 2

**TYPE**: round-trip

**A-QUOTE** (RDR 0007, Normative Contracts, `Row.RequiresOwned` block):
> "Row.RequiresOwned names the owned tag keys the row's
> post-guard transition depends on — the keys its `Writes`
> require, which per RDR 0002 includes an authored clear
> (normalization "renders as a `<clear>` write", so the kernel
> `Row` carries no separate clear list)."

and (RDR 0007, SURVIVOR MEMBERSHIP block):
> "the owned-state scan runs over
> survivors, so an unevaluable row's RequiresOwned keys DO
> raise owned_state_unavailable (they are not skipped as
> "undecided"), and the undecidable check runs over the same
> set."

**B-QUOTE** (RDR 0009): **silent** — the string `RequiresOwned` appears zero
times in the entire document. Its Phase 2 conformance step names only the
adjacent fields:
> "drop the `Writes` field from the
> `internal/resolve/fixtures_test.go::escapeRow` builder (line
> 257, inherited by its sixteen call sites) … `NextTags` stays on the builder:
> A4 did not widen the predicate."

**EXPLANATION**: Composing the two rules is not idempotent and loses fidelity:
0009 forces every escape row to `len(Writes) == 0`, and 0007 defines
`RequiresOwned` as exactly "the keys its `Writes` require" — so a conforming
escape row's `RequiresOwned` is definitionally empty, yet the shipped
`escapeRow` builder sets `RequiresOwned: []string{"status"}`
(`internal/resolve/fixtures_test.go:255`), 0009's Phase 2 deliberately leaves
it, and 0007's survivor clause then reads those now-meaningless keys to raise a
non-escapable `owned_state_unavailable` on a row that provably writes nothing.

**SEVERITY**: blocks-impl

**OWNERSHIP**: joint — 0007 owns the `RequiresOwned` narrowing and 0009 owns
the escape-row emptiness; the derived consequence (escape rows carry no
`RequiresOwned`) follows only from both and is owned by neither.

**BLOCKS**: RDR 0009 Phase 2's fixture-conformance scope (three sites vs four),
and RDR 0009 A3's "changes no frozen assertion outcome" verdict — A3's spike
stripped `Writes` and `NextTags` only, never `RequiresOwned`, so it does not
cover the state the composed contracts require. It also blocks RDR 0007's
Testing Strategy scenario 5 leg (a), whose "unevaluable escape row" is built by
`escapeRow` and would, post-0009, either error at entry (Finding 1) or refuse
`owned_state_unavailable` from a stale `RequiresOwned` rather than
`guard_unevaluable`.

**Round-trip statement, explicitly**: normalize an authored escape rule →
kernel `Row` (0002/0009: no writes, no clears) → interpret `RequiresOwned`
(0007: the keys `Writes` require) → the field must round-trip to empty. It does
not: the inverse mapping recovers `["status"]` from a row whose forward mapping
produced no writes at all. Neither RDR's prose is individually wrong.

## FINDING 3

**TYPE**: contradiction

**A-QUOTE** (RDR 0007, Normative Contracts, mapping-totality block):
> "An
> evaluator MUST surface it outside the verdict channel —
> never by answering GuardUnevaluable — and at this seam the
> only out-of-band surface that exists is a PANIC. That is
> named concretely because the alternatives do not exist:
> `Evaluate` returns a bare `GuardResult`, and the kernel's
> own error return (`resolve.go::Resolve`: "the error return
> is reserved for programmer mistakes, not for modeled
> refusals") is Resolve's, unreachable from inside the seam.
> … it is a programmer
> defect, and the kernel MUST NOT recover the panic into a
> verdict or refusal."

**B-QUOTE** (RDR 0009, Approach):
> "the kernel's `Resolve` checks the
> table's rows at entry and returns a Go error naming the
> offending row's `RuleID` and `SourceLocator`. The error is
> the channel RDR 0001 explicitly reserves for "programmer
> mistakes": a malformed table is a broken producer, not a
> behavioral disposition of the input tuple"

**EXPLANATION**: Both RDRs route a *producer/programmer defect at the
0001 kernel boundary* and pick incompatible surfaces from the same RDR 0001
sentence — 0009 normalizes the Go error return as that class's home while 0007
declares the same return unreachable for its own instance of the class and
mandates an unrecovered panic, so a `flow` verb calling `Resolve` must handle
one producer-defect class as a returned `error` (wrappable into `CLIError`,
exit 2, stable code) and a structurally identical one as a process crash, with
no rule stating which producer defects get which surface.

**SEVERITY**: risks-impl

**OWNERSHIP**: joint — the split of RDR 0001's single reserved
programmer-mistake channel across two seams is a shared allocation decision;
neither RDR's local choice is wrong in isolation.

**BLOCKS**: RDR 0009 Prerequisite "The `flow` verb that first calls `Resolve`
wraps a breach into `CLIError{Group: GroupInternal}`" — the verb's error
contract cannot be specified without knowing whether `Resolve` may also panic.
It also blocks RDR 0009's Failure Modes claim "Recovery: fix the producer — the
table value is broken; there is nothing to retry" from being the complete
producer-defect runbook.

**Secondary note (same finding, not separate)**: 0009's `CheckValid` doc
comment is normatively required to state "that nothing else is checked (in
particular not the Escape-class restriction to no_match/ambiguous_match that
Row's doc records for RDR 0002)". That disclaimer is correct and is *compatible*
with 0007's reliance on RDR 0002 L292 escape-class closure — the probe question
about escape-list closure resolves **clean**: 0007 assumes escape lists carry
only `no_match`/`ambiguous_match` and treats `guard_unevaluable` as
structurally non-escapable; 0009 neither checks nor contradicts that. But it
means a table can pass `CheckValid`, reach the guard seam, and panic — so the
disclaimer widens the surface Finding 3 describes rather than narrowing it.

## Verdict

**NEEDS_DECISION.** Findings 1 and 2 are blocks-impl and both are *joint* —
neither RDR can be corrected unilaterally without a shared precedence and
payload decision, and this project does not amend Final RDRs. Both decisions
must be recorded against the implement stages of 0007 and 0009 before either is
built, and 0009 must be built first or its precondition must be reconciled with
0007's Phase 2 harness fixtures, which are constructed from the same
`escapeRow` builder 0009's Phase 2 rewrites.
