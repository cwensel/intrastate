## 1. The three most likely ways implementation goes wrong — inter-RDR

### 1a. One refusal class, three meanings, and a discriminator nobody can read

The set mints `execution_failure` from three producers with three applied senses. 0026:C1 `refusal:` — a held pipe on the direct write leg after the child was reaped is "a post-run refusal — `Applied()` is true". 0028:C1.3 `order:` — every pre-mutation refusal the `edit` binding mints has no applied sense, `Applied()` false (0028:S27 asserts it). The shipped command writer's non-zero exit sits between them, "0004/0025's shipped decision, not reopened" (JDR 0003, What this does not decide). All three are `codeAccessorFailed`, exit 3.

The root cause is JDR 0003 §D1 rule 3, "the applied sense is `Applied()`, set by the executor, never prose," restated by 0026:C1 and 0028:A8 as a settled constraint. Source says otherwise: `Refusal.applied` is unexported, `Applied()` has no non-test caller (0026:A8 records this itself: "23 `.Applied()` hits across `internal/`, every one in a `_test.go`"), and no JSON field carries it. What reaches the agent loop — the JD-1 stake, "an agent loop deciding whether it must re-read before retrying a write" — is `flow_exec.go::detailMayHaveApplied`, a sentence composed into `detail`. 0026 knows this and asserts on it: S1's "rendered half asserts on the envelope's `detail` field carrying `detailMayHaveApplied`". That is option (a) of §D1, "prose per producer", moved from `Err` to `Detail`. The JDR ruled (a) out with the premise that `Applied()` "is already false for every `execution_failure` by construction" — and then wrote rule 3, which makes it true for 0026's case. The home contradicts itself (C-6), so neither producer can be told it is wrong.

Symptom: an agent gets exit 3 from `set-state`, reads `detail`, and either finds a rule-id token (0028: fix the model — but exit 3 told it to retry unchanged) or a "may have been applied" sentence (0026: re-read first), or neither (shipped command writer). It branches on prose. Rows C-1, C-6.

### 1b. 0028:C1.6 makes the linted argv and the executed argv different strings

0027's whole product is one sentence a reviewer can hold: refuse when an interpreter word is followed by its inline-code flag anywhere in argv; read the two named forms yourself. Its authority surface is "argv WORDS only" (0027:C1 `reads:`), and its joint check disposed 0028 as "no shared decision, no bridge surface" after comparing 0028 "on its problem statement" (0027:JC1). 0028:C1.6 is the bridge surface: `{tag.<key>}` becomes a whole argv element bound from `--tag` at invocation, "under 0025:C2's rule unchanged". Source: clause 3 of `carrierDefect` (`load.go:1099-1119`) tests each element for membership in the placeholder vocabulary and nothing else — no position rule, no argv0 exclusion. `["{tag.a}","{tag.b}","{tag.c}"]` lints green under 0027 (no listed interpreter word is present at lint time) and green under 0028 (three declared tags), and executes whatever the caller types. Neither of 0027's out-of-scope forms (one-word string, stdin) names it; 0027:A4's "the admitted-and-executes set equals C1's named list" was computed over a fixed argv, which C1.6 abolishes.

Two smaller drifts ride the same clause. `cmdbind.go::substitute` refuses an `{artifact}` value beginning with `-` "which a tool can parse as a flag"; C1.6 carries no such rule for tag values (C-4). And 0028's cross-cutting gate says the record "adds no new source of caller-supplied value" — true of the file write, false of the argv word (C-12).

Symptom: the reviewer approves a model on the strength of the shipped `--help-all` promise; the model's read-back reader is `["{tag.tool}","status","{artifact}"]`; the caller binds `--tag tool=sh`. Rows C-3, C-4, C-12.

### 1c. Two shared functions, three records, zero recorded owners

`internal/accessor/executor.go::Executor.Write` is modified by 0026 (A8: an `errors.As` for the typed held-pipe error in the `err != nil` arm or in `refusalOf`, setting `applied`) and by 0028 (A2/A10: a gate pre-check between `readerFor` and `Apply`, plus a `Registry` field). 0026:JC1 arm 1 reports `overlaps[] empty`; 0028:JC1 arm 1 lists three anchors, none in `executor.go`. `internal/table/load.go::carrierDefect` is modified by 0027 (clause 4's predicate; the `isInterp` value clause 3's exemption reads at `:1114`) and 0028 (the "neither" arm; the placeholder membership test at `:1100`, which must become a declared-tag family check and therefore a signature change; five tail categories). Both JCs call this "disjoint clauses of one function". Clause 3 is one clause, touched by both.

Root cause: the anchor-intersect ran over anchors as spelled, and the two records spell the same function differently (`executor.go::Write` vs `Executor.Write`), or cite the sub-clause rather than the function. The disposition "cite-don't-restate, 0025:C5 owns the clause map" leaves nothing that says which record's edit to clause 3 is applied first and what the merged clause reports for a brace-bearing `{tag.x}` element under a wrapper.

Symptom: the second lander opens a function the first has already rewritten, with no contract line naming the interaction; 0026:A8's "either placement compiles" invites the `refusalOf` placement that sets `applied` on reads (C-9). Rows C-7, C-8, C-9, C-11.

## 2. Which RDR in the set will be rewritten within 6 weeks of shipping

**0028, at C1.6 and at C1.3's class choice.** Not 0026, not 0027.

C1.6 is the section. It was "scored separately, because the matrix above is about the write carrier and C1.6 is not one" (0028:§decision-rationale) and it is the only part of the set that changes what a subprocess receives on argv from the caller. It will be rewritten because the first reviewer who reads 0027's shipped promise beside a C1.6 reader will ask why `{tag.<key>}` may sit at argv0, why it lacks `substitute`'s `-` refusal that `{artifact}` has, and why 0027's out-of-scope list does not name "a word bound at invocation". The honest amendment — position-restricted (never argv0, never adjacent to a listed interpreter's flag), `-`-prefix refused, and named in 0027's promise — is a successor record, and it will be seeded the week the consumer's row-addressed verb lands and the MVV runs for the first time.

C1.3's `order:` line is the second site. "No new refusal class is introduced" puts every stale-model refusal on exit 3, and `docs/cli-output-contract.md` says in so many words that a request refusal on exit 3 makes "the caller spin on an input it must instead fix". The in-tree precedent (`ClassReadBackMismatch`, exit 2, "re-running the same request unchanged cannot help") is one arm above. The first agent that retries a `edit_anchor_unmatched` on an unlinked README row until its budget runs out will force the choice JDR 0003 deferred to "0028 by citation" and 0028 never made: a new class, or a `Detail`-token-to-exit-code mapping that JDR 0001 §D10 rule 2 forbids ("inner discriminators ride one structured field").

0026 will not be rewritten; it will be *extended* by a record nobody owns (C-5). 0027 will not be rewritten because its predicate is correct over the surface it claims — the surface just stopped being the executed argv.

## 3. The cross-cutting assumption that will not survive first contact

**"The applied sense is `Applied()`."** JDR 0003 §D1 rule 3; 0026:C1 `refusal:` ("carried per JDR 0003 §D1 through the executor's write arm"); 0028:A8 ("the same class distinguished by `Applied()`, exactly as rule 3 intends"); 0028:S27 ("`Applied()` false").

It does not survive because nothing outside `_test.go` calls it and nothing serialises it. The first real user — the agent loop the JDR names as its stake — sees `{"code":"accessor-failed","detail":"…"}` and an exit code of 3 for a 0026 held pipe (applied), a 0028 stale anchor (not applied), and a shipped command writer's non-zero exit (unknown). The applied sense the set spent a JDR homing is expressed to that user as the presence or absence of the sentence "the write command already ran, so the mutation may have been applied" — for 0028's case, a sentence that is *false* on its face ("the write command already ran" of a binding that runs no command) and is simply absent, which is indistinguishable from the shipped writer's silence.

The set has every fact needed to see this. 0026:A8 counts the zero callers. 0026:S1 asserts on the prose. 0028:S27 cites `docs/cli-output-contract.md` for `param`/`findings[]` and then asserts nothing about them. JDR 0001 §D10 rule 3 gives `CLIError` exactly one structured discriminator slot, `findings[]`, and neither record puts the applied sense or the reason token in it. The assumption survived three joint checks because each record tested it at the accessor seam, where `Applied()` exists, and never at the envelope, where the user is.

A close second: **"the argv `lint` reviews is the argv that executes"** — 0027:C1 `reads:`, 0027:A4, and every one of 0027's 264 sampled vectors, all fixed argv. 0028:C1.6 ends that. Rows C-1 (primary), C-3 (second).

## 4. Premortem — written six weeks after the set shipped

The consumer's `rdr-write.toml` shipped on 0028 the day the row-addressed `rdr status --row` verb landed. Three records flipped to Final in the first hour. The fourth was `0006`, one of the two rows the README carries in the unlinked `| NNNN |` form (0028:F7). `flow set-state` refused `edit_anchor_unmatched` for `readme-flip`, exactly as MVV step 8 promised, and exited 3. The kata-flight agent driving the pipeline reads exit codes, not `detail`; exit 3 is "repair the environment and re-run unchanged" (`docs/cli-output-contract.md`), so it re-ran unchanged, sixty times, until its budget expired. Its transcript reads "accessor `readme-flip` could not be executed" sixty times. Nobody looked at `detail` because `accessor-failed` is the code a hung `rdr` binary would also produce (C-2). The fix was a one-line README edit; finding it cost an afternoon.

That afternoon produced the second failure. The operator, now reading `detail`, saw that the record flip had landed and the README flip had refused — two artifacts disagreeing, as 0028:C1.3 `write:` says they may — and asked the agent to "re-read before retrying". The agent's branch was `if strings.Contains(detail, "may have been applied")`. For 0028's refusal the sentence is absent, so the agent classified the edit as not applied and re-planned from the old Status; the record was already Final. `resolve` produced `none`, `set-state` applied nothing, and the pipeline reported success with the README still stale. The applied discriminator is `Refusal.Applied()` (JDR 0003 §D1 rule 3), which the agent cannot call because it is a Go method with no JSON field (C-1). The fallback was the prose the JDR forbade.

Week three: a reviewer approved a second consumer's model. Its read-back reader was `["{tag.tool}", "status", "-json", "{artifact}"]` — the author wanted to swap between `rdr` and a local fork by `--tag tool=…`. `intrastate lint` was green; the `--help-all` text 0027 Phase 3 shipped said a listed interpreter followed by its flag would be refused anywhere in argv, and there was none. The consumer's CI bound `--tag tool=sh` by a typo in a matrix variable; `sh status -json /path` failed, the read-back went `read_back_incomplete`, and the edit stayed applied. Harmless — but the reviewer, tracing it, found that `["{tag.a}","{tag.b}","{tag.c}"]` lints green and asked why the check that exists "to make inline shell visible where the review can see it" (0027:§problem-statement) cannot see a word the caller binds. 0027:C1's out-of-scope list names two forms; this is a third (C-3). `substitute` refuses a `-`-prefixed `{artifact}`; nothing refuses a `-`-prefixed tag (C-4). The 0028 gate response had said the record "adds no new source of caller-supplied value" (C-12). A successor RDR was seeded to restrict C1.6.

Week four, 0026 landed. It had been implemented second because 0028's Prerequisites named the consumer's verb and never named 0026 (C-10). The implementer opened `Executor.Write` and found 0028's gate pre-check already between `readerFor` and `Apply`; the JC said `overlaps[] empty` (C-7). Following 0026:A8's "refinement", she put the held-pipe `errors.As` in `refusalOf`, the shared constructor. Every read refusal that wrapped a held-pipe error now carried `applied = true`, and the read-back leg — which already set it — was fine, so S1 passed. The regression showed up in `flow resolve` against a reader whose helper escaped: the CLI rendered "the write command already ran" on a read (C-9). 0026:C1 says reads are `Applied()` false "as today"; the test that would have pinned it was never written because A8 said either placement compiles.

Week five, the case 0026 was written for. An author declared `timeout = "2s"` against a helper that backgrounds a `setsid` daemon inheriting stdout. The CLI returned in 3.0 s — the record's promise, kept — with class `timeout` and `detail` empty, as 0025:C4's `detail:` rule requires and 0026:F6 accepts. The author raised the timeout to 10 s; it returned in 11 s, `detail` empty. 0026:F6 predicted this sentence for sentence and registered the fix as a 7.1 demand: some record must open 0025:C4's `detail:` rule, or it is "a Stage-6 route-back for 0025". 7.1 closed with no owner; 0025 is Implemented and cannot be routed back (C-5). The diagnostic apparatus 0026 built — `DrainGrace`, the three-valued drain report, the typed held-pipe error — is unreachable on the journey that motivated it, for the third record in a row, exactly as F6 said.

Week six, the 0027 lander opened `carrierDefect` and found clause 3 already rewritten by 0028 to take declared tags, with the whitespace-exemption comment still reading "clause 4 fires only when argv0 (after the `env` walk) names a listed interpreter". Under position-freedom that sentence is false, `interpreterForm`'s `env` walk was deleted, and a `{tag.x}`-bearing string under `nice sh -c` reported `command_unknown_placeholder` on one branch and `command_shell_interpreter` on the other depending on which record's clause-3 edit sat first (C-8). 0027:S6 pinned `Categories()` unchanged; 0028 had appended five; the golden was regenerated without anyone deciding whether that was allowed (C-11).

None of these are bugs in a record. Each record is internally consistent and its S-rows pass. The failures live between them, at the seams the joint checks disposed as "cite, don't restate" — and in one case at a home (JDR 0003 §D1) whose `0028:C3` citations had to be corrected to `0028:C1.3` after lock and which contradicts itself on the one fact the set turns on (C-6).
