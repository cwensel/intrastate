## 1. Prospective hindsight — the failure narrative

The change shipped clean. The conformance suite grew its kind-discriminating cases, all three named construction sites were wired to the loaded model, and the zero-fields test was deleted with a commit message quoting Claim 2 verbatim.

Week two: the first incident. A customer had been routing on an ad-hoc key — one the CLI admits without declaration, exactly as a governing record permits — and guarding on it with plain string equality. That worked for months because the raw-string eq neither knew nor cared about declarations. After upgrade, the key is absent from the kind map, the new missing-key arm answers unevaluable, and every resolve on that flow refuses `flow-guard-unevaluable`. The customer's tag value is well-formed; the refusal message tells them it isn't. Support escalates; the hotfix special-cases nil-or-missing to "fall back to exact string comparison" — but only at the runtime construction site, because that is where the pager pointed. Lint's evaluator still answers unevaluable. Lint and runtime now disagree about the same model, which the old stateless struct made structurally impossible.

Week five: a quieter incident, never attributed to the release for a month. A model authored years ago carried a row guarded `eq retries 07` — a typo that made the row dead. Dead rows are invisible. Under typed numeric comparison the row came alive and began shadowing the `unless` row below it. No refusal, no log line: a silent reroute, delivered by the RDR whose problem statement is silent misroutes. The lint corpus diff that would have flagged the flip was never run, because Claim 4 said lint verdicts could not change.

Week eight: a second implementer runs the conformance suite. It passes. In production their evaluator disagrees with ours on every set-kind guard (no arm was ever specified for `set`), on `--tag flag=True` (boolean tokens were never enumerated), and on an `in` list with one malformed member. The suite passed because the fixture's kinds were consumed through a string→kind converter that silently dropped the kind name it didn't recognize — the fixture is a plain string map precisely so that no type could catch this.

The post-mortem's escaped-defect row reads: "the missing-key arm was a new semantic decision, not an application of the governing record; the one record that vetoed it — undeclared-key admission — was cited nowhere in the proposal."

## 2. Obstacle negation

### Claim 1 negated: guard-referenced keys exist that no declaration covers

The kernel is declaration-free and the CLI admits undeclared `--tag` keys (a governing record exists for exactly this admission). Nothing stated in the brief makes the loader reject a guard atom whose key has no declaration — and if such a rejection existed, the missing-key → unevaluable arm would be dead code, which the design instead treats as a live arm. So the live population includes models with guards on undeclared keys, where raw-string eq currently returns GuardTrue/GuardFalse correctly for enum-like use. The approach flips all of those to unevaluable: a refusal regression on working models, semantically indistinguishable at the seam from the malformed-int case the fix targets. The approach must answer: is missing-declaration (a) load error, (b) scalar fallback, or (c) unevaluable — and under whose record's authority? The brief silently chose (c) without citing a license.

Corollary hole: `set` is one of the five declared kinds and has no specified eq/in arm at all. Whatever the code does for set-kind keys is undesigned behavior shipping as contract.

### Claim 2 negated: the zero-fields assertion was more than a proxy

Statelessness bought three properties, and "doesn't read the runtime tag view" is only one:

1. **Interchangeability** — any two evaluator values are the same evaluator; lint and runtime cannot diverge. With a model-derived map, divergence requires only two construction sites fed different loads (reload, hotfix, test fixture). The brief's own mitigation ("must each construct over the same loaded model") concedes the property is lost and replaces structure with discipline.
2. **A tripwire** — the deleted test is the only thing that would have failed if someone later injected the runtime tag view itself into the evaluator. Its replacement is unspecified; the fence against the actually-forbidden state (runtime data) goes down along with the proxy.
3. **A safe zero value** — `struct{}{}` was fully functional; the new zero value is a landmine (see Claim 3).

The approach must answer: what structural assertion replaces the deleted one, distinguishing load-time declaration state (permitted) from runtime view state (forbidden)?

### Claim 3 negated: a construction site without the model, plus the sites nobody counted

"Three non-test construction sites" is a census of today's callers, not a property of the type. The type is exported at a seam a declaration-free kernel delegates to; the brief itself says the kernel has no declarations. If the kernel (or any library consumer) ever constructs the evaluator — and before this change, constructing it was a zero-cost literal anyone could write — it constructs the nil-map evaluator. Nil map behavior under the stated arms: every key missing → every eq/in unevaluable → every guarded row refuses. That is a total outage from one missed literal, and Go will not force the constructor. Alternatively, if nil is special-cased to legacy string comparison "for safety," the old silent-misroute behavior survives at exactly the uncounted sites. Either branch is a shipped defect; the design specifies neither.

The approach must answer: how is construction-without-declarations made impossible or loudly-defined (unexported field + constructor-only, nil-map panic, or a defined nil disposition in the conformance suite)?

### Claim 4 negated: lint verdicts do change, and the "benign" flip is a silent reroute

Claim 4 covers only held values ("lint renders held values from the declared domain in canonical form"). It is silent about guard literals, which lint also pushes through the same evaluator at every product point. A malformed or non-canonical literal on an int-kind key changes lint's verdict at every product point from False to Unevaluable — a third value lint's product enumeration must now have a disposition for, meaning either lint's output changes on existing models (claim falsified) or lint grows an undesigned folding rule (a new masking site).

The conceded `"07"` False→True flip is understated: rows dead-by-typo come alive and shadow siblings with no model edit, no refusal, and no announcement — a production reroute of exactly the "silent misroute" class in the problem statement, introduced by the fix. And the int arm is underspecified where it will be litigated: overflow past the parser's width, sign prefixes, whitespace, and `in` lists with a mix of parseable and unparseable members (atom-level unevaluable vs member-skip changes which row wins).

### Claim 5 negated: the string-map fixture moves the cycle risk into an untested conversion seam

A plain `map[string]string` fixture avoids importing the loader's Kind type, but every consumer must now convert kind-name strings into its own kind representation, and that converter is outside the published contract. An unrecognized string ("integer" vs "int", a typo, a kind added to the fixture after an implementer vendored it) is silently dropped or defaulted — and a dropped kind means those conformance cases run under the missing-key arm and can pass for the wrong reason. Nothing stated makes the suite fail on an unconverted kind or on a kind with zero discriminating cases, so the fixture can go vacuous without a red test. Cross-implementer contract by unchecked string agreement is contract by discipline again.

## 4. Refutation targets — the three seed classes applied here

**Seed 1 (unopened binding clause).** The proposal leans five-times-over on the governing record that fixed "present value a typed operator cannot parse → unevaluable." The ONE clause it never opens is the record governing undeclared `--tag` key admission. If that record admits undeclared keys as first-class routing inputs, then missing-key → unevaluable is a resolution-level veto of admitted keys — the shipped control flow negates the proposal's claim that the refusal taxonomy and existing behavior are "unchanged" for well-formed inputs. Same shape as the seed: heavy citation of the friendly record, zero citation of the vetoing one. Demand: the missing-key arm's licensing clause, quoted, before lock.

**Seed 2 (producer-cardinality premise never checked).** The kind map licenses the whole design on two producer premises stated nowhere: one declaration per key in the loaded model (else last-write-wins silently assigns kinds), and identity between the key form the normalizer stamps on atoms and the key form declarations carry (else every lookup misses and the entire model folds to unevaluable — the filter-inversion shape of the seed, where the mechanism's effect inverts because the producer emits something other than what the premise assumed). Neither premise is claimed, tested, or assigned an owner in the brief. Demand: loader-side duplicate rejection and a key-form round-trip test as preconditions of the map's validity.

**Seed 3 (misread citation as warrant).** Two instances. First, the upstream-validation rejection cites the openness of "where view-level conformance checking lives" as a reason not to decide it — while the chosen carrier decides it de facto: conformance lives at the guard seam, lazily, only for keys guards reference. Openness is being borrowed as authority for a choice that closes the question in a particular (partial) way. Second, the governing record is cited as having "already fixed" the semantics this design implements, but the record's scope is unparseable present values under typed operators; the missing-declaration arm and the author-literal-malformation routing are extensions by analogy wearing the record's authority. If the record is opened and says only what the brief quotes, two of the five arm behaviors rest on no warrant at all. Demand: quote the record's operative sentence next to each of the five arm behaviors; any arm the sentence does not cover is a new decision this RDR must own explicitly.

## Mitigations to fold (for the packet)

1. Open and cite the undeclared-key admission record; decide the missing-key arm under it (load-time rejection of guards on undeclared keys, or scalar fallback) — do not ship missing→unevaluable on the current no-warrant basis.
2. Specify the `set` eq/in arms and the exact bool token set in the conformance suite; add mixed-`in`-list, overflow, and sign/whitespace int cases.
3. Make the evaluator unconstructible without declarations (unexported field, constructor-only) with a defined loud nil disposition; add the named replacement structural test for no-runtime-view state and the lint/runtime same-model agreement test.
4. Run the lint-corpus before/after diff; enumerate every False→True literal flip as a release-noted behavior change or route unparseable literals to lint/load findings.
5. Add fixture meta-tests: every kind name converts, every kind has a discriminating case; add loader duplicate-declaration rejection and atom-key/declaration-key identity tests.
