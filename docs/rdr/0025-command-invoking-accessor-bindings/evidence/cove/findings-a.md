## Steps 1–2 — Twelve verification questions, answered independently

Each answer was derived without reference to the others.

**Q1 (codebase).** Does `internal/cli/config/` — the package C6 names as the home of `allow_commands` discovery — exist?
**A1. No.** `ls internal/cli/config` errors *No such file or directory*; `find . -type d -name config -not -path ./.git/*` returns nothing. Broader: `grep -rn "intrastate.toml" --include=*.go .` returns zero hits and `grep -rn "UserConfigDir\|UserHomeDir\|XDG_CONFIG\|os.Getenv" internal/ cmd/` (non-test) returns zero hits. The repo has **no user configuration subsystem whatsoever**. C6 cites a package as if it were existing infrastructure.

**Q2 (codebase).** Does `accessor.Refusal` have a `Detail` field for C4's stderr tail and C6's gate name?
**A2. No.** `internal/accessor/model.go:280-308`: `Class, Accessor, Capability, Role, Timeout, Keys, Expected, Observed, Reason, applied`. `Detail` exists only on `accessor.Finding` (`model.go:138-139`, "Detail names the offending key or role"), which is the validation type and never travels on a refusal.

**Q3 (codebase).** If a command binding produced a stderr tail today, would it reach the user?
**A3. No.** `internal/cli/flow_exec.go:384-386`: `case accessor.ClassExecutionFailure: return envErr(codeAccessorFailed, id, "the accessor \`"+id+"\` could not be executed")` — three arguments, no `Detail` assignment. Compare the neighbouring arms, which *do* set it (`ce.Detail = detailMayHaveApplied` at lines 379 and 397). So `execution_failure` is the one class whose CLI rendering carries no detail channel at all — precisely the class C4 and C6 route every command diagnostic through.

**Q4 (codebase).** Is `internal/accessor/executor.go::invokeWrite` — the symbol A4 anchors its read-back claim to — a real symbol?
**A4. No.** The `Executor` methods are `selects` (33), `Read` (81), `invokeRead` (156), `Gate` (186), `Write` (235). `grep -rn invokeWrite internal/` returns zero non-test hits. `readerFor` has exactly one caller: `executor.go:275`, inside `Write`.

**Q5 (codebase).** Is `internal/cli/flowbind/flowbind.go::Reader.run` — the symbol A9 anchors to — a real symbol?
**A5. No.** `func (r Reader)` yields `Capability` (179) and `Read` (189). The `Path` read A9 means is `flowbind.go:192`, in `Reader.Read`. A9's two other named sites, `Writer.Apply` (264) and `Gate.Gate` (319), are real.

**Q6 (codebase).** Is `table.Category` a genuinely open set, or does adding a constant require a second registration?

C5 adds five constants and never mentions `Categories()`.

**Q7 (codebase).** Does any sibling path in this repo already spawn a child process in production code?

No.** `grep -rn "os/exec\|exec.Command\|Setpgid\|WaitDelay" --include=*.go .` hits only `internal/resolve/resolve_test.go:387` (a string literal in a list), `internal/guard/guard_adversarial_0003_test.go:20,796` (a test re-execing the test binary), and this RDR's own spike programs under `docs/rdr/0025-.../evidence/spikes/`. Yes.** `internal/cli/flowbind/flowbind.go:110-136`: `type store map[string]string` with `json.Unmarshal(buf, &s)`, and the package comment makes the semantics normative — "Key PRESENCE is what distinguishes an empty set from a cleared key… a format that encoded absence as an empty string would collapse [REQ-66 and REQ-107]." ## Step 3 — Findings

### F1 — `0025:C6` · class (a) · codebase claim NOT-FOUND
**Claim:** the execution gate reads `allow_commands` from "user-scope `intrastate.toml`" via "`internal/cli/config/` discovery".
**Evidence:** `ls internal/cli/config` → *No such file or directory*; `find . -type d -name config` → nothing; `grep -rn "intrastate.toml" --include=*.go .` → 0 hits; `grep -rn "UserConfigDir\|UserHomeDir\|XDG_CONFIG\|os.Getenv" internal/ cmd/` (non-test) → 0 hits. The only flag machinery is `internal/cli/root.go:186`, a single `PersistentFlags().String(respond.FlagName, …)`.
**Why it matters:** C6 is written as if it were *conforming to* existing infrastructure ("`internal/cli/config/` discovery" reads as a citation), when it is in fact **specifying a whole new subsystem**: file location, precedence, format, parse-failure behaviour, and the `--allow-commands` flag, none of which the record fixes. This is the highest-value finding: it is a new capability hiding inside a parenthetical, it is load-bearing for S7 and MVV-3, and §capability-dependencies does not list it. Either C6 must specify the discovery contract (path, precedence, malformed-config disposition) or a peer RDR must own it and C6 must cite that peer.

### F2 — `0025:C4`, `0025:C6`, `0025:F1`, `0025:F2`, `0025:F3` · class (a) · codebase claim REFUTED
**Claim:** C4 — "`Detail` carries the last 4 KiB of stderr"; C6 — refuses "`execution_failure`, Detail naming `allow_commands`"; F1/F2/F3 restate it.
**Evidence:** `internal/accessor/model.go:280-308` — `Refusal` has no `Detail` field (only `Finding` does, `model.go:139`). `internal/cli/flow_exec.go:384-386` — the `ClassExecutionFailure` arm constructs `envErr(codeAccessorFailed, id, …)` and sets no `Detail`, unlike its neighbours at 379 and 397 which do (`ce.Detail = detailMayHaveApplied`).
**Why it matters:** every command-binding diagnostic C4/C6 promises — stderr tail, gate name, spawn error, malformed-envelope reason — routes through a field that does not exist on the refusal type and is not populated on the one CLI arm that would render it. Without a carrier decision, `execution_failure` on a command binding is indistinguishable from `execution_failure` on a file binding, and F1's "load-time defects name the entry and the offending element" has no runtime counterpart. C4 must either add a field to `accessor.Refusal` (a change to RDR 0004's structured-value contract, which is a joint-check trigger) or name a different carrier.

### F3 — `0025:A4` · class (a) · anchor REFUTED
**Claim:** `readerFor` is "called from `internal/accessor/executor.go::invokeWrite` for read-back".
**Evidence:** `grep -rn invokeWrite internal/` → 0 non-test hits. The `Executor` methods are `selects`(33), `Read`(81), `invokeRead`(156), `Gate`(186), `Write`(235). The real call site is `executor.go:275` inside `Write`.
**Why it matters:** the *behavior* A4 asserts is true and I confirmed it independently, so the assumption stands — but the anchor is fictional. The mechanical checker reported 32/32 resolving, which means it did not resolve method-level anchors, i.e. **the anchor check is weaker than it appears** and other `path::Symbol.method` cites carry no verification. An implementer following A4 to `invokeWrite` finds nothing.

### F4 — `0025:A9` · class (a) · anchor REFUTED
**Claim:** the file binding's runtime `Path` reads happen in "`internal/cli/flowbind/flowbind.go::Reader.run`".
**Evidence:** `grep "func (r Reader)" internal/cli/flowbind/flowbind.go` → `Capability` (179), `Read` (189). No `run`. The `Path` read is at `flowbind.go:192`, inside `Reader.Read`. A9's sibling cites `::Writer.Apply` (real, 264) and `::Gate.Gate` (real, 319).
**Why it matters:** same weakness as F3, and here it lands on the record's one genuinely exhaustive claim. The substance of A9 is **correct** — I verified the whole `.Path` sweep independently and found nothing A9 missed — so the fix is a one-token rename, not a reopened assumption. Worth fixing precisely *because* A9 is the claim a future reader will most want to trust.

### F5 — `0025:C3`, `0025:D-wire-byte-format` · class (b) · new rule with an existing sibling
**Claim:** C3 fixes `stdout (read, output = "json")` as a "flat JSON object of strings; an omitted key is not-carried".
**Sibling:** `internal/cli/flowbind/flowbind.go:110-136` — `type store map[string]string`, decoded by `load()` via `json.Unmarshal`, with the package comment making presence-vs-absence normative: "Key PRESENCE is what distinguishes an empty set from a cleared key… REQ-66 and REQ-107 turn on exactly that distinction."
**Why it matters:** two decoders of one wire shape, with the semantics stated normatively in two places and cited in neither direction. The §approach text even gestures at it ("the same shape intrastate's own artifact … already use") without naming the sibling or deciding whether the decode is shared. If they drift — on `null` values, on non-string members, on duplicate keys — the artifact and the envelope stop agreeing about what "not carried" means, which is the one distinction `0004:C8` and `0004:C11` both rest on. C3 should either cite `flowbind`'s store semantics as the definition it inherits, or state why a second, independent decoder is correct.

### F6 — `0025:C3`, `0025:D-selection-predicate` · class (b) · new discriminator with an existing sibling
**Claim:** C3's `exit_verdicts` maps child exit codes to `{allow, deny, indeterminate}`, with every unlisted code falling to `execution_failure`.
**Sibling:** `internal/cli/flowbind/flowbind.go:78-105` — `gatePrefix`/`unreachableSuffix` + `verdictFor` already implement exactly that four-way split (three verdicts plus a not-a-verdict escape that `Gate.Gate` at :318-322 turns into an execution failure), keyed on declared path suffixes instead of integers.
**Why it matters:** after this RDR the codebase has **two** independent mappings from a declared string/integer to the same closed verdict set, both deciding the "never launder a failure into a verdict" rule. §approach calls the existing one "magic `path` suffixes" that the RDR ends the accretion of, but D-selection-predicate keeps the file binding for `path` entries — so the suffix vocabulary survives untouched and the accretion is doubled, not ended. Decide explicitly: retire `verdictFor`, or state that it is fixture-only surface that command bindings do not supersede.

### F7 — `0025:C5` · class (d) · silence revealing a missing requirement
**Claim:** C5 names five new `table.Category` constants (`command_and_path_conflict`, `command_empty`, `command_unknown_placeholder`, `command_shell_interpreter`, `command_output_shape`).
**Evidence:** `internal/table/category.go:19-52` declares the constants and `:56-88` re-lists all 28 in `func Categories()`, under an explicit RDR 0024 rule: "The wire slug and the registered category are ONE decision, so each constant here also takes an entry in `Categories()` below."
**Why it matters:** `Categories()` is the closed-set accessor; a constant that skips it is invisible to whatever enumerates the vocabulary (help text, conformance tests, docs). C5 is silent on the registration, and §testing-strategy S1 asserts only "rejected with its own named C5 `table.Category`" — which passes even if the constant never joins `Categories()`. One clause in C5 and one assertion in S1 close it.

### F8 — `0025:G-contradiction`, `0025:G-scope`, `0025:G-cross-cutting` · class (d) · silence
**Claim:** the three gate sub-sections carry written responses.
**Evidence:** all three are verbatim template boilerplate. `§contradiction-check` = `[State any conflicts between Research Findings and the Proposed Solution…]`; `§scope-verification` = `[Confirm the Minimum Viable Validation is in scope…]`; `§cross-cutting-concerns` = the full candidate menu plus the canonical-form checklist, unedited.
**Why it matters:** §risks-and-mitigations defers **three** items explicitly to the cross-cutting gate — secret/credential lifecycle for argv-visible credentials, a retry/settle policy for eventually-consistent read-back, and a bare-`argv0` lint advisory — and the gate response that must dispose of them is unwritten. Additionally, `incremental adoption` is squarely in play (C6's one-boolean opt-in, listed as a Consequence) and `versioning` is in play (C3's `INTRASTATE_PROTOCOL=1` out-of-band version marker). Status is `Draft`, so this is expected remaining work rather than a lock violation, but it is the gating item.

### F9 — `0025:§approach` / `0025:§consequences` · class (c) · internal contradiction
**Claim (§consequences):** "`flowbind`'s magic-path simulation stops being the only way to express command-like behaviour, **ending the accretion at this seam**."
**Counter-claim (`0025:D-selection-predicate`):** "`path` → file binding (today's `flowbind`)" — the path carrier, and therefore `verdictFor`/`unreachable`/`sealedKey`, is retained unchanged.
**Why it matters:** the record simultaneously claims the accretion ends and preserves the accreted mechanism as a first-class carrier. Both cannot be true. Either the file binding's magic-suffix vocabulary is scheduled for retirement (say so, and say when), or the Consequence overstates and should read "stops being the only way" without the "ending the accretion" clause. This matters for the reader who has to decide, at implementation time, whether to write new tests against the suffix vocabulary.

### F10 — `0025:§prerequisites`, `0025:S5` · class (d) · silence
**Claim:** the unchecked box — "RDR 0016 lands first (fail-closed `readerFor`), or 0025 records that command-write read-back inherits first-match until it does (A4)."
**Evidence:** `internal/accessor/model.go:231-238` — `readerFor` returns on first match over `reg.Definitions` with no cardinality check; `flowbind/registry.go:31` iterates `slices.Sorted(keys(m.Readers))`, so "first" is *name-sorted*, an ordering nothing in the record states. §testing-strategy S5 covers write read-back but assumes one reader per role.
**Why it matters:** A4 supplies the "or" branch in prose, so the prerequisite is satisfiable — but under it, a model with two command readers for one role silently read-backs through the alphabetically-first one, and no scenario pins that. Either S5 gains a two-reader arm asserting the inherited behaviour, or the box is closed by hard-ordering on 0016.
