## Step 3 — Findings

1. **[0025:A9] class (a) — REFUTED codebase citation.** A9's evidence cites `internal/cli/flowbind/flowbind.go::Reader.run` as one of the enumerated consumer sites. No such method exists; the actual method is `Reader.Read` (`flowbind.go:189`). The underlying claim (this is the one site where a path-constructed binding executes its own copied `Path`) is still true in substance — `Reader.Read` does read `art.Path`/`r.Path` — but the symbol name in the RDR's own prose is wrong. Low severity (doesn't change the conclusion) but exactly the kind of rot Step 0 exists to catch, since a mechanical anchor-resolution check would not have caught a wrong *method name* cited in body prose (only `path::Symbol` in a formal anchor list resolves; free-text symbol mentions inside evidence paragraphs do not get that check). Fix: correct to `Reader.Read`.

2. **[0025:§scope-verification, §assumption-verification, §contradiction-check, §cross-cutting-concerns, §proportionality] class (d) — silence / missing requirement.** All five Finalization Gate sub-sections are unfilled template instruction text, not authored responses. The record is `Status: Draft` and cannot legitimately proceed to `rdr-finalize` until these are written. This is the single largest gap found — it is structural, not a subtle semantic error, and blocks lock outright.

3. **[0025:C6] class (d) — silence / missing capability audit entry.** C6's `allow_commands` execution gate depends on `internal/cli/config/` discovery infrastructure that does not exist anywhere in the repo today (no config package, no TOML user-scope loader, no `AllowCommands` symbol). The RDR's own §Existing Infrastructure Audit table enumerates four other needed capabilities and their existing surfaces/limits, but omits this one entirely — the audit is silent on a capability C6 is fully load-bearing for. This should be added as a fifth row (Capability: user-scope config discovery; Existing Surface: none; Decision: build; Spec Impact: C6) so the gap is visible before implementation rather than discovered mid-build.

4. **[0025:A1, §capability-dependencies] class (a/nuance) — codebase claim needs precision.** A1 and the Capability Dependencies table describe the process-group/deadline mechanism (Setpgid, Cancel=SIGKILL, WaitDelay) as something "the executor's context deadline" already does ("building on the executor's context deadline plus process-group termination"), when in fact `internal/accessor/executor.go` today implements only the plain `context.WithTimeout` half — none of the process-group/Setpgid/WaitDelay machinery exists in production code; it exists only in the A1 spike. The RDR is reasonably careful elsewhere (Capability Dependencies row: "Process-group termination + drain bound — Go stdlib os/exec ... Available") to mark this as a *stdlib* capability rather than an *executor* capability, so this is not a contradiction, but a reader skimming A1's assumption prose alone could wrongly conclude the mechanism already exists in `internal/accessor`. Recommend tightening A1's own wording to make explicit that `invokeRead`/`invokeWrite` (the write path) contain none of this today and it is 100% new code for this RDR to add.

5. **[0025:A9] class (b), confirmed as NOT a finding — checked, no sibling duplication.** Verified the exhaustive-consumer claim by grep; no additional `.Path` consumer exists beyond the four sites A9 names. This is listed here only to record that the check was run and passed — no action needed.

6. **[0025:C5, command_shell_interpreter] class (d) — silence on closure.** Unlike C3's exit-code maps (explicitly "the maps list verdict codes only") and unlike the eight-member `ValidationCode` closure (A6, explicitly closed and tested), C5's `command_shell_interpreter` defect names four example forms (`sh -c`, `bash -c`, `python -c`, "env chains") without stating whether this enumeration is closed (a fixed list validation checks against) or an open-ended heuristic pattern-matcher. Given the RDR's own stated principle that "not a shell runner" must be "enforced rather than aspirational," an open-ended heuristic is exactly the kind of soft check that erodes over time (new interpreters, `perl -e`, `ruby -e`, `node -e`, `awk` programs, etc. are not named). This should be resolved before implementation: either declare the closed list normatively (as C3/A8 do for exit codes) or explicitly accept it as a best-effort heuristic and say so.

7. **[0025:A2] class (d) — silence on the Windows caveat's practical implication.** A2 notes "on Windows the vector is re-quoted into a single command line... v1's supported platforms are the Unix ones the process-group mechanism needs," but no Normative Contract (C1-C6) or Failure Mode explicitly states what happens if a command entry is declared on a model that later runs on Windows — is it a load-time defect, a runtime refusal, or silently broken argv semantics? The RDR is silent on the cross-platform failure mode for this specific case, which is a gap Failure Modes (F1-F7) should probably enumerate (e.g., as a documented known-unsupported-platform behavior) given the RDR explicitly acknowledges the divergence exists.
