## 1. Prospective hindsight — the failure narrative, written as accomplished fact

`--plan-only` shipped on `flow resolve` in the release after this record locked. Adoption was immediate and narrow: the two chained skills set it on their second and third resolve calls, exactly as designed. Measured transcript cost on the 48-fact model dropped, though by 54% rather than the 72% in the record — the record's ~430-byte figure had been the `emit` + `rule` answer, and the shipped plan group also carried `gates`, `writes`, and `next`, which on populated calls added back roughly 250 bytes. Nobody filed anything; the flag worked, the number was smaller than promised, and the promise lived only in the RDR.

The first real break came from `outcome`. A skill chained `resolve` → (branch) → `resolve` and used the second call's plan to drive a write. Under `--plan-only` the second response had no `outcome`, and the skill's branch logic — which had been reading `outcome` to decide whether the second resolve had re-recognized the same situation or a new one — fell through to its default arm. It fell through silently, because the consumer struct decoded the absent key to `""`, and `""` was the struct's zero value for a field whose meaningful values were all non-empty. The record had cited exactly this property as *safety*: "absent keys decode to zero values." The branch had been written before the flag existed, against a payload where `outcome` was always present, and no test covered "outcome absent." It ran for three weeks. It was noticed when an operator reviewing a transcript asked why a plan for outcome `escalate` had been applied under a run whose first resolve had recognized `defer` — the transcript showed the second resolve's projected payload, and there was no `outcome` line to contradict the operator's assumption that it matched.

The second break was the partition drift. Two fields were added to the resolve payload in the same cycle: `confidence` (added by the team that owned recognition) and `source_rows` (added by the decision-table team). Neither author read the RDR. `confidence` was added to the payload struct and appeared in `--plan-only` output because the projection had been implemented as an explicit *omit* list — the echo group — so anything new defaulted into the plan group. `source_rows` was a 900-byte array of the matching table rows. Under `--plan-only`, output went from 700 bytes to 1600 — larger than the unprojected payload had been at lock time. The chained-call token cost that motivated the entire record was now worse with the flag than without it had been a quarter earlier. Nothing failed: there was no test asserting the projected key set, only tests asserting that the six echo fields were absent. The design record's sentence "plus any future field assigned to that group" had assigned nothing, because assignment was a prose obligation on authors who never saw the prose.

The third break was the sibling copy. A fourth verb, `flow preview`, shipped with `--plan-only` registered on it — the author had seen the flag on `resolve`, found it useful-sounding, and wired it to a projection that did not exist, so the flag parsed and did nothing. The non-registration oracle did not fire: it asserted absence from the three siblings and the root that existed when it was written, and `preview` was not on that list. An agent that had learned "always pass `--plan-only`" from the resolve skill passed it to `preview` and received full-width output, paying for it on every turn while believing it had opted out.

The fourth, smallest, and most annoying break: a human ran `flow resolve --plan-only` in text mode during an incident. The projection had been implemented with a `map[string]any` (because the payload struct could not express absent keys without either `omitempty` on fields whose empty values were meaningful, or a parallel struct). The text flattener, which had been written against the struct and relied on field order, emitted the projected map in Go's map-iteration order — different on each invocation. The operator, diffing two runs, saw the lines reorder and spent forty minutes convinced the resolver was nondeterministic. The design record had asserted that projecting before the gateway made "text and JSON agree automatically," and JSON *had* been fine — a single line, order-stable enough not to matter. Text had never been tested under the flag.

None of these were caught by the shipped test suite, because every shipped test was a default-mode test plus one `--plan-only` test asserting six absences.

## 2. Obstacle negation — each of the 8 claims negated, with a failure scenario

### Negation of claim 1 — "projecting before the gateway makes text and JSON agree automatically"

**Negated:** Projecting before the gateway makes the two modes agree only if the projected value is the *same Go type* as the unprojected one. It is not, and cannot be. The requirement is "absent JSON keys," and a Go struct emits a key unless the field is tagged `omitempty` and holds an empty value — which is precisely the confusion claim 6 promises to avoid. So the implementation must either (a) tag the echo fields `omitempty` and zero them, which makes "projected away" and "legitimately empty" the same wire state, contradicting claim 6; (b) make the echo fields pointers and nil them, which changes default-mode marshaling for every field and risks moving default oracles, contradicting claim 5; or (c) marshal through a `map[string]any` or a second struct type, which is a second shape whose text flattening is a second code path.

**Failure scenario the approach must answer:** implementation picks (c). The text flattener consumes the marshaled bytes (per the environment note: "renders both JSON ... and flattened text from the same bytes"), so nested structures under `gates` — which were struct-shaped — arrive as `map[string]interface{}` and flatten with different key ordering and possibly different scalar formatting (a `time.Time` that had a `MarshalJSON` on the struct path now round-trips through `any` as a string, or a numeric field arrives as `float64` and renders `1e+06` instead of `1000000`). Default text and `--plan-only` text disagree on the *shared* plan fields, which the design says are unchanged.

### Negation of claim 2 — "the payload partitions cleanly into decision content and pure request echo"

**Negated:** `outcome` and `revision` are outputs, not echoes. `outcome` is the resolver's recognition result — the thing the verb's own problem statement calls "one recognized outcome." Placing the recognized outcome in the "request/input echo" group is a category error visible from the problem statement in this brief. `revision` identifies which version of the model produced the plan; it is the only provenance in the payload. And `observed` is only an echo if the resolver performs no normalization on the facts — an unverified premise about the producing code.

**Failure scenario:** a chained caller receives a plan under `--plan-only` and cannot answer "which outcome was this a plan for?" — it must re-derive the recognition it just paid the CLI to perform, or trust that the outcome is the one it assumed. When a model revision changes the outcome→plan mapping mid-session, the caller has no revision field to detect that the second call answered from a different model than the first. Cross-revision plan mixing goes undetected.

### Negation of claim 3 — "the flag is report-only; same readers, same kernel, same gates, same refusals, same exit codes"

**Negated:** "Report-only" is a property the design asserts but nothing enforces. The design gives no invariant test tying `--plan-only` execution to default execution; the assertion rests on the implementer choosing to project at the last step. And the motivating pressure — token/latency cost — actively rewards a future change that skips work whose output is projected away. `owned` and `readers` in particular sound like fields populated by side-effecting reader lookups; if a later optimization skips those lookups under the flag, a reader error becomes invisible under `--plan-only` and visible under default.

**Failure scenario:** an agent uses `--plan-only` for the fast path and, on a surprising result, re-runs without the flag to "see everything." The unprojected re-run refuses (exit non-zero) where the projected run succeeded, because the unprojected run ran a reader the projected run had skipped. The agent now has two contradictory answers for one input and no way to decide which is authoritative.

### Negation of claim 4 — "omitting the echo recovers ~1529 → ~430, ~72%"

**Negated:** the ~430 byte figure is stated in the brief as "the `emit` + `rule` answer" — two fields. The plan group is eight. The reduction being claimed was measured on a projection *narrower* than the one being shipped. The shipped projection retains `gates`, `next`, `writes`, `clear`, `escaped`, `escape_class`, none of which are in 430 bytes. Further, the 75%-echo measurement is a single datapoint on a 48-fact table; echo bytes scale with fact count while plan bytes scale with gate/write count, so the ratio is a property of that one model, not of resolve.

**Failure scenario:** the flag lands, and on the second-largest consumer model (12 facts, 9 gates, a populated `writes`) the reduction is 18%. The consumer team, having budgeted a migration against 72%, abandons the flag; the record's headline number is now a false claim in the permanent design history, and the migration that justified the work does not happen.

### Negation of claim 5 — "no shipped test, fixture, or consumer requires the echo fields' presence in a way an opt-in flag disturbs"

**Negated:** the claim is scoped to *disturbance of existing tests*, which opt-in trivially satisfies, and it is therefore not evidence of safety. The actual risk is the inverse: the new branch has no oracles at all beyond "six keys absent." Nothing pins the *positive* key set of the projected payload, so any future payload field enters `--plan-only` output unreviewed (P-12), and nothing pins the projected text rendering (P-1).

**Failure scenario:** `source_rows` (or any large derived field) is added to the payload. It defaults into the plan group because the projection is an omit-list. `--plan-only` output grows past the unprojected size at lock time. Every test passes.

### Negation of claim 6 — "absent keys are safe; one consumer struct parses both widths"

**Negated:** "one consumer struct" is the whole evidence base, and it is a sample of one at a moment when the flag has zero users. Absence is safe for a Go struct with lenient decoding and unsafe for: JSON-schema validators with `required`, `jq` expressions that index into `.observed`, any consumer that treats missing-vs-zero as meaningful, and — most sharply — any consumer whose field zero value is a legal value. `outcome` decoding to `""` is exactly this: the projected payload asserts, in the wire language the consumer speaks, that the outcome was empty.

**Failure scenario:** the chained-branch fallthrough in the narrative above. A consumer branches on `outcome`, gets `""`, takes the default arm, and applies the wrong plan. There is no error, no log line, and no test.

### Negation of claim 7 — "a structural non-registration oracle pins the flag to `resolve` only"

**Negated:** the oracle is a negative assertion over an enumerated set of sites that existed when it was written. It has no coverage over sites added later, which is where flag-sprawl actually comes from. A negative-list test does not express the invariant "`--plan-only` exists on exactly one verb"; it expresses "these four specific places do not have it today." Additionally, the oracle checks *registration*, not *behavior* — it says nothing about what a user sees when they pass the flag to a sibling, which per the environment is a generic exit-2 bucket with no verb-scoping hint.

**Failure scenario:** a fifth verb ships with the flag registered (copied because it looked useful) and no projection wired. The oracle passes. Callers pass `--plan-only` to it, get full-width output, and pay for the echo while believing they opted out — the exact cost the record exists to remove, now invisible because the flag is accepted.

### Negation of claim 8 — "the in-flight `dispositions` proposal composes in either landing order"

**Negated:** composition-in-either-order requires each proposal to know the other's partition, which means whichever lands second must edit the first's group table — a coupling, not a composition. And the substantive problem is that `dispositions` is described as *an interpretation of `emit`*; if its derivation also consults the facts, then keeping `dispositions` while projecting `observed` away yields a derived claim stripped of its evidence. Claim 8 assumes the derivation is a pure function of `emit`; the brief does not establish that, and the claim is resting on what a sibling record is *assumed* to say.

**Failure scenario:** `dispositions` lands second, is filed plan-group by its own author without editing this record's table (there is no compile-time forcing function), and a consumer under `--plan-only` receives dispositions it cannot cross-check against the facts that produced them. A mis-derived disposition — the class of bug an evidence field exists to catch — ships and is caught only in production.

### Additional negation — the rejected alternatives

- **Named-field selection, rejected for the drop-`escaped` hazard.** The rejection is correct, and it is a time bomb for the chosen design: the first request for a second profile converts the boolean into an enum and then into a field list, arriving at the rejected design without the always-keep set the rejection identified as the missing safety. The chosen approach should adopt the always-keep concept *now* (`escaped`/`escape_class` and, I argue, `outcome`/`revision` are never projectable) so the invariant survives the inevitable generalization.
- **Gateway verbosity tier, rejected as "structurally impossible."** If the projection requires a second shape anyway (P-1), the impossibility argument does not hold — the same indirection placed in the gateway would be reusable across verbs and would give exactly one place where partition membership is declared. The rejection may be right on cost but is stated as a structural fact that the chosen implementation's own mechanics contradict.
- **Inverted default, rejected because "the echo default is agreed correct."** Agreed by one consumer at one moment. The record's own success metric (wide model migration) is the pressure that will re-open it.

## 4. Refutation targets — the three seed classes applied here

### Seed 1 (the spec asserts a clean split the implementation's control flow contradicts)

**Where it lands here:** "The partition of every current and future payload field into plan-group or echo-group is owned by the design record, not by the caller."

This is a partition that exists only in prose. The shipped code will have *one* of the two lists — almost certainly the echo list, since the mechanism is omission — and the other group will be "everything else," i.e. a default, not a partition. The record's sentence "plus any future field assigned to that group" describes an assignment step that has no place to happen: a new field's author edits the payload struct, not the RDR. Every model in the repo hits the resulting drift the moment a field is added, and nothing fails.

The seed-1 defect was "it routed a case into a class via a peer clause it never cited, while the shipped code discarded the selected value entirely." The isomorph here: the record routes future fields into plan-group-by-default via an implementation detail (omit-list) it never cites, and the "assignment" ceremony it does cite never runs. **Demanded mitigation:** an exhaustive, reflected, test-enforced two-list partition over the payload struct (`TestPayloadFields_AllPartitioned` above), so an unpartitioned field is a build failure rather than a silent default.

### Seed 2 (a "one X per Y" cardinality premise never checked against the producing code)

**Where it lands here:** "about 75% of a resolve's output is the caller's own input echoed back under `observed.*`" and the partition's claim that the echo group is "pure request/input echo."

This is a one-to-one premise — one `observed` entry per caller-supplied fact, values identical — asserted about the producing code without citing it. Seed 2's actual defect was a normalizer that emitted two atoms for one key. The identical hazard exists here: if the resolver defaults absent facts, coerces types, canonicalizes keys, or expands a fact with two operators into two observed entries, then `observed` is not an echo, the caller cannot reconstruct it, and projecting it away removes the only view of what the kernel actually matched against. The brief's own 48-fact framing does not tell us whether the caller supplied 48 facts or supplied 30 and the resolver defaulted 18.

**Demanded mitigation:** `TestResolve_ObservedIsVerbatimEcho` (above) run over the fixture corpus, before lock. If it fails on any model, `observed` moves to plan group or the record must state explicitly that projected callers lose visibility into resolver-side fact derivation.

### Seed 3 (borrowed authority — resting a choice on what a cited record is assumed to say)

**Two instances here.**

*(a) The sibling `dispositions` proposal.* Claim 8 asserts that `dispositions` "is plan-group, never projected, and neither proposal's contract moves." That is a statement about a record this one has not verified — specifically about whether the disposition derivation consults only `emit` or also `observed`/`outcome`. The brief describes `dispositions` as "an interpretation of `emit`," which is the *summary* of the sibling record; the seed-3 failure was precisely a summary that described the opposite of the record's content. If the derivation touches the facts, the composition claim inverts: `--plan-only` then ships an interpretation without its evidence.

*(b) The "settled" echo default.* "The echo is the right default and is settled: a live consumer deliberately dropped its own status call because the resolve already returns every fact it renders." That consumer's decision is authority for "the echo is useful to a rendering consumer" — it is not authority for "the echo is not needed by a chained consumer," which is the different question this record answers. The rejection of the inverted-default alternative rests entirely on this borrowed authority, and the borrowed decision is about a one-call rendering consumer, i.e. the population that would never set the flag either way. The cited evidence is orthogonal to the choice it is being used to settle.

**Demanded mitigation:** for (a), the derivation-input test above, checking the sibling's *code path* rather than its abstract. For (b), restate the inverted-default rejection on its own grounds — "one-call consumers outnumber chained ones and should not need a flag" — rather than on a consumer decision that speaks to a different question.

---

## Bottom line

The approach is a small, reversible, opt-in flag on one verb, and it survives as a shape. It does not survive as specified: the partition puts two *produced* fields (`outcome`, `revision`) in the "pure echo" group, the byte-reduction number is measured against a narrower projection than the one shipping, the future-field partition has no enforcement, the non-registration oracle is a snapshot rather than an invariant, and "report-only" is unenforced. All five are fixable inside the chosen approach — none forces a switch to named-field selection, a gateway tier, or jq.
