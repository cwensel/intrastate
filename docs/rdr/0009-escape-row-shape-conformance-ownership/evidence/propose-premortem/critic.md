## 1. Prospective Hindsight — Failure Narrative (as accomplished fact)

The kernel entry check shipped in March; the normalizer did not — its spec stayed final-but-unimplemented for two more quarters. That window was where everything went wrong.

First incident: a table author added an escape rule and, following an older example, left a write block on it. With no normalizer, nothing rejected it at load. The first `Resolve` against the table returned a Go error on the channel the kernel spec reserves for "parser bugs, IO failures, or programmer mistakes." The CLI mapped that to its internal-error exit code. The operator's runbook said that code means "file a bug against the CLI"; the on-call engineer for the CLI spent half a day bisecting releases before anyone read the table. The error message could not name the source rule — Row carries no provenance — so even after the table was suspected, finding the offending rule was manual (P-1, P-3, P-7).

Second incident: the anticipated non-TOML producer arrived — a service that assembles Row values programmatically. Its row builder copied a template row, Writes included, into escape rows. No load-time gate exists on that path and the design exported no `ValidateTable`; the producer's own tests never called `Resolve` with the full table. The defect was latent until the first production resolve of a customer table, days after deploy (P-2).

Third incident, the ironic one: the original user complaint — "an owned tag has a value no rule in my table ever set, after an escape" — recurred *after* the invariant shipped. The vehicle was NextTags. Escape rows legitimately carry NextTags as "the exit route," but a downstream consumer persisted the route tags into owned tag state. The invariant guarded Writes; the leak rode the field the design explicitly blessed. The disposition again gave no hint (P-5).

Fourth: when the normalizer was finally implemented, its authors — working from their own final spec — chose to render escape rows with a sentinel audit write marking the escape reason. The kernel's entry check, pinned only by a doc comment on Row, rejected every table the new normalizer produced. Two enforcers of "the same" invariant, specified in two documents with no shared conformance artifact, disagreed on what write-free meant (P-10).

Throughout, the frozen adversarial suite stayed green — because stripping Writes from escape fixtures had made the two tests that previously exercised the combination vacuous, and no positive test asserted the entry check fires. A later cleanup deleted the check; nothing went red (P-4, P-9).

## 2. Obstacle Negation (per claim)

**Claim 1 negated — the normalizer is *not* the only production constructor.**
It is not even *a* production constructor today: it is unimplemented. The set of real constructors at ship time is exactly {tests, anything anyone writes next}. The claim quietly converts a future intention into a present guarantee. Scenario: a migration tool, a table-diffing utility, or a programmatic table service constructs Rows directly; none of them pass through spec-B code; the only enforcement they meet is the per-Resolve backstop, which fires in production, not at build time. The design must answer: what artifact does a non-TOML producer call at *construction* time? (P-1, P-2)

**Claim 2 negated — the Go error path is not taxonomy-neutral at the boundary that matters.**
Inside the kernel it is neutral; at the CLI it must become an exit code, and the exit-code peer spec's semantics for that code ("tool defect") are now wrong for a class of table-content failures. "The CLI-contract spec needs no change" is true only if one accepts that operators will misattribute these failures. Scenario: CI pipelines that retry on "table error" but page on "tool error" page humans for a bad table. The design must answer: what does the operator-facing contract say this exit code means after this change? (P-3, P-11)

**Claim 3 negated — the entry check does disturb frozen behavior.**
"Triage confirmed every existing test still discriminates with stripped fixtures" verifies the *existing* tests, not the frozen behavioral property. Two disturbances: (a) a table with a malformed row that no resolution path reaches previously resolved fine; now every Resolve against it errors — a genuine behavior change for inputs the suite may model; (b) the precedence between the entry error and modeled refusals is a new, unpinned decision (given a table with both a malformed row and an input that triggers a modeled refusal, which surfaces?). Scenario: a deployed table with one dormant malformed row bricks all resolutions after upgrade. (P-4)

**Claim 4 negated — the illegal payload is not exactly Writes.**
Two holes. (a) NextTags: if any downstream persists route tags, escape rows mutate owned tag state through the blessed field, reproducing the original complaint verbatim. (b) The clears-reduce-to-sentinel-writes premise is a property of an unimplemented component; producers that never run that reduction can express clearing some other way, and the empty-Writes check is blind to it. The design must answer: what, precisely, does the kernel/persistence layer do with an escape row's NextTags, and where is the sentinel convention pinned as a testable artifact rather than prose? (P-5, P-6)

**Claim 5 negated — a write-bearing escape effect can still be emitted, and failures are not always diagnosable.**
"No write-bearing escape *plan*" may hold while the *effect* (owned-tag mutation after escape) still occurs via NextTags persistence — the invariant is stated over a field, the user's expectation is stated over an outcome. And on the backstop path, diagnosability collapses to a row index at best: the kernel has no source-rule names. "Diagnosable to the responsible producer" is only as good as the error text plus provenance available at Resolve time. (P-5, P-7)

**Claim 6 negated — the check reopens the deferral rather than narrowing it.**
"Kernel assumes a parsed, reviewable table shape" was a clean line: the kernel validates nothing. The new line is "the kernel validates exactly one shape property and assumes the rest," which is not a narrower deferral — it is a different, fuzzier contract. Scenario: the next producer author reads the kernel, sees it rejects malformed escape rows, reasonably infers shape checking is the kernel's job, and skips validation; the next shape defect (one the kernel does not check) ships. Partial validation transfers perceived ownership without transferring actual coverage. (P-8)

## 3. Consumer Artifacts (what would have caught each at review)

- **P-1 / P-2:** User journey "programmatic producer authors an escape row" walked end-to-end from Row construction to first Resolve, with the step where the defect is first detectable marked. Review question forced by the journey: "where is the load-time gate on this path?" Concrete artifact: an exported `ValidateTable(rows) error` (or `Row.Validate`) named in the design, with test `TestValidateTable_EscapeRowWithWrites_NamesOffendingRow`.
- **P-3 / P-11:** Runbook entry / user journey "operator sees exit code E from a resolve" written at review time. If the entry cannot be written without saying "…which might be a tool bug or might be your table," the misroute is exposed. Concrete artifact: golden test in the CLI contract suite `TestExitCode_MalformedTableRow_DistinguishableFromInternalError` (even if the answer is "documented as indistinguishable," it becomes a recorded decision, not drift).
- **P-4:** Named fixture "table containing one unreachable escape+writes row" run through the full frozen suite before/after the change: `TestResolve_DormantMalformedRow_WholeTableRejected` — its expected outcome forces the whole-table-vs-on-path decision into review. Plus precedence pin: `TestResolve_MalformedRow_PrecedesModeledRefusal` (or the inverse), so ordering is a recorded choice.
- **P-5:** User journey "escape fires: dump owned tag state before and after," asserting byte-identical owned tags. Concrete test at whatever layer persists tags: `TestEscape_OwnedTagsUnchangedAfterEscape` — this tests the *outcome* the user complained about, not the field the design chose to guard.
- **P-6:** Cross-spec conformance fixture shared by kernel and normalizer test suites: one canonical "authored clear on ordinary row" input whose normalized Row form is asserted identically in both suites (`TestSentinelWriteRepresentation_SharedFixture`). Any drift in the sentinel convention goes red in one suite.
- **P-7:** Golden error-message test `TestResolve_MalformedRowError_IdentifiesRow` asserting the error names the row (index, id, or provenance). If Row has no identity to name, the test cannot be written — which is itself the review finding.
- **P-8:** A one-table "kernel validation surface" section in the kernel spec listing every property the kernel checks vs. assumes, reviewed against the deferral text. Artifact form: doc table plus test file whose test names enumerate exactly the checked properties, so the surface is greppable.
- **P-9:** Positive precondition test `TestResolve_EscapeRowWithWrites_ReturnsError` (breach in, error out) plus a discrimination check on the stripped fixtures: temporarily revert the entry check and confirm at least one test fails (mutation-style review step, recorded in the evidence). Boundary cases `TestResolve_EscapeRowWithNonNilEmptyWrites_OK` pin the len-based semantics.
- **P-10:** The same shared-fixture artifact as P-6, plus a design-review checklist line: "which document is normative for the Row-level meaning of write-free, and what test binds the other document to it?" A doc comment on Row does not satisfy it; a shared test fixture does.

## 4. Refutation Targets — What Survives a Standard Premortem

With no escaped-defect ledger to seed from, the classes most likely to survive this exercise:

1. **Cross-layer drift (P-10):** the invariant's two enforcers live in different documents at different maturity (implemented kernel vs. final-unimplemented normalizer spec). Every premortem finding above can be individually mitigated and this can still fail, because the binding between the two is prose. The only durable mitigation is a shared executable artifact (common fixture or exported validator both sides call).
2. **Fixture/spec divergence (P-4, P-9):** "bring fixtures into conformance" is a deletion of test signal disguised as cleanup. Without a positive test and a discrimination pass, the suite's greenness after the change proves nothing about the check's existence.
3. **Silent-channel misuse (P-3, P-11):** the "programmer mistakes" error channel is the design's pressure-relief valve around a closed taxonomy. It is correct for this one case in isolation; the failure is cumulative and cross-release, which is exactly the kind no single-change premortem flags. Worth a recorded rule: what qualifies for the error channel, stated in the kernel spec, so the next borrower has to argue against text rather than precedent.
4. **Outcome-vs-field mismatch (P-5):** the user's invariant is about persisted tag state after escape; the design's invariant is about a struct field. These coincide only under an assumption about NextTags persistence that the brief never states. This is the finding most likely to reproduce the original bug report after ship.

## Verdict Reasoning

The approach — producer-side obligation with a kernel backstop on the reserved error channel, single Row shape — survives every negation with mitigations; none of the failures forces a different ownership structure (a type split or kernel-only ownership would trade these failures for worse ones: representational churn or a validating kernel). But the draft as briefed is missing: an exported construction-time validator for non-TOML producers, a positive precondition test plus discrimination check, pinned whole-table/precedence semantics, row-identifying error text, a recorded NextTags-persistence decision, an operator-facing statement of what the error exit code now covers, and a shared fixture binding kernel and normalizer to one sentinel convention.
