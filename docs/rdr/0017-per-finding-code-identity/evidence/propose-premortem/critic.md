## 1. Prospective hindsight — the failure narrative, as accomplished fact

The change shipped in the next minor. For six days nothing happened, because single-disposition refusals — the common case — emit only `flow-*` finding codes and are byte-compatible with the old output.

Day 7: the first mixed-disposition refusal in a live pipeline. The repair skill that motivated the fix worked. But a second consumer — an envelope-sanity wrapper another team had written around `flow resolve`, which validated every `findings[i].code` against the published closed refusal-code table before dispatching — hit `gate_allowed`, classified the envelope as corrupt, and put the run into retry. Retries produced the identical envelope. The pipeline wedged (P-3). The wrapper's author pointed at the contract doc; the doc's schema appendix still enumerated finding codes from the refusal table, because Claim 1's "the doc already defines `code` as the finding's own discriminator" had been asserted from memory, not quoted — the actual clause said "one of the codes from the table above" (P-1, P-2).

Day 12: an ops script that estimated refusal severity by counting findings whose code matched the envelope code began reporting "1 gate denied" on rows where it used to report "3". Nobody had called that pattern "correct", but it had been stable for a year, and the alerting thresholds tuned to it went quiet (P-9).

Day 19: the subtle one. Under a `flow-gate-denied` envelope with one denying and one indeterminate gate, a skill walked `findings[]` looking for "the code that explains the refusal" and matched the first `flow-*` literal it found — the indeterminate one. It repaired the wrong gate. The exact defect class this RDR existed to kill — mis-attribution via `findings[i].code` — had survived, because the refusal literals still live at two levels with two meanings and nothing in the payload says which level a given literal is speaking at (P-6).

The retro found the premortem had accepted Claims 1 and 2 on the proposal's own citation, without a verbatim quote of the doc clause or a schema grep — the same three-stage escape as Seed 1 and Seed 3.

## 2. Obstacle negation

### Claim 1 — "the doc already defines per-finding `code` as the finding's own discriminator"
Negation: it does not, or it does so only in prose while a normative schema/enum elsewhere in the same doc closes finding codes over the refusal table. Scenario: the contract doc's field table says "code — the machine-readable code for this finding" (ambiguous) and the appendix schema says `enum: [flow-…]` (vetoing). The change then IS a new contract, shipped under a "fix" label, skipping the review a contract change requires. The proposal cites the doc but never quotes the one clause that decides the question — Seed 1's exact shape.

### Claim 2 — "REQ-51 fixes only the envelope code and cardinality"
Negation: the assignment of per-finding codes may live not in REQ-51 but in a blanket clause ("all codes in a refusal envelope are drawn from the closed table"), a locked schema, or a peer RDR's resolution that this RDR's author never opened. "No locked requirement assigns per-finding code values" is an absence claim; absence claims about a corpus you haven't exhaustively quoted are precisely what escaped three stages in Seed 1.

### Claim 3 — "no exit group, therefore no table row, therefore no spec review"
Negation: the inference chain assumes the spec-review rule is scoped to the table rather than to the emitted-code vocabulary. If the rule's intent is "no new machine-branchable literal reaches consumers unreviewed", the underscore spelling is a loophole, not a compliance. Scenario: a later audit treats `gate_allowed` as an unreviewed contract surface; the precedent then licenses every future producer to mint unreviewed slugs, and the closed table stops meaning anything (P-8, P-11).

### Claim 4 — "no existing structured consumer depends on the echo; correct consumers are untouched"
Negation A: consumers that validate finding codes against the table are arguably MORE correct than average, and they break hard on `gate_allowed` (P-3).
Negation B: consumers that count `findings[i].code == envelope.code` change behavior silently (P-9).
Negation C: the claim is asserted, not inventoried. No consumer census is cited. Seed 2's lesson applies: a "cannot break anyone" coupling claim must be checked against actual shipped consumer control flow, where one early validation branch can make the claimed safety unreachable.

### Claim 5 — "keeping refusal literals on refusing findings is principled"
Negation: it creates a two-level homonym. `flow-gate-denied` in the envelope means "the transition was refused because at least one gate denied"; in a finding it means "this gate denied". Same literal, different referent, different cardinality semantics. A consumer (or grep, or log aggregator) that keys on the literal without tracking JSON depth mis-attributes exactly as before (P-6). "Principled, not accidental" also fails aesthetically under Claim 6: the principle yields dash-literals for two dispositions and an underscore slug for the third, which no future producer can derive from the rule alone (P-7).

### Claim 6 — "the identity rule generalizes to future multi-subject producers"
Negation: the rule says WHAT the code names (own disposition) but not HOW it is spelled, who registers it, or what happens on collision. First future producer with an "allowed"-like subject faces: reuse `gate_allowed` (semantic collision), mint `check_allowed` (vocabulary sprawl), or ask for a table row (contradicting this RDR's fourth rejection). Meanwhile the sibling success verb already ships a third vocabulary (`allow`/`deny`/`indeterminate`). A generalizing rule that three existing surfaces already spell three ways is not generalizing (P-7, P-8).

### Rejected alternative 1 — full rename to producer-local slugs
Rejection reason attacked: "renaming breaks consumers for zero information gain" directly contradicts Claim 4's "no consumer depends on finding codes carrying the envelope code / correct consumers don't branch on them". If consumers don't branch on finding codes, the rename breaks nobody and buys a single uniform vocabulary plus elimination of the P-6 homonym — strictly better. If consumers DO branch on finding codes, then Claim 4 is false and the chosen approach's own change is a break too. The rejection and the safety claim cannot both stand; one of them is the inverted-rejection escape (P-5).

### Rejected alternative 2 — carry disposition in `class`
Rejection reason attacked: rests entirely on an uninspected peer record ("field ownership assigns `class` to a different design record", "its shipped meaning is the failure class of an escape-scoped finding"). Seed 3 is literally this: a warrant borrowed from a peer record that, when opened, said the opposite. Until the peer record's clause is quoted verbatim in this RDR's evidence, the rejection is unverified (P-10).

### Rejected alternative 3 — status quo + doc fix
Rejection reason attacked: "the behavior contradicts the contract doc's definition of `code`" is Claim 1 again; if Claim 1 falls (P-1), this rejection loses one of its two legs. The other leg (structured mis-attribution) stands — but note the chosen approach only half-fixes it, per P-6.

### Rejected alternative 4 — new `flow-gate-allowed` table row
Rejection reason attacked: "the table is exit-group-bearing refusal surface and an allow is not a refusal" is coherent ONLY if nothing in shipped code or schema requires finding codes to come from the table (P-2, P-4). If something does, this rejected alternative is the only one that satisfies the shipped constraint, and the rejection reason has argued away the sole conforming design.

### Missing alternative (not in the brief's list)
A per-finding `disposition` (or `verdict`) field carrying `allow`/`deny`/`indeterminate` — the sibling verb's exact vocabulary — with `code` left alone or deprecated for gate findings. Fixes mis-attribution, adds no code literal, creates no homonym, aligns the two verbs. Its absence from the weighed set means the "once and generally" decision was made without its strongest competitor (P-13).

## 3. Consumer artifacts — what would have caught each failure at review time

- **P-1, P-2 — Contract-clause citation artifact.** A review-gate requirement: verbatim quotes, with file and line, of (a) the contract doc's definition of `findings[i].code`, (b) REQ-51's exact text, and (c) the result of a sweep for any schema/enum/lint that constrains finding codes (`grep -rn 'findings' --include='*.json' --include='*.cue' --include='*.go' | grep -i 'enum\|code'` or equivalent). No quote, no lock. This is the direct countermeasure to Seeds 1 and 3.
- **P-3 — Schema conformance test.** `TestEnvelopeSchema_MixedRefusal_GateAllowedFindingValidates`: build the mixed-disposition envelope with a `gate_allowed` finding and validate it against the SHIPPED published schema (not a schema updated in the same commit). Red before the doc/schema change lands; proves the ordering of contract change vs. behavior change.
- **P-4 — Derivation-independence test.** `TestRefusalEnvelope_CodeAndExitGroup_IndependentOfFindingCodes`: construct refusals where the findings list is permuted and where a `gate_allowed` finding appears first; assert envelope code and process exit group are unchanged and no default/panic branch fires. This is the Seed-2 countermeasure: check the claim against control flow, not intention.
- **P-5 — Consumer inventory.** A committed census: every in-tree skill/script that reads `findings[i].code`, with the branch each takes on (i) `flow-*` literals and (ii) an unknown code. If the census is empty, the full-rename rejection must be re-argued; if non-empty, Claim 4 must be re-argued. The contradiction cannot survive an actual list.
- **P-6 — Level-disambiguation journey.** `TestConsumerJourney_IndeterminateEnvelope_DenyFindingNotMisattributed`: envelope `flow-gate-indeterminate` (or `-denied`) with mixed findings; drive the REAL repair skill (not a mock) and assert it selects the gate whose finding disposition matches the envelope's cause, never keying on the first `flow-*` literal in `findings[]`.
- **P-7, P-13 — Vocabulary alignment table.** A one-page design artifact enumerating every surface that names a gate verdict (`gates[]` values, finding codes, envelope codes) in one table. Review question: "why three spellings of `allow`?" forces either alignment with the sibling verb or a recorded reason.
- **P-8 — Slug registry test.** `TestProducerLocalSlugs_RegisteredAndUnique`: a committed registry of producer-local finding slugs; test fails on an emitted slug absent from the registry or registered twice. Turns "producer-local" from folklore into a checked namespace.
- **P-9 — Count-stability journey.** `TestConsumerJourney_RefusalGateCount_MixedDispositions`: for a 3-gate row (1 deny, 1 indeterminate, 1 allow), assert the documented way to count refusing gates and pin its value across the change; any consumer using the undocumented `code == envelope.code` count shows up as a golden-file diff here.
- **P-10 — Peer-record quote.** Same form as the P-1 artifact: the `class`-ownership record's operative sentence quoted verbatim in this RDR's evidence before the `class` alternative may be marked rejected.
- **P-12 — Mixed-disposition golden fixture.** `TestResolveRefusal_MixedDispositions_EachFindingCodeMatchesOwnGateVerdict`: one fixture with all three dispositions on one row, asserting per-finding `(gate accessor, code)` pairs exactly — not three single-disposition fixtures, which the echo bug would also have passed for deny-only and indeterminate-only rows.

## 4. Refutation targets — the three seed classes located in THIS proposal

- **Seed 1 (cited the peer contract five times, never the veto clause; named a partition the code didn't have).** This proposal cites the contract doc (Claim 1), REQ-51 (Claim 2), and the closed table's exit-group property (Claim 3) — but never quotes the one clause that decides whether finding codes are closed over the table. And it confidently names a partition — "exit-group-bearing refusal codes" vs. "producer-local non-refusal slugs" — that the shipped code may simply not have: if there is one code namespace validated in one place, the partition exists only in this document. P-1, P-2, P-4 are this class. Countermeasure: the citation artifacts above; no verbatim quote, no lock.
- **Seed 2 (widening claim negated by shipped control flow).** Claim 4 is a "strictly additive — cannot break a correct consumer" claim, the same genus as "strictly widening — cannot turn an acceptance into a refusal". The seed's lesson: one early return above a switch defeated the claim. Here the candidate defeaters are (a) a consumer-side validation branch that rejects unknown codes before any correct branching is reached (P-3), and (b) a producer-side envelope/exit derivation that scans finding codes (P-4). Neither has been checked against actual control flow in the brief. P-3, P-4, P-9 are this class.
- **Seed 3 (borrowed authority; every reviewer accepted the warrant without opening the entry).** The `class`-field rejection rests wholly on what "field ownership" and "its shipped meaning" say in a peer design record that this proposal characterizes but does not quote (P-10). Claim 1 has the same structure against the contract doc. The seed escaped because every reviewer accepted the paraphrase; the only countermeasure is the opened entry, quoted, in evidence.

## Verdict rationale

The core rule — a finding's `code` names its own disposition, never an echoed envelope code — survives every negation above; no failure scenario forces switching to a rejected alternative. But four things are load-bearing and currently unverified or inconsistent, and each is an identified escape class from this project's own post-mortems: the unquoted doc clause (P-1/P-2), the unchecked derivation/validation control flow (P-3/P-4), the Claim-4-vs-rename contradiction (P-5), and the two-level homonym plus vocabulary split that half-preserves the original defect (P-6/P-7). These are mitigations, not approach-switches: quote the clauses, run the census, add the mixed fixture and journey tests, and either align the slug vocabulary with the sibling `gates[]` verdicts (or the missing `disposition`-field alternative, P-13) or record why not. PASS, blocking until folded.
