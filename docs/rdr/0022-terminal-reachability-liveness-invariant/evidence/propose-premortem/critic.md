# Premortem critique — terminal-reachability liveness invariant (livelock finding)

Scope note: this critique is written from the proposal brief alone. No repository code, no design record, and no search was consulted. Every claim about shipped code shape below is therefore stated as a *question the proposal must answer with a citation*, not as a fact I verified. That framing is deliberate: refutation seed S2 is exactly the failure of asserting a premise about shipped code shape without opening it, and I am structurally unable to avoid that failure here — so I convert it into an explicit obligation on the author rather than pretending to have discharged it.

## Failure narrative (written as accomplished fact)

The livelock check shipped in the lint engine's blocking tier. It was validated against the checked-in production model — two declared terminals, revise self-loops, rewind backedges — which passed unchanged, exactly as the record predicted. The record's claim 8 was true and load-bearing for the review's confidence, and it was the only corpus evidence anyone had.

The first failure was a false red, and it arrived from a model the project did not write. A consumer's model carried a non-terminal key — an attempt counter with an abstract value set `{first, retry, exhausted}` — that guarded the escape edge out of the revise loop. Because the counter key did not participate in any terminal predicate, the split step left it merged. In the merged view, the revise state's abstract node held all three counter values simultaneously, and the guard on the escape row was evaluated against the merged set. The engine's row-matching, which had been written for the dead-end check's purposes, treated the guard as unsatisfiable against the merged value set under one of the split views and satisfiable under another; the backward closure marked the revise state's split node as bad, found the self-loop was an ordinary row, found no edge out of the bad region, and emitted a trapping-sink finding. The consumer traced every concrete execution by hand. Every one of them reached a terminal within four steps. The finding was sound over the declared relation and false about their program, and the finding text — which said the model "cannot reach a declared terminal" — made no distinction between the two. They filed it as a bug. The project's response was that the behavior was documented under the residual clause borrowed from the dead-end check. The consumer pointed out that the dead-end residual was local and this one had swallowed a whole path, and that the doc they had been pointed to did not describe what happened to them. That exchange consumed three weeks and ended with the check being disabled by configuration at two sites, which meant the invariant was not enforced anywhere it mattered.

The second failure was the silent green, and it was found in a postmortem rather than by a user. A large model tripped the 4096 node ceiling during the forward traversal. The ceiling finding fired and blocked, and the liveness check was skipped per the design. The reviewer, reading a single finding that said "model too large," waived it with a comment and shipped — the ceiling finding was understood by the team as a capacity warning, not a correctness gate, because that is what its text said. Six weeks later the model livelocked in production in a rewind cycle that the liveness check would have caught in under a millisecond had it run. The premortem's claim 6 was literally true: nothing was silently green in CI. What was silently green was the ship decision, because a blocking finding about tool capacity does not carry the information that a *different* correctness invariant went unevaluated, and nothing in the artifact record said which invariants had been checked on the shipped revision.

The third failure was structural and showed up during implementation, not in production. The re-anchor step in claim 3 could not be made total. Row successors were, in practice, sometimes subsumed by two incomparable merged nodes and sometimes by none, and the implementer resolved both cases by picking the first match in map iteration order, because the record did not say what else to do. That made finding output nondeterministic on roughly one model in thirty, which the snapshot tests caught as flakes and which was patched by sorting the candidate anchors by a synthesized key. The sort restored determinism and silently changed which node the closure explored, so the check's verdict on those models became an artifact of the sort key. Nobody could say afterward which verdicts had been affected, because the pre-sort behavior was never recorded. Separately, the re-anchor loop was not monotone — narrowing on re-split let it revisit — and on two models it ran until the split closure crossed 4096 and emitted product-too-large on graphs with under twenty authored states. Those users could not act on the refusal: their models were plainly small, and the message told them to reduce a product they had no way to see.

The fourth failure was the inversion, and it is the one that should have been caught in review. When the split closure's termination problem surfaced, the fastest fix available was to drop the re-split step and run the backward closure over merged nodes — the explicitly rejected alternative. It went in as a bug fix, not as a design change, because it made the flakes and the spurious refusals stop and the production model still passed. The rejected alternative's failure mode is false green, so nothing turned red and nothing looked wrong. The shipped tool now carried the blocking severity that had been justified by the split closure's precision, over an analysis that no longer had it. The record still described the split closure. That divergence was found by a reader of the code eleven months later, and by then the check had been green on three models that were subsequently found to contain reachable traps.

## Per-claim negations

**Claim 1 — over-approximation makes accusations sound.**
*Negation:* the composition of merging and splitting is not a pure over-approximation, and even where it is, soundness over the declared relation is not soundness over the user's program.
*Scenario:* a revise state merges three attempt-counter values because the counter is not terminal-participating. The escape row's guard is `counter = exhausted`. The merged node holds `{first, retry, exhausted}`. Whether the escape edge survives into the abstract graph depends entirely on the engine's guard-vs-value-set semantics, which the brief never states. If the engine requires universal satisfaction (all values in the set satisfy the guard — the same "universal per split node" rule claim 2 invokes for terminals), the escape edge is *dropped*, the revise self-loop is the only remaining ordinary row, and a correct model is accused. Dropping edges is the under-approximating direction, which is precisely the unsound direction for a "no path exists" verdict. The approach must state the guard semantics on merged value sets and prove they are existential for edge admission while universal for terminal satisfaction — and if they are both universal, claim 1 is simply false.

**Claim 2 — splitting on terminal-participating keys recovers exactness.**
*Negation:* it recovers exactness of the terminal predicate at a node; the reachability question is about edges, and edges are guarded by non-terminal keys.
*Scenario:* two terminals, `approved` and `rejected`, both keyed on `decision`. Split on `decision`. A rewind backedge is guarded on `reviewer_tier`, a non-terminal key, and only fires for `tier=senior`. In the merged view every node carries `{junior, senior}`, so the backedge is present for all split views. A split node reachable only under `tier=junior` — where the backedge does not exist and the only route out is forward to a terminal — inherits the backedge anyway. That does not by itself create a trap, but the mirror case does: a *forward* edge to a terminal guarded on `tier=senior` is, under universal semantics, dropped from a merged node, and the junior-only region becomes a trap that does not exist. The residual is not a corner: guards on non-terminal keys are the normal way authored models express retry limits and role gates.

**Claim 3 — re-anchoring preserves direction and keeps the closure finite.**
*Negation:* subsumption gives no unique anchor, and re-split after re-anchor is not monotone, so neither the direction nor the termination follows.
*Scenario:* split node S, view `decision=pending`, takes a row to a successor footprint F. F is subsumed by merged node M1 (widened along path A) and by M2 (widened along path B); M1 and M2 are incomparable. Anchoring at M1 yields a terminal-key value set that re-splits into two views; anchoring at M2 yields three, one of which is bad. The verdict depends on the choice. Anchoring at *both* (the conservative move) is the over-approximating choice but multiplies the closure and is what drives the ceiling blowups. The brief must specify: anchor to the join of all subsumers, or to all subsumers, or refuse — and must give the well-founded measure for termination, not merely observe the state space is finite.

**Claim 4 — trapping sink SCC is the right unit.**
*Negation:* the sink is where the model is stuck; the defect is at the entry edge, and multiple sinks share upstream nodes so fixing one need not cure the others.
*Scenario:* bad region with two sink SCCs, T1 and T2, both reachable from bad node B, which is reachable from good node G via one authored row. The finding reports T1 and T2. The authored bug is the single row `G -> B`. The user gets two findings, neither of which names the row they must edit, and fixing either sink leaves B bad via the other. The diagnostic unit should include at least one witness path from a good node into the accused region — a concrete sequence of authored rows — or the finding is not actionable.

**Claim 5 — populations are disjoint.**
*Negation:* disjoint at node granularity, overlapping at defect granularity, and possibly *gapped* because the two checks run over different node sets.
*Scenario (double-code):* state X's only ordinary row is removed by an edit; X becomes dead-end-flagged. X is also the sole exit from a two-state cycle, which now becomes a trap. One edit, two blocking codes, and the user cannot tell they are the same bug.
*Scenario (gap):* the re-anchored closure produces split node S' that the forward fixpoint's dead-end pass never enumerated. S' has no outgoing ordinary row. The dead-end check never saw it; the liveness check excludes it by the "at least one ordinary-row edge" rule. No finding. This is the silent green the design claims to have eliminated, arriving through the seam between the two checks rather than through the ceiling.

**Claim 6 — skipping on truncation leaves no silent green.**
*Negation:* it leaves no silent green *in that CI run*, and that is not the property that matters. The ceiling finding does not carry the information "liveness unevaluated," so any waiver of the ceiling finding is an unrecorded waiver of the liveness invariant.
*Scenario:* reviewer waives a "model too large" finding, believing it to be about tool capacity — which is what it says. Ships. Livelocks. The fix is cheap and specific: when the check is skipped, emit a distinct finding or a machine-readable field naming the invariants that were not evaluated, so a waiver of the ceiling is visibly a waiver of liveness.

**Claim 7 — blocking severity is right.**
*Negation:* the argument has three parts and each is about the tool, not the user. "Blocking tier is extensible" is a permission. "Advisory tier is closed" is a constraint. "Sound over the declared relation" is an internal-consistency property. None of them establishes that a user who receives this finding has an obligation to change their model. Given claims 1–3's negations, some recipients do not.
*Scenario:* a user whose model is correct is blocked, and the only way to clear the finding is to add a transition their runtime will never take, or to change a guard from a non-terminal key to a terminal-participating one purely to make the splitter see it. The linter has now shaped the model against the domain. The mitigation is either a documented suppression path with a recorded reason, or a two-stage rollout (advisory for one release with telemetry on hit rate) — and if the advisory tier is genuinely closed, that constraint is a reason to open it, not a reason to block.

**Claim 8 — production model passes unchanged.**
*Negation:* the production model is the design's training sample. Its passing is evidence of no regression on one input and evidence of nothing about generalization.
*Scenario:* first non-project model hits the false red of claim 1's negation. Required artifact is a corpus: at minimum the production model, a hand-built true-positive trap, a hand-built near-miss that must pass, and a model with a non-terminal-keyed guard on the escape path — the case the approach is structurally weakest on.

**Claim 9 — escape rows are self-loops that never count as progress.**
*Negation:* this is an unverified premise about shipped code shape, of exactly the class that has already burned this project once.
*Scenario:* if any escape row targets a state other than its source, then an escape-only cycle spanning two states contains no ordinary-row edge, is excluded by the rule, and is never reported — a real livelock, silently green, produced by the exclusion clause that was added for precision. Conversely if a row can be escape-flagged in one view and ordinary in another, the exclusion is view-dependent and the finding set depends on split order. The proposal must cite the emitter that constructs escape rows and show the self-loop property is structural, not conventional.

## Consumer artifacts (what would have caught each at review time)

## Refutation-seed application

**S1 (selective citation of a locked peer contract).** The candidate is claim 7's "the blocking tier is extensible ('at least these classes'), the advisory tier is closed." That is a fragment, quoted in the direction that supports the proposal. The uncited remainder of a severity-tier clause conventionally carries the consumer-facing guarantee: what a run with no blocking findings asserts, and what stability consumers may assume about the finding-code set. If that remainder says a clean blocking tier means the enumerated invariants were evaluated, then the claim-6 skip path violates it, and the extensibility permission the proposal relies on comes packaged with an obligation the proposal has discarded. Required: quote the clause whole (A-15). This is the seed's exact shape — control flow in the uncited half vetoing the assumed partition.

**S2 (premise about shipped code shape refuted by the code).** Two candidates, and neither can be discharged from this brief. The stronger is claim 9's "escape rows are self-loop edges" (P-11): a structural assertion about the row emitter, used to justify an *exclusion* clause, which is the direction that produces silent greens rather than noisy reds. The second is claim 5's assumption that the dead-end check and the liveness check range over the same split node population (P-12); the brief says "the same split the shipped dead-end check uses" while claim 3 introduces a re-anchored closure that is, by construction, a different node set. S2's signature failure was a nested loop emitting two atoms where the proposal assumed one — the proposal assumed the shipped code's *shape* rather than reading it, and the shape inverted the fix. Both candidates here have that form: an exclusion or a hand-off justified by an assumed structural property. Required: A-11 and A-9 written as assertions over the shipped emitter and the shipped dead-end pass, before the closure is designed.

**S3 (contract break justified by borrowed authority).** The candidate is claim 2's "matching the dead-end check's documented residual" (P-4). The proposal borrows an acceptance granted to the dead-end check's imprecision and applies it to a path property. The borrowed record's stated harm runs the other way: a local residual misjudges one node and the user sees one wrong finding they can evaluate by inspection. The liveness residual propagates along paths, so one imprecise edge condemns every node upstream, and the user cannot evaluate it by inspection at all. The borrowed record almost certainly never names path-reachability as a covered class — it was written about outgoing-row enumeration. Required: either the dead-end residual clause explicitly covers path properties (quote it), or the liveness residual gets its own written acceptance with its own magnitude stated, and that acceptance is a decision for the user of the tool, not an inheritance.

## Assessment

The check is worth building and the diagnostic instinct (SCC-level trap reporting) is right. What is not established is the pairing of *blocking* severity with an analysis whose precision rests on three unproven premises: the guard semantics on merged value sets (claim 1), the totality and termination of the re-anchor loop (claim 3), and the structural shape of escape rows (claim 9). Any one of those failing turns the blocking finding into a false red on correct models — the one failure mode a blocking tier cannot absorb. The proposal does not fail; it under-specifies, and the under-specified parts are exactly where the escaped-defect ledger says this project loses.
